# 계획 보고서 양식

운영 정책 §10의 양식이다. 위험도에 따라 둘 중 하나를 사용한다. 항목을 임의로 빼지 않는다.

## 용어와 표현 (정책 §6.3 — 두 양식 공통)

- 판정할 수 없는 표현(「적절히」·「가능하면」·「문제없이」)은 구체적 조건으로 바꾼다.
- 약어·은어·프로젝트 내부 용어는 가능한 한 쓰지 않는다. 써야 하면 **최초 등장 시 전체 표현과 의미를 함께** 적는다.
- 전문 용어가 반복되거나 여러 개 등장하면 문서 상단에 용어 정의를 둔다.
- 다른 문서를 참조할 때는 키워드만 적지 말고 **문서명·위치·참조 이유**를 적는다.

---

## A. 낮은 위험 작업 — 간략 계획

보고 후 별도 승인 대기 없이 실행할 수 있다.

```markdown
# 간략 작업 계획

위험도: 낮음

## 목적

## 변경 범위

## 기대 결과

## 검증 방법
```

**검증 담당**: 간략 계획에는 담당 열이 없다. 정책 §6.1의 기본값에 따라 **「검증 방법」에 적은 항목 전부가 검증 담당 Agent의 배정분**이고, 실행 담당은 그중 로컬에서 빠르게 할 수 있는 것을 중복 수행한다. 낮은 위험이어도 **코드 개발이면 검증 담당을 호출**한다(정책 §7.1). 사용자가 직접 판단해야 하는 항목이 있으면 그 줄에 `(담당: 사용자)`를 붙인다.

---

## B. 중간·높은 위험 작업 — 상세 계획

보고 후 **사용자 승인을 받은 뒤** 실행한다. 높은 위험은 대안·영향·복구 방법을 함께 제시한다.

```markdown
# 작업 계획

## 1. 주제

## 2. 목적

## 3. 위험도와 승인 필요 여부

## 4. 범위

### 포함 범위

### 제외 범위

## 5. 상세 작업과 실행 순서

## 6. 선행 조건과 의존성

## 7. 영향 범위와 하위 호환성

## 8. 위험과 복구 방법

## 9. 기대 결과

## 10. 완료 조건

- [ ]

## 11. 검증 방법

| 완료 조건 | 검증 방법 | 담당 | 예상 결과 |
| --------- | --------- | ---- | --------- |
|           |           |      |           |
```

### 작성 시 유의

- **검증 방법의 기본 담당은 검증 담당 Agent**다. 실행 담당은 로컬에서 빠르게 할 수 있는 검증을 중복 수행한다. 사용자가 판단해야 하는 정성적 확인은 담당을 `사용자`로 적는다(정책 §6.1).
- 실행 가능한 검증 명령은 `references/verification-policy.md`의 표에서 고른다.
- 작업을 여러 단위로 나눴으면 §5에 단위별 목적·범위·완료 조건·선행 관계를 적는다(`references/work-splitting.md`).
- 계층적 분할을 선택했으면 그 이유와 수직 분할로 전환할 조건을 §5에 적는다.
- 변경량이 500줄을 넘을 전망이면 재분할을 검토하고, 그대로 진행하는 이유를 §5에 적는다.
