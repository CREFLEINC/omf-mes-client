# 작업 분할 — 이 저장소 적용

정본은 `operating-policy.md` §5다. 이 문서는 분할 우선순위를 이 저장소 구조에 대응시킨 판정 보조 자료다.

## 우선순위 체크리스트

정책 §5의 6단계를 순서대로 적용한다. 충돌하면 위 항목이 이긴다.

1. **단일 목적** — 목적을 한 문장으로 말할 수 있는가. 기능+리팩터링, 수정+신규를 섞지 않았는가
2. **하위 호환·위험 격리** — 공개 인터페이스를 유지하는가. 호환성을 깨는 변경을 분리했는가. 미완성 부분이 노출되지 않는가
3. **독립 완료·검증 가능** — 이 단위만으로 저장소 검증을 통과하는가(`verification-policy.md`). 완료 조건을 독립적으로 판정할 수 있는가
4. **수직 분할 우선** — 관찰 가능한 동작 하나를 완성하는가
5. **계층적 분할은 조건부** — 아래 허용 조건에 해당하는가. 해당하면 이유와 수직 전환 조건을 계획에 적는가
6. **변경량** — 생성 코드·잠금 파일 제외 400줄 이하인가. 500줄 초과 시 재분할 검토 후 사유를 기록했는가

## 이 저장소의 수직 분할 단위

관리웹 화면 작업의 기본 단위는 **화면 슬라이스 1개**다(`apps/web/src/screens/<slice>/`). 한 슬라이스는 그 화면의 필드·컬럼·검증·레이아웃·문구·예외를 소유한다.

관찰 가능한 동작 기준으로 더 잘게 나눌 수 있다.

- 목록 조회와 로딩·빈 상태·오류 표시
- 항목 선택과 상세 표시
- 신규 등록과 입력값 검증
- 수정과 저장 실패(충돌·잠김) 처리
- 사용 중지와 확인 절차

각 단위는 필요한 계층(표현·검증·조회/저장·문구)만 포함한다. 그 화면에 없는 계층을 억지로 만들지 않는다.

## 계층적 분할이 허용되는 경우

정책 §5.5의 조건이 이 저장소에서 실제로 해당하는 것들이다.

| 상황 | 이 저장소의 예 |
| --- | --- |
| 여러 기능이 쓸 안정된 계약·공통 기반 | `packages/api-client` 횡단 규약(ETag·오류 정규화), `patterns/` 공통 workflow |
| 외부 계약이 선행 조건 | 계약(OpenAPI)에서 타입 생성(`pnpm gen:api`) |
| 공통 셸·화면 전환 구조 | `apps/web/src/app`(프로바이더·레이아웃), `routes/` |
| 기술 위험을 먼저 검증하는 짧은 실험 | 목 서버 연동 방식 확인 |

계층적 단위도 그 자체로 빌드·검증을 통과해야 하고, 후속 작업과의 인터페이스(타입·함수 시그니처)를 계획에 명시한다.

## 경계를 지키는 분할 규칙

이 저장소는 허용 의존 방향이 도구로 강제된다(`pnpm dep:check`). 분할이 이 경계를 넘지 않게 한다.

```
routes → screens → patterns → packages
domain(의존 0) ← api-client · ui(domain·api-client 무의존) · i18n
apps 간 직접 의존 금지
```

- `patterns/`에 리소스 이름(`warehouse`·`routing` 등)이나 특정 화면 분기가 들어가야 한다면, 그 로직은 화면 슬라이스 소유다 — 작업을 그렇게 나눈다
- 화면 슬라이스와 `patterns/` 변경이 한 작업에 함께 필요하면 **위험도가 올라간다**(`risk-classification.md`)
- 계약·DS 갱신은 화면 작업과 분리한다

## 분할 결과를 계획에 적는 방법

각 작업 단위마다 다음을 적는다. 항목이 비면 분할이 덜 된 것이다.

- 목적 한 문장
- 포함/제외 범위(파일 경로 수준)
- 이 단위가 끝났을 때 관찰 가능한 변화
- 완료 조건(예/아니요로 판정 가능)
- 검증 방법과 담당
- 선행 작업(있으면 작업 번호로)
