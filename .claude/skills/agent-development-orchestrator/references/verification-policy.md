# 검증 정책 — 이 저장소 적용

정본은 `operating-policy.md` §7·§8이다. 이 문서는 이 저장소에서 실제로 실행 가능한 검증 수단과 절차를 정리한다.

**저장소 적용 v1.1**(2026-08-14)과 **v1.2**(2026-08-18)가 반영돼 있다 — v1.1: 게이트 등급 분리 · 간헐 실패 판별 상한 · 검증·리뷰 병렬과 분담 / v1.2: 승격 조건 세분화 · 기준 상태 도출 규칙 · 기존 실패 면제선 · 뮤테이션 절차. 개정 사유는 `../SKILL.md` 상단의 개정 이력 참조. 기존 조항과 상충하면 나중 판의 조항이 이긴다.

## 저장소 검증 명령

명령은 **저장소 루트**(이 파일 기준 `../../../../`)에서 실행한다. 실행 Node는 `node` devDependency로 24 LTS에 고정돼 있으므로 `pnpm`을 통해 실행한다.

| 검증 항목 | 명령 | 적용 대상 |
| --- | --- | --- |
| 타입 검사 | `pnpm typecheck` | 전 패키지 — 모든 코드 변경에 필수 |
| 단위·컴포넌트 테스트 | `pnpm test` | 테스트가 있는 패키지 전체(재귀) |
| 특정 패키지 테스트 | `pnpm --filter <패키지명> test` | 변경 범위가 좁을 때 빠른 회차용 |
| 허용 의존 방향 검사 | `pnpm dep:check` | `apps/`·`packages/` 경계를 건드리는 변경 |
| 계약(목 서버) 스모크 | `pnpm mock:smoke` | 계약·목 서버·API 클라이언트 변경 |
| 빌드 가능 결과물 | `pnpm --filter @omf-mes/web build` | 관리웹 코드 변경 |
| 생성물 경계 검사 | `pnpm check:generated` | 자동 생성물(`packages/api-client/src/generated/`) 경계에 닿는 변경 |
| 계약 타입 동기화 확인 | `pnpm gen:api` 후 `git diff --stat` | 계약 정본이 갱신됐을 가능성이 있을 때 |

**아직 없는 수단**: 코드 규칙 검사(ESLint)·포맷 검사 스크립트·시각적 회귀·접근성 자동 검사. 포맷 도구는 `prettier`가 설치돼 있으나 검사 스크립트가 없다. 이 항목이 필요한 작업에서는 정책 §5.3에 따라 **대체 검증 방법을 계획에 정의**한다(예: 렌더링 테스트로 대체, 사용자 육안 확인 담당 지정). 도구가 추가되면 이 표를 먼저 갱신한다.

## 게이트 등급 (v1.1 신설)

게이트(위 표의 명령 묶음) 실행을 회차 성격에 따라 두 등급으로 나눈다. **이 절은 실행 횟수의 규정이지 테스트 범위의 완화가 아니다** — 「변경량 제한을 맞추기 위해 필요한 테스트를 생략하거나 축소해서는 안 된다」(정책 §5.6)는 그대로 적용된다.

근거: 전체 테스트 8,386건 · 약 2.6분/회(W-01-06 시점 실측) — 회차마다 전체 게이트를 반복하면 회차당 5~8분이 게이트에만 나간다.

**전체 게이트** — typecheck · 전체 테스트(`pnpm test`) · dep:check · build · mock:smoke · check:generated 중 작업에 해당하는 전부. 다음 세 시점에 고정한다:

1. **구현 초회 커밋 완료 시** (실행 담당)
2. **검증 초회** (검증 담당) — 이때 **전체 테스트는 2회 반복 실행**한다(간헐 실패 탐지용). 반복 실행 요구는 v1.1 신설 조항이며 **검증 초회에만** 있다 — 종전 문서에는 반복 요구가 없었고 실무 관행(검증 보고서상 2~3회)을 상한과 함께 성문화한 것이다.
3. **병합 직전 최종 1회** (오케스트레이터 또는 마지막 재확인 담당)

**빠른 게이트** — 수정 회차 · 감지기 보강 회차 · 재확인에 적용: 슬라이스 테스트(`pnpm --filter <패키지> test` 또는 해당 화면 테스트 파일 지정) + `pnpm typecheck` + 변경 파일 Prettier(`pnpm exec prettier --check <변경 파일>`).

**승격 조건 (v1.2 세분화)**: 승격은 접촉 **위치**가 아니라 변경의 **성격**으로 판단한다 — 그 회차의 수정이 **다른 소비처에 파급될 수 있는 형태**일 때만 전체 게이트로 승격한다:

- **승격한다**: 공개 export·타입 시그니처 변경 · 계약·생성물 변경 · 목 서버 동작 변경 · 라우트 구조 변경 · 공용 컴포넌트의 동작 변경
- **승격하지 않는다**: 공용 패키지 안이라도 **문구 상수의 값 교체 · 주석 · 문서**만 바뀐 경우 — 타입도 시그니처도 안 바뀌어 다른 화면에 파급될 경로가 없다
- **판단이 갈리면 높은 쪽(승격)** — 정책 §6.2 말미와 같은 원칙

근거(v1.2): 문구 상수 1줄 교체가 「공용 패키지 접촉」으로 승격되어 전체 테스트를 실행·검증 양쪽에서 돌렸고 검출한 신규 실패는 0건이었다 — 위치 기준은 무파급 변경과 파급 변경을 구분하지 못한다.

게이트 등급은 **명령 실행의 규정**이며, 검증 담당의 회귀 검증 **범위 판단**(정책 §7.4 — 수정으로 영향받을 수 있는 항목까지, 고친 부분만 보지 않는다)을 대체하지 않는다.

## 간헐 실패 판별 (v1.1 신설)

검증 중 간헐 실패(같은 테스트가 실행마다 다른 결과)를 만나면 **그 자리에서는 다음까지만** 확인한다:

1. HEAD에서 재실행 **2회**
2. 격리 실행 **1회**(해당 슬라이스/파일 단독)

그것으로 「이번 변경과 무관」이 판별되면 — **변경 파일에 그 테스트가 없고 격리에서 통과** — 판정을 「작업 결과 통과, 기존 실패 존재」로 적고, 상세 재현 증거는 **간헐 실패 추적 이슈 #99에 추기**하는 것으로 갈음한다. 기준 커밋 워크트리 반복 실행 같은 심층 조사는 **오케스트레이터가 별건으로 지시할 때만** 수행한다.

판별이 안 되면 — 실패가 변경 파일에 걸쳐 있으면 — 기존대로 그 자리에서 심층 조사한다. **이 갈래는 줄이지 않는다.**

근거: W-01-06 PR ⑤에서 검증 담당이 현장에서 기준 커밋 18회 반복 조사에 약 40분을 썼고, 결론은 「기준에서도 재현되는 기존 실패」였다 — 판별에 필요한 정보는 앞의 세 번 실행으로 이미 얻어진다.

## 기준 상태 기록 (정책 §9-6)

변경 **전에** 관련 검증을 실행해 결과를 기록한다. 이 기록이 없으면 기존 실패와 신규 실패를 구분할 수 없다.

1. **기준 상태의 명령 목록은 계획의 완료 조건(C-*)에서 기계적으로 도출한다**(v1.2) — 완료 조건에 있는 검사는 **전부**(포맷 검사 포함) 기준에 포함한다. 근거: 완료 조건에 있는 검사가 기준에 빠지면, 그 검사가 처음 실행되는 시점에 나온 실패가 기존인지 신규인지 실행·검증 담당이 각자 판별해야 한다 — 착수 전 1회 실행이면 없었을 비용이다
2. 통과/실패와 실패 항목의 이름을 실행 보고서의 「변경 전 기준 상태」 표에 적는다
3. 실행하지 못한 검증이 있으면 그 사실과 이유를 적는다

기준 상태에 없던 실패가 변경 후 나타나면 **신규 실패**다. 기준 상태에 있던 실패는 이번 작업의 완료 판정에서 제외하되, 최종 보고에 남아 있는 사실을 명시한다(정책 §7.4).

### 기존 실패 파일의 신규 결함 (v1.2 신설)

기존 실패의 면제선은 **파일이 아니라 「검사 × 파일」 조합**이다. 어떤 검사가 어떤 파일에서 기준부터 실패 중이면, 그 검사는 그 파일의 **신규 결함에도 침묵한다** — 결함이 있을 때도 고쳐진 뒤에도 같은 실패만 낸다. 따라서:

- 기존 실패 중인 검사가 침묵하는 파일을 **변경하는 회차**는, 그 파일에 대한 **대체 검사**(원문 diff 계수 · 구조 파싱 · 서식본 대조 등 변경 성격에 맞는 것)를 계획 또는 보고서에 명시하고 실행한다
- 대체 검사도 자기 한계가 있다 — 예: 서식본 대조는 표에 행이 늘면 기존 행의 재서식과 섞여 무용지물이다. **어떤 대체 검사를 왜 골랐는지** 한 줄 적는다

근거(v1.2): 문서의 표 구조가 깨진 신규 결함을, 그 파일이 기준부터 포맷 검사에 실패 중이라 어떤 게이트도 잡지 못했다 — 구조 파싱이 잡았다.

## 테스트 우선 개발 적용 (정책 §8.2)

**테스트를 먼저 작성하는 변경**: 비즈니스 규칙 · 상태 전이 · 데이터 변환 · 오류 처리 · 사용자 상호작용 · 과거 오류의 재발 방지.

이 저장소의 해당 예: 폼 검증 규칙(조건부 필수·짝 제약), API 오류 정규화, ETag 보관, 계층 평탄화 로직, 화면의 상태별 렌더링(로딩·빈·오류).

**구현 후 검증으로 대체 가능**: 단순 스타일 조정 · 의미 변화 없는 정적 마크업 · 도구 설정 변경 · 자동 생성 코드(`packages/api-client/src/generated/`). 대체하는 경우에도 검증 방법을 계획에 명시한다.

## 검증 항목 선택

정책 §8.3의 공통 항목 중 이 작업에 해당하는 것만 고른다. 관련이 명백해 보이는데 제외했다면 이유를 계획에 적는다.

UI가 포함된 작업은 §8.4에 따라 추가한다. 이 저장소에서 실행 가능한 것은 **컴포넌트 렌더링·상호작용 테스트**(Testing Library)이며, 접근성·시각적 회귀·반응형은 자동 수단이 없으므로 **사용자 육안 확인**을 담당으로 지정하거나 렌더링 테스트의 접근성 쿼리(`getByRole`·`getByLabelText`)로 부분 대체한다.

비코드 업무(문서·조사·설계)는 §8.5를 적용한다.

## 역할 분리 (정책 §7.1)

- **코드 개발은 위험도와 무관하게** 실행(`development-implementer`)과 최종 검증(`development-verifier`)을 다른 Agent가 담당한다
- 비코드 업무는 중간·높은 위험일 때 분리하고, 낮은 위험이면 실행 Agent의 자체 검증으로 갈음할 수 있다
- 검증 Agent는 실행 Agent의 설명이나 자체 검증 결과를 **검증의 대체물로 쓰지 않는다** — 배정된 검증을 직접 실행한다
- 검증 Agent는 발견한 문제를 직접 고치지 않는다. 재현 방법과 기대 결과를 붙여 실행 Agent에게 반환한다
- 별도 검증 Agent를 쓸 수 없으면 **최종 검증 완료로 처리하지 않고**, 수행/미수행 검증을 구분해 보고한다

**코드 리뷰 업무의 역할 분리** (정책 §7.1 2문단): 리뷰 대상 변경을 **작성한 Agent와 다른 Agent**가 검증 담당을 맡는다. 작성 Agent가 분리돼 있지 않거나 식별할 수 없으면 — 예컨대 하네스 도입 이전에 만들어진 변경이나 사람이 직접 작성한 변경을 리뷰할 때 — 리뷰 Agent는 **그 사실을 검증 보고서에 명시**한다. 식별 불가를 이유로 리뷰를 건너뛰지 않는다.

### 검증·리뷰 병렬과 분담 (v1.1 신설)

- 독립 검증과 독립 리뷰는 구현의 자체 검증이 끝나면 **병렬로 착수**한다. 직렬 예외와 리뷰 단계 정의는 `../SKILL.md` 「9. 독립 검증과 독립 리뷰」가 정본이다.
- **분담은 계획으로 가른다**: 검증 담당 = 계획의 검증 방법 표 배정 항목 · 리뷰 담당 = 전례 대조와 표 밖 영역. 리뷰 담당은 검증 배정 목록을 「재지 않을 자리」로 받고, **검증 보고서를 기다리거나 읽지 않는다**.
- 목 서버 포트: **검증 4023 · 리뷰 4024** — 겹치지 않게 배정한다(v1.1에서 처음 성문화).
- **제품 코드가 바뀐 수정 회차의 재확인은 두 담당 모두 거친 뒤에만 병합**한다.

## 검증 Agent가 존재만 확인하지 않는 방법

파일이 생겼는지·테스트가 있는지만 보면 통과시켜서는 안 된다. 경계면을 교차 확인한다.

- 계약(OpenAPI)의 응답 형태와 화면·클라이언트가 기대하는 형태가 같은가
- 함수 시그니처와 호출부의 인자·반환 사용이 일치하는가
- 완료 조건에 적힌 동작이 **실제로 실행돼 관찰되는가**(테스트 실행 결과·명령 출력)
- 계획 범위 밖 파일이 변경되지 않았는가(`git status`·`git diff --stat`)
- 추가 검증이 배포·외부 전송·비용을 유발하면 **실행 전 사용자 승인**을 받는다(정책 §7.3)

## 뮤테이션 절차 (v1.2 신설)

감지기(테스트)를 **추가**하는 변경은 게이트가 원리적으로 검증하지 못한다 — 추가 전에도 전부 녹색, 추가 후에도 전부 녹색이라, 새 감지기가 실제로 결함을 무는지는 게이트 결과에 나타나지 않는다. 그래서 **일부러 결함(뮤턴트)을 주입해 정확히 그 감지기가 실패하는지 보고 복원**한다. 실행 담당은 새 감지기의 실효 증명에, 검증 담당은 교차 확인과 사각 탐색에 쓴다. 아래 여섯 규칙은 전부 실측 사고(직전)에서 나왔다:

1. **검증 담당의 재주입은 최소(신고 확인 1종 이하), 독자 설계 중심** — 실행 담당의 신고 뮤테이션을 그대로 재주입하는 확인은 여러 회차 연속 100% 일치했고, 신규 발견은 전부 **신고 목록 밖을 겨눈 독자 뮤테이션**에서 나왔다. 자기 재주입은 생각한 자리를 확인하고, 독자 설계는 목록 밖을 찾는다 — 후자에 시간을 쓴다.
2. **회차마다 「총 시험 수」와 「실패한 감지기 이름」을 함께 기록한다** — 서로 다른 함정을 하나씩 잡는 두 열이다. 총 시험 수는 구문이 깨진 무효 뮤턴트를 잡고(시험 수 자체가 줄어 「실패 0건」이 거짓 신호가 된다), 감지기 이름은 엉뚱한 것을 재는 뮤턴트를 잡는다(실패 건수만으로는 의도한 감지기가 문 건지 부수 효과인지 모른다).
3. **뮤턴트가 겨눈 자리에 앉았는지 확인한다** — 같은 문자열이 파일에 여럿일 때 첫 번째 일치를 치환하면 형제 구획이 바뀌어, 엉뚱한 감지기가 울고 「검출 확인」 기록이 거짓이 된다.
4. **서식 확정 뒤에 실행한다** — 포맷 도구 적용 전에 돌리면 보고서에 적은 줄 번호가 서식 후 낡아 증거 추적이 끊긴다.
5. **결과가 예상과 다르면 감지기보다 뮤테이션을 먼저 의심한다** — 하나도 안 걸리면 등가 치환(의미가 같아 걸릴 수 없는 변형)일 수 있고, 예상보다 많이 걸리면 의도보다 큰 파괴(호출을 옮기려다 지움 등)일 수 있다. 어느 쪽이든 「감지기 사각」으로 직행하면 오판이다.
6. **「잴 수 없다」는 신고는 경로 단위로 좁혀야 성립한다** — 정상 경로에서 측정 불가여도 오류 경로에서는 측정 가능할 수 있다. 「어떤 경로에서」 잴 수 없는지까지 적지 않은 미측정 신고는 검증되지 않은 것으로 다룬다.

복원 증명은 필수다 — 주입 파일의 해시 대조(`shasum`)와 `git status` 클린을 보고서에 남긴다. 기록 양식은 `assets/verification-report-template.md`의 뮤테이션 표를 따른다.
