# Agent Coding 기반 소프트웨어 개발 공통 지침

> **배포본 안내** — 이 파일은 개발팀 운영 정책의 **저장소 배포본**이다. 정본은 팀 문서 저장소에 있고, 배포 정보는 `../policy-manifest.yaml`에 기록한다.
> 본문은 정본과 동일하게 유지한다. 이 저장소 고유의 적용 방법(검증 명령·위험도 사례·분할 기준)은 본문을 고치지 않고 `risk-classification.md` · `work-splitting.md` · `verification-policy.md`에 둔다.
> 정본이 갱신되면 이 파일을 교체하고 매니페스트의 버전·배포일·해시를 함께 갱신한다.

## 1. 목적

이 지침은 Agent를 활용하여 소프트웨어 개발 프로젝트를 수행할 때 공통으로 적용할 작업 원칙을 정의한다.

- Agent가 명확한 경계 안에서 스스로 작업을 완료할 수 있도록 한다.
- 작업의 크기와 위험을 제한하여 오류 발생 가능성과 변경 영향을 줄인다.
- 사용자가 계획과 결과를 빠르고 객관적으로 검토할 수 있도록 한다.
- 실행과 검증을 분리하여 구현자의 판단에만 의존하지 않는 품질 체계를 만든다.
- 소프트웨어의 기술 영역과 관계없이 기능 단위의 독립성과 테스트 가능성을 유지한다.

## 2. 적용 범위

이 지침은 다음 업무에 적용한다.

- 신규 소프트웨어 및 기능 개발
- 기존 기능 변경 및 오류 수정
- 백엔드, 프론트엔드, 데스크톱, 모바일, 라이브러리, 개발 도구와 자동화 코드 변경
- 공통 모듈, 컴포넌트와 애플리케이션 공통 구조 변경
- 리팩터링과 기술 부채 개선
- 개발 관련 문서 작성
- 테스트, 검증 및 코드 리뷰

규칙은 다음 우선순위로 적용한다.

1. 사용자가 승인한 요구사항과 안전·권한 경계
2. 저장소에 정의된 구체적인 개발 규칙, 코드 스타일과 검증 절차
3. 이 공통 지침

일반적인 규칙 차이는 더 구체적인 저장소 규칙을 적용한다. 저장소 규칙이 사용자 요구사항, 안전·권한 경계 또는 명시적으로 합의한 하위 호환성 조건과 충돌하거나 어떤 규칙이 더 구체적인지 불분명하면 Agent는 임의로 선택하지 않고 사용자에게 보고한다.

## 3. 용어 정의

| 용어 | 정의 |
| ---- | ---- |
| Agent Coding | 인공지능 Agent가 계획, 구현, 테스트 또는 검증 과정에 참여하는 개발 방식 |
| 작업 단위 | 하나의 목적을 가지며 독립적으로 실행하고 완료 여부를 판단할 수 있는 최소 업무 범위 |
| 수직 분할 | 하나의 사용자 또는 시스템 동작을 완성하는 데 필요한 기술 계층과 테스트를 함께 구현하는 분할 방식 |
| 계층적 분할 | 인터페이스, 데이터 접근, 비즈니스 로직, UI처럼 기술 계층을 기준으로 작업을 나누는 방식 |
| 실행 담당 Agent | 승인되었거나 보고된 계획에 따라 코드, 문서 또는 그 밖의 산출물을 만들고 자체 검증을 수행하는 Agent |
| 검증 담당 Agent | 실행 결과를 독립적으로 점검하고 계획에서 자신에게 배정된 검증을 직접 수행하는 별도의 Agent |
| 완료 조건 | 작업을 완료했다고 판단하기 위해 반드시 충족해야 하는 관찰 가능하고 판정 가능한 기준 |
| 기준 상태 | 변경 전 관련 검증을 실행하여 기록한 정상 결과와 기존 실패 상태 |
| 기능 플래그 | 미완성 기능이 사용자, 외부 호출자 또는 운영 환경에 노출되지 않도록 활성화를 제어하는 장치 |

## 4. 기본 원칙

### 4.1. 검토 가능한 자율성

Agent는 승인되었거나 보고된 목적, 범위와 완료 조건 안에서 자율적으로 판단하고 실행한다. 범위를 벗어나거나 결과에 중대한 영향을 주는 판단이 필요하면 작업을 중단하고 사용자에게 보고한다.

### 4.2. 기존 규칙 우선

Agent는 작업 전에 저장소의 지침, 기존 구현 방식, 코드 스타일, 테스트 도구와 디렉터리 구조를 확인한다. 특별한 이유가 없다면 기존 패턴을 따른다.

### 4.3. 관련 없는 변경 금지

현재 목적 달성에 필요하지 않은 리팩터링, 이름 변경, 포맷 변경 또는 기능 개선을 같은 작업에 포함하지 않는다. 별도 개선이 필요하면 새로운 작업으로 제안한다.

### 4.4. 근거 기반 완료 판정

Agent는 산출물이 작성되었다는 사실만으로 완료를 선언하지 않는다. 계획된 검증을 실제로 수행하고 그 결과를 확인한 후에만 완료를 보고한다.

### 4.5. 작업 환경과 외부 상태 보호

Agent는 작업 대상뿐 아니라 사용자의 기존 작업과 외부 시스템 상태를 보호한다.

- 기존의 커밋되지 않은 변경을 임의로 덮어쓰거나 삭제하지 않는다.
- 현재 작업과 관련 없는 파일의 변경을 되돌리거나 정리하지 않는다.
- 파괴적 작업을 수행하기 전에 대상, 영향 범위와 복구 가능성을 확인한다.
- 비밀정보와 개인정보를 코드, 로그, 테스트 결과 또는 보고서에 노출하지 않는다.
- 배포, 외부 메시지 전송, 운영 데이터 변경, 유료 서비스 사용은 명시적인 권한 없이 수행하지 않는다.
- 기존 변경과 안전하게 분리할 수 없으면 작업을 중단하고 사용자에게 보고한다.

## 5. 규칙 1: 독립적으로 완료 가능한 작업 분할

작업량이 너무 크면 Agent가 전체 맥락을 안정적으로 유지하기 어렵고, 오류 가능성과 검토 비용이 증가한다. 모든 업무 계획은 사용자가 검토할 수 있고 Agent가 독립적으로 완료할 수 있는 작업 단위로 나눈다.

분할 원칙이 충돌하면 다음 우선순위를 적용한다.

### 5.1. 우선순위 1: 단일 목적

하나의 작업 단위는 하나의 목적만 가져야 한다.

- 기능 구현과 관련 없는 리팩터링을 섞지 않는다.
- 오류 수정과 새로운 기능 추가를 섞지 않는다.
- 서로 독립적인 여러 사용자 또는 시스템 기능을 하나의 작업으로 묶지 않는다.
- 작업 목적을 한 문장으로 설명할 수 있어야 한다.

단, 현재 목적을 안전하게 달성하기 위한 국소적 구조 개선은 허용할 수 있다. 이 경우 개선의 필요성과 범위를 계획에 명시한다.

### 5.2. 우선순위 2: 하위 호환성과 위험 격리

변경으로 인한 영향이 다른 기능으로 확산되지 않도록 작업 경계를 정한다.

- 기존 공개 인터페이스와 사용자 동작을 기본적으로 유지한다.
- 호환성을 깨는 변경은 별도 작업으로 분리한다.
- 미완성 기능은 기능 플래그, 개발 전용 경로 또는 접근 불가능한 경계로 격리한다.
- 인증, 권한, 개인정보, 결제, 데이터 구조 변경은 일반 기능 변경과 분리한다.
- 실패 시 되돌릴 수 있는 범위로 변경을 제한한다.

### 5.3. 우선순위 3: 독립적인 완료와 검증 가능성

각 작업 단위는 전체 기능의 일부일 수 있지만 저장소에 반영되는 시점에는 다음 조건을 충족해야 한다.

- 저장소에 정의된 빌드, 정적 분석, 타입 검사, 코드 규칙 검사와 테스트 중 해당하는 검증을 통과한다.
- 특정 검증 수단이 존재하지 않으면 작업 성격에 맞는 대체 검증 방법을 계획에 정의한다.
- 기존에 정상 동작하던 기능을 손상시키지 않는다.
- 해당 작업의 완료 조건을 독립적으로 검증할 수 있다.
- 필요한 테스트와 검증 수단이 함께 제공된다.
- 미완성 부분이 사용자, 외부 호출자 또는 운영 환경에 노출되지 않는다.

테스트할 수 있다는 이유만으로 깨진 중간 상태나 사용할 수 없는 코드를 병합해서는 안 된다.

### 5.4. 우선순위 4: 사용자 또는 시스템 동작 기준의 수직 분할

기능 개발은 가능한 한 사용자 또는 외부 시스템에서 관찰할 수 있는 하나의 동작을 기준으로 수직 분할한다. UI가 있는 기능은 사용자 행동을 기준으로 하고, UI가 없는 서비스·라이브러리·자동화 기능은 외부 호출자나 시스템이 사용하는 동작을 기준으로 한다.

예를 들어 프로젝트 관리 기능은 다음처럼 나눈다.

1. 프로젝트 목록 조회와 로딩·빈 상태·오류 표시
2. 프로젝트 선택과 상세 정보 표시
3. 프로젝트 생성과 입력값 검증
4. 프로젝트 수정과 저장 실패 처리
5. 프로젝트 삭제와 권한 및 확인 절차

각 작업은 해당 행동을 완성하는 데 필요한 인터페이스, 도메인 로직, 데이터 처리, 오류 처리, UI와 테스트 중 관련된 계층을 함께 포함한다. 해당 기능에 존재하지 않는 계층을 억지로 추가하지 않는다.

UI가 없는 작업은 다음처럼 나눌 수 있다.

1. 입력 파일 한 건을 읽고 유효성을 검사한다.
2. 유효한 데이터를 변환하여 저장한다.
3. 잘못된 입력을 분류하고 오류 결과를 반환한다.
4. 실패한 작업을 재시도하고 처리 결과를 기록한다.

다음과 같이 전체 기능을 기술 계층별로 길게 나누는 것은 원칙적으로 피한다.

1. 모든 API 인터페이스 구현
2. 모든 비즈니스 로직 구현
3. 모든 상태 관리 구현
4. 모든 UI 구현

이 방식은 통합 검증과 사용자 피드백이 늦어지고 미완성 계층이 장기간 누적될 위험이 있다.

### 5.5. 우선순위 5: 필요한 경우의 계층적 분할

다음 상황에서는 제한적으로 계층적 분할을 사용할 수 있다.

- 여러 기능이 사용해야 하는 안정된 계약이나 공통 기반을 먼저 정의해야 하는 경우
- 외부 API 또는 데이터 구조가 선행 조건인 경우
- 애플리케이션 공통 셸, 화면 전환 구조 또는 공통 레이아웃을 구성하는 경우
- 기술적 위험을 먼저 검증하는 짧은 실험이 필요한 경우

계층적 작업도 자체적으로 빌드와 검증이 가능해야 하며, 후속 작업과의 인터페이스를 명확히 정의해야 한다. 계층적 분할을 선택한 이유와 수직 분할로 전환할 조건을 계획에 기록한다.

### 5.6. 우선순위 6: 물리적 변경량 제한

변경량은 검토 가능성을 판단하는 보조 지표이며 절대적인 품질 기준이 아니다.

- 하나의 작업은 생성 코드, 잠금 파일과 자동 생성 스냅샷을 제외한 변경 코드 및 테스트가 약 400줄 이하가 되도록 분할한다.
- 400줄은 권장 상한이며 다른 상위 원칙을 훼손하면서 맞추지 않는다.
- 변경량이 500줄을 초과하면 작업을 다시 분할할 이점이 있는지 반드시 검토한다.
- 500줄을 초과한 상태로 진행하려면 분할하지 않은 이유를 계획 또는 실행 보고에 기록한다.
- 줄 수보다 변경된 책임의 수, 파일 간 결합도, 위험과 검토 난이도를 우선 판단한다.
- 변경량 제한을 맞추기 위해 필요한 테스트를 생략하거나 축소해서는 안 된다. 테스트 증가로 기준을 초과하면 테스트 범위를 유지하고 작업 분할의 이점을 별도로 판단한다.

## 6. 규칙 2: 명확한 계획 보고와 승인

### 6.1. 계획 보고의 목적

Agent는 실행 전에 사용자가 작업의 목적, 범위, 위험, 기대 결과와 완료 판단 방법을 이해할 수 있도록 계획을 보고한다.

계획에는 다음 항목을 포함한다.

1. **주제**: 개발, 오류 수정, 리팩터링, 문서화 등 어떤 작업인지 작성한다.
2. **목적**: 이 작업을 수행하는 이유와 해결하려는 문제를 작성한다.
3. **위험도와 승인 필요 여부**: 위험도를 분류하고 실행 전 승인이 필요한지 작성한다.
4. **범위와 제외 범위**: 변경할 대상과 의도적으로 변경하지 않을 대상을 구분한다.
5. **상세 내용**: 수행할 작업과 작업 분할, 실행 순서를 작성한다.
6. **선행 조건과 의존성**: 필요한 기존 기능, 외부 시스템, 라이브러리 또는 결정 사항을 작성한다.
7. **영향 범위와 호환성**: 영향을 받는 기존 기능과 공개 인터페이스를 작성한다.
8. **위험과 복구 방법**: 예상 위험과 실패 시 되돌리거나 격리하는 방법을 작성한다.
9. **기대 결과**: 완료 후 사용자 또는 시스템에서 관찰할 수 있는 변화를 작성한다.
10. **완료 조건**: 완료 여부를 예 또는 아니요로 판정할 수 있는 기준을 작성한다.
11. **검증 방법**: 완료 조건을 확인할 구체적인 절차, 담당 역할, 테스트와 객관적인 평가 기준을 작성한다.

중간 및 높은 위험 작업은 모든 항목을 작성한다. 낮은 위험 작업은 `6.2. 위험도에 따른 승인`에서 정한 간략 계획 항목을 사용할 수 있다.

검증 방법의 기본 담당은 검증 담당 Agent이다. 실행 담당 Agent는 로컬에서 안전하고 빠르게 수행할 수 있는 검증을 자체 검증으로 중복 수행한다. 사용자가 직접 판단해야 하는 정성적 승인이나 권한이 필요한 확인은 담당을 사용자로 명시한다.

### 6.2. 위험도에 따른 승인

계획 승인 절차는 작업 위험도에 따라 적용한다.

#### 낮은 위험

다음 조건을 모두 만족하는 작업이다.

- 변경 범위가 작고 국소적이다.
- 공개 인터페이스와 사용자·시스템 흐름을 변경하지 않는다.
- 데이터 복구, 운영 중단 또는 외부 협업 없이 변경 전 상태로 되돌릴 수 있다.
- 보안, 권한, 개인정보 또는 데이터 구조에 영향을 주지 않는다.

Agent는 다음 항목을 포함한 간략한 계획을 보고한 후 별도 승인 대기 없이 실행할 수 있다.

- 목적
- 변경 범위
- 기대 결과
- 검증 방법

#### 중간 위험

낮은 위험 조건을 모두 충족하지 않고 높은 위험 조건에도 해당하지 않는 작업은 중간 위험으로 분류한다. 여러 컴포넌트 또는 하나의 사용자·시스템 흐름에 영향을 주지만 영향 범위가 명확한 작업이 여기에 포함된다. Agent는 상세 계획을 보고하고 사용자 승인을 받은 후 실행한다.

#### 높은 위험

다음 중 하나에 해당하는 작업이다.

- 공개 인터페이스 변경
- 신규 외부 라이브러리 도입
- 기존 의존성의 주요 버전 변경
- 광범위한 공통 컴포넌트 변경
- 인증, 권한, 개인정보 또는 결제 관련 변경
- 데이터 구조나 API 계약 변경
- 빌드·배포 파이프라인 또는 운영 환경 설정 변경
- 외부 시스템의 데이터 변경, 메시지 전송 또는 비용 발생 작업
- 대규모 삭제 또는 마이그레이션
- 여러 핵심 사용자 흐름에 동시에 영향을 주는 변경

Agent는 대안, 영향, 위험과 복구 방법을 포함한 계획을 보고하고 사용자의 명시적 승인을 받은 후 실행한다.

사용자가 모든 작업에 대한 사전 승인을 별도로 요구한 경우에는 위험도와 관계없이 승인을 기다린다.

위험도를 명확히 판단할 수 없으면 더 높은 위험도를 적용한다.

### 6.3. 용어와 표현

- 약어, 은어와 프로젝트 내부 용어는 가능한 한 사용하지 않는다.
- 사용해야 하는 경우 최초 등장 시 전체 표현과 의미를 함께 작성한다.
- 전문 용어가 반복되거나 여러 개 등장하면 문서 상단에 용어 정의를 둔다.
- 다른 문서를 참조할 때는 단순 키워드만 적지 않고 문서명, 위치와 참조 이유를 작성한다.
- 완료 여부를 판정할 수 없는 `적절히`, `가능하면`, `문제없이` 같은 표현은 구체적인 조건으로 바꾼다.

### 6.4. 계획 변경

실행 중 다음 상황이 발생하면 Agent는 계획을 임의로 확장하지 않는다.

- 계획에 없는 공개 인터페이스 변경이 필요하다.
- 예상하지 못한 외부 의존성이 필요하다.
- 완료 조건 또는 검증 방법을 변경해야 한다.
- 관련 없는 대규모 리팩터링이 필요하다.
- 작업량이나 영향 범위가 계획보다 크게 증가한다.

Agent는 현재 상태, 변경이 필요한 이유, 대안과 영향을 보고하고 필요한 승인을 받은 후 계속한다.

## 7. 규칙 3: 분리된 실행과 독립 검증

### 7.1. 역할 분리

코드 개발 업무의 실행과 최종 검증은 위험도와 관계없이 서로 다른 Agent가 담당한다. 문서화, 조사와 설계 등 비코드 업무는 중간 또는 높은 위험일 때 실행과 검증을 서로 다른 Agent가 담당하고, 낮은 위험일 때는 실행 담당 Agent가 자체 검증할 수 있다.

코드 리뷰 업무에서는 대상 변경을 작성한 Agent와 다른 Agent가 검증 담당 역할을 수행한다. 대상 변경을 작성한 Agent가 분리되어 있지 않거나 식별할 수 없으면 리뷰 Agent는 그 사실을 보고서에 명시한다.

- 실행 담당 Agent는 계획의 목적과 내용을 충족하는 산출물과 필요한 테스트 또는 검증 수단을 작성한다.
- 검증 담당 Agent는 원래 계획과 요구사항을 기준으로 결과를 독립적으로 평가한다.
- 검증 담당 Agent는 실행 담당 Agent의 설명이나 자체 검증 결과를 검증의 대체물로 사용하지 않는다.

독립 검증이 필요한 작업에서 별도의 검증 담당 Agent를 사용할 수 없으면 최종 검증 완료로 처리하지 않는다. 수행한 자체 검증과 미수행 검증을 구분하여 사용자에게 보고한다.

### 7.2. 실행 담당 Agent의 책임

실행 담당 Agent는 다음 업무를 수행한다.

1. 승인되었거나 보고된 계획과 기존 저장소 규칙을 확인한다.
2. 계획의 작업 단위를 더 세부적으로 실행할 순서를 정한다.
3. 코드 개발 업무는 `8.2. 테스트 우선 개발 적용`에 따라 필요한 테스트와 구현을 작성한다.
4. 계획의 목적과 범위를 벗어나지 않는지 변경 내용을 점검한다.
5. 로컬에서 안전하고 빠르게 수행할 수 있는 검증을 직접 실행한다.
6. 변경 파일, 주요 판단, 자체 검증 결과와 남은 위험을 실행 보고서에 기록한다.

### 7.3. 검증 담당 Agent의 책임

검증 담당 Agent는 다음 업무를 수행한다.

1. 원래 계획, 요구사항, 완료 조건과 검증 방법을 직접 읽는다.
2. 실제 변경 내용을 확인하고 계획 범위와 비교한다.
3. 실행 담당의 결과와 관계없이 계획에서 검증 담당 Agent에게 배정된 모든 검증을 직접 수행한다.
4. 변경 전 기준 상태를 근거로 기존에 존재하던 실패와 이번 변경으로 발생한 실패를 구분한다.
5. 완료 조건별로 통과, 실패 또는 검증 불가를 판정한다.
6. 누락된 테스트, 회귀 위험과 범위 밖 변경을 확인한다.
7. 발견한 위험과 직접 관련된 비파괴적 검증을 추가로 수행할 수 있다.
8. 실행 명령과 결과를 포함한 검증 보고서를 작성한다.

검증 담당 Agent는 원칙적으로 발견한 문제를 직접 수정하지 않는다. 수정이 필요하면 실행 담당 Agent에게 구체적인 재현 방법, 기대 결과와 함께 반환한다.

추가 검증에 배포, 외부 메시지 전송, 외부 데이터 변경, 비용 발생 또는 운영 환경 변경이 필요하면 검증 담당 Agent도 실행 전에 사용자 승인을 받아야 한다.

### 7.4. 수정 및 재검증 반복

검증에서 문제가 발견되면 다음 절차를 반복한다.

1. 검증 담당 Agent가 실패 내용과 재현 방법을 보고한다.
2. 실행 담당 Agent가 원인을 분석하고 수정한다.
3. 실행 담당 Agent가 자체 검증을 다시 수행한다.
4. 검증 담당 Agent가 실패했던 항목과 영향을 받을 수 있는 회귀 검증을 다시 수행한다.
5. 계획된 모든 완료 조건을 충족할 때까지 반복한다.

이번 변경으로 검증 항목이 실패했거나 계획된 검증이 수행되지 않았다면 완료로 선언하지 않는다. 검증할 수 없는 항목이 있다면 그 이유와 위험을 사용자에게 보고하고 판단을 요청한다.

변경 전부터 존재했고 이번 작업과 무관하다는 근거가 있는 실패는 신규 실패로 판정하지 않는다. 해당 작업의 완료 조건과 영향 범위에 대한 검증이 모두 통과하면 `작업 결과 통과, 기존 실패 존재`로 판정할 수 있지만 전체 검증이 통과했다고 보고해서는 안 된다.

## 8. 테스트 우선 개발과 검증 기준

### 8.1. 테스트 계획의 의미

계획에 명시된 테스트와 검증 방법은 최소 기준이다.

- 실행 담당 Agent는 계획된 테스트를 삭제하거나 완화할 수 없다.
- 구현 중 발견한 위험을 검증하기 위한 테스트는 추가할 수 있다.
- 테스트 전략을 크게 변경하거나 계획된 테스트가 부적절하다고 판단한 경우 계획 변경을 보고한다.
- 테스트가 실패한다는 이유로 정당한 근거 없이 테스트를 삭제하거나 기대값을 완화해서는 안 된다.

### 8.2. 테스트 우선 개발 적용

코드 개발 업무 중 다음 변경에는 원칙적으로 실패하는 테스트를 먼저 작성한 후 구현한다.

- 비즈니스 규칙
- 상태 전이
- 데이터 변환
- 오류 처리
- 사용자 상호작용
- 과거에 발생한 오류의 재발 방지

다음 작업은 테스트 우선 구현이 실익이 낮을 수 있으므로 구현 후 적절한 정적 검사 또는 시각적 검증으로 대체할 수 있다.

- 단순 스타일 조정
- 의미 변화가 없는 정적 마크업
- 도구 설정 변경
- 자동 생성 코드

예외를 적용할 때도 검증을 생략하는 것은 아니다. 작업 성격에 맞는 검증 방법을 계획에 명시한다.

### 8.3. 소프트웨어 공통 검증 항목

작업 위험, 변경 내용과 저장소에서 지원하는 검증 수단에 따라 다음 항목 중 필요한 검증을 계획에 포함한다.

- 타입 검사
- 코드 규칙 검사와 포맷 검사
- 단위 테스트
- 모듈, 서비스 또는 계층 간 통합 테스트
- 외부 인터페이스와 데이터 계약 테스트
- 핵심 사용자 또는 시스템 흐름의 전체 구간 테스트
- 데이터 구조 변경과 마이그레이션 검사
- 오류 처리, 재시도와 복구 동작 검사
- 보안, 권한과 개인정보 처리 검사
- 성능 기준 검사
- 빌드 및 배포 가능한 결과물 생성 검사

모든 작업에 모든 검증을 적용하지 않는다. 제외한 검증이 명백히 관련되어 보이는 경우 제외 이유를 계획에 작성한다.

### 8.4. UI가 포함된 작업의 추가 검증 항목

UI가 포함된 작업은 변경 내용에 따라 다음 검증을 추가한다.

- 컴포넌트 렌더링 및 사용자 상호작용 테스트
- 핵심 사용자 흐름을 확인하는 UI 자동화 테스트
- 키보드 조작, 의미 구조와 명도 대비 등 접근성 검사
- 목표 화면 크기와 실행 환경의 반응형 또는 크기 변화 검사
- 시각적 회귀 검사

### 8.5. 비코드 업무의 검증 항목

비코드 업무는 산출물의 성격에 따라 다음 검증을 적용한다.

- 문서화: 사실성, 요구사항 누락, 내부 일관성, 링크와 예시의 유효성, 형식 검사
- 조사: 출처의 신뢰성, 정보의 최신성, 사실과 추론의 구분, 결론을 뒷받침하는 근거 검사
- 설계: 요구사항과의 일치, 가정과 제약, 대안과 장단점, 실패 처리와 검증 가능성 검사
- 코드 리뷰: 원래 요구사항, 실제 변경 내용, 테스트 증거, 회귀·보안·호환성 위험 검사

## 9. 표준 작업 흐름

업무는 다음 순서로 진행한다.

1. 저장소 규칙, 현재 구조와 기존 작업 상태 확인
2. 요구사항, 목적과 완료 조건 확인
3. 위험도 분류
4. 독립적으로 완료 가능한 작업 단위로 분할
5. 계획 보고 및 필요한 승인 획득

## 13. 완료 정의

다음 조건 중 해당 업무에 적용되는 항목을 모두 충족해야 작업을 완료로 처리한다.

- 계획된 범위의 산출물이 완료되었다.
- 계획 밖의 변경이 없거나 승인된 변경만 존재한다.
- 코드 개발 업무에 필요한 테스트가 작성되었다.
- 실행 담당 Agent의 자체 검증이 완료되었다.
- 계획된 검증을 각 담당 역할이 수행했으며, 독립 검증이 필요한 업무는 검증 담당 Agent가 자신에게 배정된 모든 검증을 수행했다.
- 모든 완료 조건이 통과했다.
- 기존 실패, 제한 사항과 남은 위험이 문서화되었다.
- 기준 상태로 확인한 기존 실패 외에 이번 작업으로 발생한 신규 실패가 없다.
- 미완성 기능이 사용자, 외부 호출자 또는 운영 환경에 노출되지 않는다.
- 사용자에게 변경 결과와 검증 증거가 보고되었다.

## 14. 작업 중단 및 사용자 보고 조건

Agent는 다음 상황에서 작업을 중단하고 사용자에게 판단을 요청한다.

- 요구사항을 둘 이상의 의미로 해석할 수 있고 결과 차이가 크다.
- 계획에 없던 공개 인터페이스 변경이 필요하다.
- 새로운 외부 의존성 또는 유료 서비스가 필요하다.
- 기존 의존성의 주요 버전을 변경해야 한다.
- 보안, 권한, 개인정보 또는 결제 위험을 발견했다.
- 기존 기능을 제거하거나 하위 호환성을 깨야 한다.
- 배포, 외부 메시지 전송, 외부 데이터 또는 운영 환경 변경이 필요하지만 권한이 없다.
- 기존의 커밋되지 않은 변경과 현재 작업을 안전하게 분리할 수 없다.
- 계획 범위를 크게 넘는 리팩터링이 필요하다.
- 작업량이나 영향 범위가 계획보다 현저히 증가했다.
- 계획된 검증을 수행할 수 없다.
- 기존 저장소 규칙과 이 지침이 충돌한다.

보고할 때는 현재 상태, 중단 이유, 가능한 대안, 각 대안의 영향과 권장안을 함께 제시한다.
