**코드 스타일·네이밍·오류 처리·언어별 규칙은 `crefle-agent-skills:coding-rules` 스킬이 정본이다.** 실행 담당 Agent가 호출한다. 이 하네스는 그 내용을 복제하지 않는다.

## 언제 이 스킬을 쓰는가

**사용한다**: 기능 추가·변경, 버그 수정, 리팩터링, 테스트 작성·수정, **아직 커밋하지 않은 작업 변경분의 리뷰**, 설계·개발 문서 작성, 그리고 위 작업들의 **후속 수정·보완·재검증**.

**사용하지 않는다**: 코드 변경이 없는 개념 설명("dependency-cruiser가 뭐야?"), 읽기 전용 조회("이 파일 어디 있어?", "엔드포인트 몇 개야?"), 실행 방법 안내("목 서버 어떻게 띄워?"), 기술 선택 이유 설명, 저장소 상태 확인("지금 브랜치 뭐야?"). 이런 요청은 직접 답한다. 답하는 도중 코드를 고쳐야 할 일이 생기면 그때 이 스킬로 전환한다.

**다른 스킬이 맡는 것**: 번호·URL로 지정된 **GitHub PR 리뷰**는 `crefle-agent-skills:pr-review`, 코딩 컨벤션·네이밍·커밋 메시지 **규칙 질의**는 `crefle-agent-skills:coding-rules`.

## 다른 스킬과의 관계

| 스킬 | 관계 |
| --- | --- |
| `crefle-agent-skills:coding-rules` | **참조** — 코드 작성 규칙의 정본. 실행 담당이 호출 |
| `superpowers:brainstorming` | **선행 가능** — 요구사항 자체가 불명확하면 먼저 설계를 합의한 뒤 이 스킬로 들어온다. 요구사항이 이미 명확하면 바로 이 스킬 |
| `superpowers:writing-plans`·`executing-plans`·`subagent-driven-development` | **대체** — 계획·실행 절차는 이 하네스와 정책 §10 양식을 쓴다. 중복 호출하지 않는다 |
| `superpowers:test-driven-development`·`verification-before-completion` | **흡수** — 정책 §8.2·§13이 같은 취지를 담고 있다 |
| `crefle-agent-skills:pr-review`·`code-review`·`pr-review-toolkit:*` | **공존** — 사용자가 번호·URL로 지정한 GitHub PR 리뷰는 그쪽이 맡는다. 아직 커밋하지 않은 작업 변경분의 독립 검증·독립 리뷰는 이 하네스가 맡되, 하네스 내부의 **독립 리뷰 단계(9절)는 `crefle-agent-skills:pr-review`를 기준 스킬로 삼는다**(v1.1) |
| `superpowers:systematic-debugging` | **흡수** — 버그 수정도 이 하네스의 흐름(위험도 → 계획 → 실행 → 독립 검증)으로 처리한다. 원인 규명 기법을 참고할 수는 있으나 **스킬을 호출하지는 않는다** |

## 실행 모드 — 서브 에이전트 파이프라인

이 환경에는 Agent Team 도구(`TeamCreate`)가 **없다**(2026-08-05 확인). 따라서 팀 대신 `Agent` 도구로 서브 에이전트를 순차 호출하는 파이프라인으로 동작한다. 정책이 요구하는 「실행 담당에게 반환 → 재검증」 루프는 `SendMessage`로 **기존 에이전트를 컨텍스트를 유지한 채 재개**해 구현한다.

- 모든 Agent 호출에 `model: "opus"`와 `subagent_type`을 명시한다
- 검증 담당과 리뷰 담당은 **한 메시지에서 동시에 호출**해 병렬로 돌린다(v1.1 — 「9. 독립 검증과 독립 리뷰」의 분담·예외 규정을 따른다)
- 오케스트레이터는 각 Agent의 **호출·반환 시각을 기록**한다(v1.1) — 이슈 종료 정리보고(`assets/closing-report-template.md`)의 프로파일링 근거다
- 진행 상황은 `TaskCreate`/`TaskUpdate`로 추적한다(작업 단위가 2개 이상일 때). ⚠ 이 도구는 **오케스트레이터가 도는 메인 세션에서만** 보인다 — 서브 에이전트에게 작업 목록 갱신을 지시하지 않는다
- 산출물은 `.claude/_workspace/<작업슬러그>/`에 남긴다 — 재실행·감사 추적용이며 `.gitignore`에 포함돼 있다
- ⚠ `.claude/agents/`의 정의는 **즉시 반영되지 않을 수 있다.** 호출 전에 사용 가능한 Agent 목록에 해당 `subagent_type`이 있는지 확인하고, **있으면 그대로 호출한다.** 없을 때만 `general-purpose`로 호출하고 프롬프트 첫머리에 정의 파일을 읽어 역할을 채택하라고 지시하되, **이 우회에는 정의의 `tools` 제한이 적용되지 않는다**(예: 검증 담당의 `Edit` 부재가 강제되지 않아 「직접 수정 금지」가 프롬프트 지시로만 남는다). 우회를 썼다면 그 사실을 최종 보고에 적는다

```
Agent(subagent_type: "development-planner",     model: "opus")   # 중간·높은 위험만
Agent(subagent_type: "development-implementer", model: "opus")
Agent(subagent_type: "development-verifier",    model: "opus")   # ┐ 한 메시지에서 동시 호출 (v1.1)
Agent(subagent_type: "general-purpose",         model: "opus")   # ┘ 독립 리뷰 — pr-review 스킬 기준
SendMessage(to: "<implementer 이름/ID>", ...)   # 검증·리뷰 지적 통합 반환
SendMessage(to: "<verifier 이름/ID>", ...)      # 재검증 요청 (리뷰 재확인과 병렬)
```

## Phase 0 — 컨텍스트 확인

작업을 시작하기 전에 이번 요청이 어떤 성격인지 판별한다.

1. `.claude/_workspace/` 아래에 관련 작업 슬러그가 있는가
2. 사용자가 **부분 수정·재검증**을 요청했는가 → **부분 재실행**: 해당 Agent만 `SendMessage`로 재개한다
3. 사용자가 **새 요구사항**을 줬는가 → **새 실행**: 새 작업 슬러그로 시작한다
4. 관련 산출물이 없는가 → **초기 실행**: 아래 전체 흐름을 따른다

작업 슬러그는 kebab-case로 짧게 짓는다(예: `w06-07-layout`, `mock-server-state`).

## 실행 흐름 (정책 §9)

### 1. 저장소 규칙과 현재 상태 확인

- 루트 `CLAUDE.md`(공개 저장소 경계·디자인 시스템·설계 정본 위치)와 `docs/decisions.md`를 확인한다
- `git status`로 **커밋되지 않은 변경**을 확인한다. 있으면 이번 작업과 분리 가능한지 판단하고, 분리할 수 없으면 중단해 사용자에게 보고한다
- 현재 브랜치를 확인한다. `main` 직접 push는 차단돼 있으므로 작업 브랜치에서 진행한다

### 2. 요구사항·목적·완료 조건 확인

요구사항이 둘 이상으로 해석되고 결과 차이가 크면 여기서 되묻는다. 추측으로 진행하지 않는다.

### 3. 위험도 분류

`references/risk-classification.md`의 판정 순서를 적용한다. **판단이 갈리면 더 높은 쪽**을 택한다.

### 4. 작업 분할

`references/work-splitting.md`의 우선순위 6단계를 적용한다. 수직 분할이 기본이고, 계층적 분할을 택하면 이유와 수직 전환 조건을 계획에 적는다.

### 5. 계획 보고와 승인

| 위험도 | 계획 | 승인 |
| :-: | --- | --- |
| 낮음 | 오케스트레이터가 `assets/plan-template.md`의 **간략 계획**을 직접 작성 | 보고 후 대기 없이 실행 |
| 중간·높음 | `development-planner`를 호출해 **상세 계획** 작성 | **사용자 승인을 받고 실행** |

`development-planner` 프롬프트에 반드시 포함할 것:

- **작업 슬러그**(`_workspace` 경로 결정용)
- 사용자 요구사항 원문
- 오케스트레이터의 1차 위험도 판단과 그 근거
- 저장소 현재 상태(브랜치·미커밋 변경 유무)
- 관련 선행 작업·산출물 경로(있으면)

**간략 계획의 검증 담당**: 간략 계획에는 담당 열이 있는 표가 없다. 정책 §6.1의 기본값에 따라 **모든 검증 항목의 기본 담당은 검증 Agent**이고, 실행 담당은 로컬에서 빠르게 할 수 있는 것을 중복 수행한다. 낮은 위험이어도 코드 개발이면 검증 담당을 호출하며, 그때 「검증 방법에 적힌 항목 전부가 검증 담당 배정분」임을 프롬프트에 명시한다.

사용자가 모든 작업에 사전 승인을 요구했으면 위험도와 무관하게 승인을 기다린다.

계획을 사용자에게 보고할 때는 전문을 그대로 낸다. 승인 질문은 명확하게 한다(무엇을 승인하는지, 승인하지 않으면 어떤 대안이 있는지).

### 6. 기준 상태 기록

**변경을 시작하기 전에** 관련 검증을 실행해 통과/실패를 기록한다(`references/verification-policy.md`). 이 기록이 없으면 나중에 기존 실패와 신규 실패를 구분할 수 없다. 실행 담당에게 이 단계를 지시하거나, 오케스트레이터가 직접 실행해 전달한다.

### 7~8. 실행과 자체 검증

`development-implementer`를 호출한다. 프롬프트에 반드시 포함할 것:

- 작업 슬러그와 `_workspace` 경로
- 계획 전문 또는 계획 파일 경로
- 기준 상태 기록
- 이번 작업의 범위와 **제외 범위**
- 「코드 작성 전 `crefle-agent-skills:coding-rules` 스킬을 호출하라」
- **전례 사본으로 시작하는 화면이면** 「`references/copy-checklist.md`를 착수 시 대조하고 체크 결과를 실행 보고서에 적으라」(v1.1 — 최근 리뷰 Major 다수가 전례의 인자·감지기를 반쪽만 베낀 형태였다)

### 9. 독립 검증과 독립 리뷰 — 병렬 (v1.1 개정)

구현의 자체 검증이 끝나면 **검증 담당과 리뷰 담당을 한 메시지에서 동시에 착수**한다. 두 담당은 같은 커밋을 보고, 서로의 보고서를 기다리거나 읽지 않는다. 목 서버가 필요하면 포트를 겹치지 않게 배정한다 — **검증 4023 · 리뷰 4024**(v1.1에서 처음 성문화 — 종전에는 워크스페이스 보고서에만 있던 관례).

**병렬 구간의 작업 트리 격리**(v1.2): 검증 담당은 메인 체크아웃에서 뮤턴트를 주입·복원하므로, **리뷰 담당은 격리 워크트리(`git worktree add <경로> <대상 커밋>`)에서만 파일을 읽는다** — 메인 체크아웃은 검증 담당 소유다. 같은 트리를 공유하면 리뷰가 뮤턴트 섞인 소스를 커밋본으로 오독한다(1번 팀 회차에서 충돌 직전 실증 · 2번 팀 회차는 리뷰가 매회 먼저 끝나 우연히 회피). 리뷰 종료 시 워크트리를 제거한다(`git worktree remove`).

**독립 검증** — `development-verifier`를 호출한다. **실행 담당과 반드시 다른 Agent**다. 프롬프트에 포함할 것:

- 계획 파일 경로(먼저 읽게 한다)와 사용자 요구사항 원문
- 실행 보고서 경로
- 계획의 검증 방법 표에서 **검증 담당에게 배정된 항목**(간략 계획이면 「검증 방법」 절 전체가 배정분이다 — `(담당: 사용자)` 표기가 붙은 것만 제외)
- 기준 상태 기록

**독립 리뷰**(v1.1 성문화 — 실무에서 화면마다 수행해 온 단계를 문서에 올린 것) — **구현·검증과 다른 Agent**를 `general-purpose`로 호출하고, 프롬프트 첫머리에 `crefle-agent-skills:pr-review` 스킬을 기준으로 삼게 한다(심각도 4단계 · 승인 기준 Blocker+Major 0). 소스 미수정 · PR 코멘트 미게시 · 미머지 · 미푸시. 산출물은 `05_review.md`(슬라이스·회차 규약은 「산출물 배치」)이며, **리뷰 보고서에도 시작·종료 시각을 회차마다 적는다** — 이슈 종료 정리보고의 프로파일링 근거다.

**분담은 보고서가 아니라 계획으로 가른다 — 생략 불가.** 검증 담당은 계획의 검증 방법 표 배정 항목을, 리뷰 담당은 **전례 대조와 표 밖 영역**(주석·문구 정합, 컨벤션, 계획에 없는 뮤테이션 지점, PR 본문·공개 경계)을 맡는다. 리뷰 프롬프트에 검증 배정 항목 목록을 **「재지 않을 자리」로 전달**한다. 이유: 직렬 시절의 겹침 회피(리뷰가 검증 보고서를 읽고 이미 잰 자리를 피함)는 병렬에서 불가능하다 — 분담 없이 병렬화하면 같은 자리를 중복 측정해 절감이 상쇄된다.

**직렬 예외**: 검증이 제품 결함으로 「수정 후 재검증 필요」를 반환할 확률이 높다고 볼 근거가 있으면(예: 큰 쓰기 슬라이스의 위험 신호), 오케스트레이터 판단으로 기존 직렬(검증 → 통과 후 리뷰)을 택할 수 있다 — 리뷰가 곧 무효가 될 코드를 읽는 낭비를 막는다. **근거가 없으면 병렬이 기본이다.**

기대 효과(v1.1 근거 — W-01-06 프로파일 기준): 분담 규칙이 지켜질 때 **PR당 약 15~20분 · 화면당 약 80분** 단축. 후속 재프로파일링(상단 개정 이력)의 비교 기준이다.

UI 화면 작업의 브라우저 확인은 기존 품질 절차대로 수행하고 산출물은 `04_browser-check.md`에 남긴다.

코드 개발 업무는 위험도와 무관하게 독립 검증을 생략하지 않는다. 비코드 업무(문서·조사·설계)는 낮은 위험이면 실행 담당의 자체 검증으로 갈음할 수 있다(정책 §7.1).

### 10. 수정과 재검증 반복 (v1.1 개정)

검증·리뷰에서 문제가 나오면:

1. **두 보고가 모이면 오케스트레이터가 지적을 합쳐 한 번의 수정 회차로 만든다** — 중복 지적은 합치고 출처(검증/리뷰)를 병기한다
2. `SendMessage`로 **기존 implementer를 재개**해 통합 문제 목록(재현 방법·기대 결과)을 전달한다 — 새 Agent를 스폰하면 컨텍스트가 사라져 같은 실수를 반복한다
3. implementer가 수정 + 자체 검증 — 수정 회차의 게이트는 `references/verification-policy.md`의 「게이트 등급」을 따른다(빠른 게이트 기본 · 승격 조건 확인)
4. `SendMessage`로 기존 verifier·리뷰 담당을 재개해 실패 항목과 회귀 검증을 요청한다 — **재확인도 가능하면 병렬**로 띄운다. 단 **제품 코드가 바뀐 수정 회차의 재확인은 두 담당 모두 거친 뒤에만 병합**한다
5. 완료 조건을 모두 충족할 때까지 반복한다 — **병합 직전에 전체 게이트를 최종 1회** 실행한다(오케스트레이터 또는 마지막 재확인 담당)

같은 문제가 두 회차 연속 해소되지 않으면 사용자에게 상황과 대안을 보고한다.

**Minor 이월 기준**(v1.2): 승인 기준은 Blocker+Major 0이다 — Minor는 병합을 막지 않는다. 재확인 회차의 비용은 diff 크기가 아니라 판정 항목 수에 비례해(재확인이 초회의 57~71% 실측) 회차 추가가 비싸므로, 재확인에서 나온 **신규 Minor**는 다음 두 조건을 모두 충족하면 수정 회차를 더 돌리지 않고 이월할 수 있다: ① 제품 결함이 아니다(감지기·기록·문서 보강류) ② 다음 슬라이스 또는 예정된 후속 작업이 같은 파일을 수정한다. **이월은 반드시 이월 목록 파일에 출처와 함께 기록**하고 다음 회차 프롬프트에 싣는다 — 기록 없는 이월은 유실이다. (근거: 한 화면에서 이월 4건 전부가 다음 회차에서 처리됐다)

### 11. 최종 보고

정책 §13의 완료 정의를 충족했는지 확인하고 사용자에게 보고한다. 포함할 것:

- 완료 조건별 결과
- 수행한 검증과 **실행 명령·결과 근거**
- 기존 실패·제한 사항·남은 위험
- 계획 밖 변경이 없었다는 사실(또는 승인받은 변경 목록)

**하나라도 미충족이면 완료로 보고하지 않는다.** 검증하지 못한 항목이 있으면 이유와 위험을 적어 사용자 판단을 요청한다.

**GitHub 이슈를 닫으며 정리보고를 할 때는 `assets/closing-report-template.md` 양식을 따른다**(v1.1). 정책 §11~§12의 실행·검증 보고서를 대체하지 않는 **이슈 종료 시점의 추가 산출물**이다. 규모 비례(소형 작업은 1~2절만) · 공개 경계 · 지표 기반 프로파일링 원칙은 템플릿에 있다 — Agent별 시간은 각 보고서의 시작·종료 시각과 오케스트레이터가 기록한 호출·반환 시각을 쓴다.

## 승인 없이 하지 않는 것

정책 §14와 `references/risk-classification.md`에 따라, 다음은 사용자 승인 전에 실행하지 않는다.

신규 외부 의존성 추가 · 의존성 주요 버전 변경 · 공개 인터페이스 변경 · 데이터 구조·API 계약 변경 · 인증·권한·개인정보·결제 변경 · 빌드·배포 파이프라인 변경 · 운영 데이터 변경 · 외부 메시지 전송 · 유료 서비스 사용 · 대규모 삭제·마이그레이션 · 기존 작업을 덮어쓰거나 되돌리는 작업.

**이 저장소는 공개 저장소다.** 비공개 설계 문서의 본문, 고객사 식별 정보, 실 운영 값, 인프라 정보가 코드·주석·커밋 메시지·PR 본문·테스트 데이터에 들어가려 하면 중단하고 대체 방법을 찾는다(루트 `CLAUDE.md`).

## 에러 핸들링

| 상황 | 처리 |
| --- | --- |
| Agent 호출 실패·응답 없음 | 1회 재시도. 재실패하면 그 단계를 건너뛰지 말고 사용자에게 보고한다 — 검증 단계라면 「최종 검증 완료」로 처리하지 않는다 |
| Agent 호출이 서버 측 오류(과부하·5xx)로 연쇄 실패 | **냉각 사다리**(v1.2): 즉시 재시도 → 3분 냉각 → 10분 냉각 → 중단·보고. 재개 전에 브랜치·트리 상태를 확인한다. 일시 장애에서 파이프라인이 스스로 회복한 실측(1번 팀 — 10분 냉각으로 작업 손실 0)에 근거한다 |
| 담당 교체·기존 워크트리 인계 | **첫 명령은 `git status` + 대상 커밋 해시 대조**(v1.2) — 선임이 주입한 뮤턴트가 남은 트리를 그대로 물려받으면 설계 판단이 뒤집힐 수 있다(오염 인계 실증 — 교체 담당의 첫 status가 잡아 복원) |
| 검증 Agent를 쓸 수 없음 | 완료로 선언하지 않는다. 수행한 자체 검증과 미수행 검증을 구분해 보고한다(정책 §7.1) |
| 계획과 실제 변경이 어긋남 | 승인 없이 통과시키지 않는다. 사용자에게 차이와 판단 요청을 보고한다 |
| 기존 실패가 이미 있는 저장소 | 기준 상태로 기록하고, 완료 판정에서 제외하되 「작업 결과 통과, 기존 실패 존재」로 명시한다 |
| 미커밋 변경과 분리 불가 | 즉시 중단하고 보고한다. 사용자 변경을 덮어쓰거나 stash하지 않는다 |
| 요구사항 해석이 갈림 | 중단하고 해석 후보와 결과 차이를 제시해 사용자에게 묻는다 |

## 테스트 시나리오

**정상 흐름 (중간 위험 화면 1장 — v1.1 개정 흐름)**: 요청 접수 → 미커밋 변경 없음 확인 → 중간 위험 판정 → 3단위 분할(전례 사본 화면) → planner 상세 계획(검증 방법 표에 검증 담당 배정 항목 명시) → 사용자 승인 → 기준 상태 기록 → implementer 구현(**copy-checklist 대조 결과를 실행 보고서에 기록**) + 자체 검증 → 구현 초회 커밋 완료 시 **전체 게이트** → 【병렬 분기】 직렬 예외 근거 없음 확인 후 verifier(포트 4023 · **계획 표 배정 항목** · 검증 초회 전체 게이트 + 전체 테스트 2회)와 리뷰 담당(포트 4024 · **전례 대조·표 밖 영역** · 검증 배정 목록을 「재지 않을 자리」로 수령)을 **한 메시지에서 동시 착수** → 두 보고 수합, 지적 통합(출처 병기) → implementer 1회 수정 회차(**빠른 게이트** — 승격 조건 비해당 확인) → 재확인 병렬(두 담당 모두 통과) → **병합 직전 전체 게이트 최종 1회** → 완료 조건·증거 포함 최종 보고 → 【이슈 종료】 `assets/closing-report-template.md` 양식으로 정리보고(각 보고서의 시작·종료 시각 + 오케스트레이터 호출·반환 기록으로 5절 프로파일링 표 작성).

**에러 흐름 (검증 실패 후 재검증)**: 위와 동일하게 진행하다 verifier가 「수정 후 재검증 필요」 판정(예: 오류 경로 테스트 누락), 리뷰는 Minor 2건 → 오케스트레이터가 두 보고의 지적을 합쳐 한 번의 수정 회차로 `SendMessage` → implementer 수정 + 자체 검증(빠른 게이트 — 단 수정이 목 서버에 닿아 **전체 게이트로 승격**) → verifier·리뷰 담당 재개(병렬) → 실패 항목 + 회귀 검증 「통과」 → 최종 보고에 1회 재작업 사실 기록.

**직렬 예외 흐름**: 큰 쓰기 슬라이스에서 자체 검증 중 위험 신호(예: 상태 연쇄의 경계 미검증) → 오케스트레이터가 「검증 반환 확률이 높다」고 판단, 직렬 선택(근거를 기록) → verifier 먼저, 「수정 후 재검증 필요」 반환 → 수정 회차 후 재검증 통과 → 그때 리뷰 착수 — 리뷰가 무효가 될 코드를 읽지 않았다.

**중단 흐름 (승인 필요)**: 구현 중 신규 외부 의존성이 필요해짐 → implementer가 중단하고 보고 → 오케스트레이터가 사용자에게 대안·영향·권장안 제시 → 승인 후 계획을 갱신하고 재개.
