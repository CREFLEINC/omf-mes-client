# 배치 규범

간격·정렬 값을 **무엇을 기준으로 정하는가**의 기록. 값 자체보다 그 값이 어디서 나왔는지를 남기는 것이 목적이다.

## 이 문서의 범위

**담는 것** — 화면 셸이 소유하는 배치 결정. 블록 사이 간격, 한 줄 안에서 컨트롤을 어느 선에 맞추는가,
디자인 시스템이 라벨을 주지 않는 컨트롤의 라벨 처리, 비활성 컨트롤의 사유를 어디에 어떻게 붙이는가, 반응형 접힘 기준점.

**담지 않는 것** — 컴포넌트 내부의 치수·색·상태(디자인 시스템 소관), 도구 선택(`decisions.md` 소관),
화면별 필드 순서와 문구(화면 스펙 소관).

### 왜 디자인 시스템이 아니라 여기가 소유하나

이 규범들은 전부 **기존 컴포넌트의 조합**(루트 `CLAUDE.md`의 갭 분류 `c`)이다. 같은 문서가
「조합물을 DS로 올리려는 것이 디자인 시스템이 망가지는 가장 흔한 경로」라고 적었다.

디자인 시스템 쪽 `docs/patterns.md`도 등재 기준을 스스로 이렇게 못 박았다 —
**「갈리는 것이 렌더뿐이면(간격·정렬·라벨 문구) 패턴이 아니다」.** 아래 다섯 건이 정확히 그 경우다.
같은 문서의 「검색·필터 바」 패턴은 트리거 모델·조건 칩·빈 상태·조건 유지 같은 **동작만** 정하고
배치·정렬·간격은 정하지 않는다. 그 빈자리를 이 문서가 채운다.

같은 문서가 정한 서술 방식도 따른다 — **기본값 하나와 이탈 조건을 함께 적는다.**
「상황에 따라 다르다」로 쓰면 등재하지 않은 것과 같다.

## 근거 토큰

값의 출처는 전부 디자인 시스템 토큰이다. 아래 픽셀 값은 토큰 정의에서 계산한 것이다.

| 토큰 | 값 |
| --- | --- |
| `--space-1` / `--space-3` / `--space-4` / `--space-5` / `--space-6` | 4 / 12 / 16 / 20 / 24 px |
| `--control-height-md` | 40px |
| `--type-label-sm` | `500 12px/16px` → 줄높이 **16px** |
| `--type-body-sm` | `400 14px/20px` |
| `--type-body-lg` | `400 16px/24px` |

## 규범 1 — 화면 최상위 블록의 세로 리듬

**기준.** 디자인 시스템 컴포넌트는 **바깥 여백을 갖지 않는다.** `AlertBanner`의 `padding`은 안쪽 여백이고,
`PageHeader`의 `gap`은 탐색경로↔제목↔액션 사이의 **내부** 간격이다. 따라서 블록과 블록 사이 이음매는
**배치하는 쪽(화면 셸)이 소유한다.**

이음매를 블록마다 하나씩 붙이면 반드시 하나를 빠뜨린다. 그래서 **이음매를 한 곳에서 한 번만 정의한다.**

**값과 근거.** `--space-5`(20px).
블록 사이 간격은 **그 블록의 내부 최대 간격보다 커야 블록 경계가 읽힌다.** 지금 쓰이는 블록의 내부 최대 간격은
`PageHeader`의 16px과 `.pane`의 안쪽 여백 16px이므로 20px이 그보다 크다.
24px(`--space-6`)로 올리면 `main`의 안쪽 여백과 같아져 더 뚜렷하지만, 이미 확정된 다른 간격까지 함께 바뀐다.

**구현.**

```css
main > * + * {
  margin-top: var(--space-5);
}
```

인접 형제 결합자를 쓰는 이유는 블록 서식을 그대로 두기 때문이다. flex·grid 컨테이너로 바꾸면 자식이
`flex-shrink`로 눌리거나 grid 최소 크기 문제를 안는다. 래퍼 요소를 두는 방식은 **화면마다 래퍼를 잊을 수 있다** —
이 규범이 생긴 계기가 바로 「잊음」이었다.

`<dialog>`가 같은 자리에 있어도 영향이 없다. 닫혀 있을 때는 브라우저 기본 스타일이 `display: none`이고
(디자인 시스템이 이 값을 덮어쓰지 않는다), 열리면 최상위 레이어로 올라가 흐름에서 빠진다.

**이탈 조건.** 바로 앞 블록과 붙여야 하는 블록은 그 블록에 `margin-top: 0`을 직접 준다.

## 규범 2 — 한 줄에 라벨 있는 컨트롤과 없는 컨트롤이 섞일 때의 정렬

**기준.** **컨트롤 상자의 윗선**에 맞춘다. 「컨트롤 상자」란 입력·선택·버튼의 **테두리가 그려지는 사각형**을 말한다.
라벨은 그 상자 위에 있고, 사유·오류 텍스트는 그 아래로 자란다.

세 후보를 비교하면 윗선만 남는다.

| 정렬 기준 | 사유·오류가 붙었을 때 |
| --- | --- |
| 가운데(`center`) | 셀 높이가 제각각이라 어느 선도 맞지 않는다 |
| 아래 가장자리(`flex-end`) | 사유가 붙는 순간 그 컨트롤이 사유 높이만큼 **위로 밀린다** |
| **윗선(`flex-start` + 라벨 층 확보)** | 사유가 아래로 자라도 컨트롤 상자의 위치가 변하지 않는다 |

**값과 근거.**

- **라벨 층 = 20px** = 라벨 줄높이 16px(`--type-label-sm`) + 라벨–컨트롤 간격 4px(`--space-1`).
  이 값은 우연이 아니다. 디자인 시스템의 내장 라벨(`SearchInput`)이 `flex-direction: column; gap: var(--space-1)`이고,
  우리가 직접 붙이는 `.field-label`이 `margin-bottom: var(--space-1)`이라 **양쪽에서 같은 20px이 나온다**(규범 3이 이것을 보장한다).
- **컨트롤 상자 높이 = `--control-height-md`(40px)** — 버튼·검색 입력·선택 트리거의 기본 크기가 모두 이 토큰이다.

줄 위쪽을 0으로 놓았을 때 결과:

| 셀 구성 | 계산 | 컨트롤 상자 위치 |
| --- | --- | --- |
| 라벨 내장 입력 | 16 + 4 + 40 | 20 → 60 |
| 직접 붙인 라벨 + 선택 | 16 + 4 + 40 | 20 → 60 |
| 라벨 없는 버튼 | 라벨 층 20 + 40 | 20 → 60 |
| 라벨 없는 1층 컨트롤(체크박스) | 라벨 층 20 + 40px 상자 안 중앙 | 상자 20 → 60 |

**구현.**

```css
:root {
  --field-label-layer: calc(16px + var(--space-1));
}

.filter-bar {
  align-items: flex-start;
}

.field-cell {
  display: flex;
  flex-direction: column;
  align-items: flex-start;
  justify-content: center;
  align-self: start;
  min-height: var(--control-height-md);
}

.field-cell-unlabeled {
  margin-top: var(--field-label-layer);
}
```

`.field-cell`이 `justify-content: center`와 `min-height`를 함께 갖기 때문에 **한 클래스가 세 경우를 모두 처리한다.**
컨트롤이 40px보다 낮으면 상자 안 중앙에 놓이고, 40px이면 그대로이며, 40px보다 높으면(라벨+컨트롤, 컨트롤+사유) 위에서부터 쌓인다.

**`align-self: start`는 이 셀이 grid 부모 안에 놓일 때를 위한 것이다.** grid 자식은 기본이 `stretch`라
셀이 줄 높이만큼 늘어나고, 그러면 `justify-content: center`가 발동해 **사유가 없는 셀의 라벨이 같은 줄 짝보다 아래로 내려간다.**
이 규범이 막으려는 어긋남이 그대로 생기는 것이다. flex 부모 안에서는 이미 같은 값이라 영향이 없다.
셀 하나가 두 부모에서 같게 동작해야 규범이 성립한다.

`.field-cell`을 flex 컨테이너로 둔 것에는 두 번째 이득이 있다. 인라인 서식 컨트롤(`display: inline-block`인 선택 트리거,
`inline-flex`인 체크박스)이 블록 컨테이너 안에 있으면 인라인 줄상자가 생겨 글꼴 내려긋기만큼의 빈 공간이 붙는다.
flex 자식은 블록화되므로 이 빈 공간이 사라지고 셀 높이가 계산값과 정확히 같아진다.

**이탈 조건.** 한 줄에 라벨 있는 컨트롤이 **하나도 없으면** 라벨 층을 확보하지 않는다
(예: 조건 칩만 있는 줄, 폼 하단 액션 줄).

## 규범 3 — 디자인 시스템이 `label` prop을 주지 않는 컨트롤의 라벨 처리

**기준.** 선택(`Select`) 컴포넌트에는 `label` prop이 없다(`id`·`aria-label`·`aria-labelledby`만 있다).
라벨을 직접 만들되 **디자인 시스템이 내장 라벨에 쓰는 것과 같은 토큰**을 쓴다.
그래야 규범 2의 라벨 층 20px이 양쪽에서 같게 나온다.

**값과 근거.** 내장 라벨과 1:1로 맞춘다.

| 속성 | 값 |
| --- | --- |
| 글꼴 | `var(--type-label-sm)` + `var(--type-label-sm-tracking)` |
| 색 | `var(--on-surface-variant)` |
| 컨트롤과의 간격 | `var(--space-1)` |

**구현.** `.field-label` 클래스를 쓴다. 컨트롤에는 `id`를 주고 `<label htmlFor={id}>`로 잇는다.
셀 래퍼에는 규범 2의 `.field-cell`을 붙인다.

필수 표시(`*`) 같은 **장식은 `<label>` 밖에 두되 같은 줄에 오도록** `.field-label`을 감싸는 요소로 올린다.

```tsx
<span className="field-label">
  <label htmlFor={id}>{label}</label>
  {required && <span aria-hidden="true"> *</span>}
</span>
```

두 조건을 동시에 만족시키는 유일한 배치이기 때문이다. `.field-label`이 블록 서식이라 `*`를 그 **밖**에 두면
별도 줄로 떨어진다. 반대로 `*`를 `<label>` **안**에 넣으면 접근성 이름이 「이름 *」이 되어 라벨 조회가 깨진다.

값을 보여 주기만 하면 되는 자리는 폼 컨트롤을 잠그지 말고 **값 표기**로 낸다
(`<span className="field-label" id>` + `<p aria-labelledby>`). 디자인 시스템 `docs/patterns.md`의
「읽기 전용 구획 배치」를 그대로 따른 것이다.

**이탈 조건.** 컨트롤이 시각적 라벨 없이 쓰이는 자리(예: 표 안의 인라인 편집)에서는 `.field-label` 대신 `aria-label`을 준다.

## 규범 4 — 비활성 컨트롤의 사유 표시

**기준.** 사유를 보이는 것으로는 부족하다. **어느 컨트롤의 사유인지 보이게 붙인다.** 다섯 항목이다.

1. **사유는 감추지 않고 항상 보이는 DOM 텍스트로 렌더하고 `aria-describedby`로 그 컨트롤에 잇는다.**
   비활성 컨트롤은 포커스를 받지 못해 툴팁만으로는 키보드·스크린리더 사용자가 닿을 수 없다
   (디자인 시스템 `docs/patterns.md` 「읽기 전용 구획 배치」).
2. **사유는 그 컨트롤 바로 아래, 컨트롤과 왼쪽 가장자리를 맞춰 놓는다.** 규범 2의 `.field-cell`이 그 세로 묶음이다.
3. **사유 텍스트의 폭에 상한을 준다.** 사유가 줄 전체로 퍼지면 **줄 전체의 설명으로 읽힌다.**
4. **사유가 붙는 비활성 버튼은 테두리가 남는 표현을 쓴다.**
5. **문구는 그 컨트롤의 이름으로 시작한다.**

**값과 근거.**

*폭 상한 `20rem`(320px).* 폼 페인의 액션 줄 폭은 통상 창 폭에서 700~800px 대다.
사유 폭을 그 **절반 아래**로 가두면 「줄 전체」로 읽히지 않는다.
`--type-body-sm`(14px)에서 한 줄에 한글 약 22자가 들어가 두세 줄로 접힌다.

*버튼 표현.* 비활성일 때 각 variant에 남는 것은 다음과 같다.

| variant | 비활성일 때 남는 것 | 버튼으로 보이나 |
| --- | --- | --- |
| `text` | 흐린 글자색뿐. 배경·테두리 없음 | **아니오** — 라벨로 읽힌다 |
| `outlined` | `inset` 그림자 테두리가 남는다 | 예 |
| `filled` · `tonal` | 배경 채움이 남는다 | 예(다만 주 액션처럼 보인다) |

→ 사유가 붙는 비활성 보조 액션은 **`outlined`**를 쓴다. `text`는 쓰지 않는다.

*문구.* 주어가 없으면 붙은 대상이 시각적으로 끊겼을 때 복원 단서가 없다.
문형은 **「〈컨트롤 이름〉은 … 없습니다. 〈풀리는 조건〉이면 이 버튼을 쓸 수 있습니다.」**
개발·설계 쪽 표현(「규약」·「서버 렌더링」·「API」·「스키마」)과 내부 이슈 번호를 쓰지 않는다.

**구현.**

```css
.field-note {
  max-width: 20rem;
}

.form-actions {
  align-items: flex-start;
}

.form-actions-secondary {
  margin-right: auto;
}
```

액션 줄에서 보조 액션(사유가 붙은 비활성 버튼)은 줄 **왼쪽**에 두고 주 액션(취소·저장)은 오른쪽에 남긴다.
`margin-right: auto`로 그 배치를 **의도적으로** 만든다 — 폭이 넓어서 우연히 왼쪽에 놓이는 것과 다르다.
`align-items: flex-start` 덕분에 사유가 아래로 자라도 주 액션은 윗줄에 남는다.

보조 액션을 주 액션 옆에 붙이면 사유가 취소 버튼 아래로 흘러 소유가 다시 모호해진다.
보조 액션에 자기 줄을 주면 소유는 확실해지지만 비활성 버튼 하나에 한 줄을 쓴다.

**이탈 조건.**

- 여러 컨트롤이 공유하는 안내(예: 선택지가 아직 준비되지 않았다는 알림)는 컨트롤 이름 대신
  **무엇에 대한 안내인지**로 시작한다.
- 텍스트 입력(`TextField`)은 `disabledReason` prop이 이 처리를 내장하고 있으므로 직접 만들지 말고 그대로 쓴다.

## 규범 5 — 반응형 접힘 기준점

**기준.** 접힘 기준점은 **그 배치가 유지될 수 있는 최소 폭**에서 정한다. 임의의 「모바일/태블릿」 구분이 아니다.

**값과 근거.**

| 기준점 | 무엇이 접히나 | 근거 |
| --- | --- | --- |
| **1280px** | 2단 배치 → 1단 | 좌측 열 최소 폭이 320px(`minmax(320px, 2fr)`)이고 우측이 `3fr`이다. 이 아래에서는 우측 폼이 2열을 유지할 폭을 잃는다 |
| **720px** | 폼 그리드 2열 → 1열 | 한 열이 약 340px로, 텍스트 입력·선택이 값을 자르지 않고 담기는 하한이다 |

**구현.** `.two-pane`과 `.form-grid`의 `@media (max-width: …)` 블록. 값은 이미 코드에 있고,
이 문서가 채우는 것은 **그 숫자가 어디서 왔는지**다.

창 폭이 아니라 페인 폭을 기준으로 삼는 컨테이너 쿼리가 더 정확하지만, 소비 화면이 늘어나기 전에는 이득이 없다.
두 번째 화면에서 다시 판단한다.

**이탈 조건.** 다른 열 구성을 쓰는 화면은 자기 기준점을 정하고 **그 근거를 자기 화면 파일에 적는다.**
근거 없이 숫자만 두지 않는다.

## 갱신 규칙

- **두 번째 화면에서 같은 결정을 또 하게 될 때 규범을 추가한다.** 화면 한 장에서 전반 규범을 뽑으면 과적합한다.
- 규범을 추가할 때는 **기준 · 값과 근거 · 구현 · 이탈 조건** 네 항목을 모두 채운다. 하나라도 비면 등재하지 않은 것과 같다.
- 값을 바꿀 때는 이 문서를 먼저 고치고 `app.css`를 맞춘다. 구현이 아니라 규범이 정본이다.
- 이 문서는 공개 저장소에 있다. 고객사 식별 정보·실 운영 값·인프라 정보·비공개 문서 본문·화면 캡처를 넣지 않는다.
  가능한 한 **컴포넌트의 언어**로 쓴다.
