# 배치 규범

간격·정렬 값을 **무엇을 기준으로 정하는가**의 기록. 값 자체보다 그 값이 어디서 나왔는지를 남기는 것이 목적이다.

## 이 문서의 범위

**담는 것** — 화면 셸이 소유하는 배치 결정. 블록 사이 간격, 한 줄 안에서 컨트롤을 어느 선에 맞추는가,
디자인 시스템이 라벨을 주지 않는 컨트롤의 라벨 처리, 비활성 컨트롤의 사유를 어디에 어떻게 붙이는가, 반응형 접힘 기준점.

**담지 않는 것** — 컴포넌트 내부의 치수·색·상태(디자인 시스템 소관), 도구 선택(`decisions.md` 소관),
화면별 필드 순서와 문구(화면 스펙 소관).

### 왜 디자인 시스템이 아니라 여기가 소유하나

이 규범들은 전부 **기존 컴포넌트의 조합**(루트 `CLAUDE.md`의 갭 분류 `c`)이다. 같은 문서가
「조합물을 DS로 올리려는 것이 디자인 시스템이 망가지는 가장 흔한 경로」라고 적었다.

디자인 시스템 쪽 `docs/patterns.md`도 등재 기준을 스스로 이렇게 못 박았다 —
**「갈리는 것이 렌더뿐이면(간격·정렬·라벨 문구) 패턴이 아니다」.** 아래 다섯 건이 정확히 그 경우다.
같은 문서의 「검색·필터 바」 패턴은 트리거 모델·조건 칩·빈 상태·조건 유지 같은 **동작만** 정하고
배치·정렬·간격은 정하지 않는다. 그 빈자리를 이 문서가 채운다.

같은 문서가 정한 서술 방식도 따른다 — **기본값 하나와 이탈 조건을 함께 적는다.**
「상황에 따라 다르다」로 쓰면 등재하지 않은 것과 같다.

## 근거 토큰

값의 출처는 전부 디자인 시스템 토큰이다. 아래 픽셀 값은 토큰 정의에서 계산한 것이다.

| 토큰 | 값 |
| --- | --- |
| `--space-1` / `--space-3` / `--space-4` / `--space-5` / `--space-6` | 4 / 12 / 16 / 20 / 24 px |
| `--control-height-md` | 40px |
| `--type-label-sm` | `500 12px/16px` → 줄높이 **16px** |
| `--type-body-sm` | `400 14px/20px` |
| `--type-body-lg` | `400 16px/24px` |

## 규범 1 — 화면 최상위 블록의 세로 리듬

**기준.** 디자인 시스템 컴포넌트는 **바깥 여백을 갖지 않는다.** `AlertBanner`의 `padding`은 안쪽 여백이고,
`PageHeader`의 `gap`은 탐색경로↔제목↔액션 사이의 **내부** 간격이다. 따라서 블록과 블록 사이 이음매는
**배치하는 쪽(화면 셸)이 소유한다.**

이음매를 블록마다 하나씩 붙이면 반드시 하나를 빠뜨린다. 그래서 **이음매를 한 곳에서 한 번만 정의한다.**

**값과 근거.** `--space-5`(20px).
블록 사이 간격은 **그 블록의 내부 최대 간격보다 커야 블록 경계가 읽힌다.** 지금 쓰이는 블록의 내부 최대 간격은
`PageHeader`의 16px과 `.pane`의 안쪽 여백 16px이므로 20px이 그보다 크다.
24px(`--space-6`)로 올리면 `main`의 안쪽 여백과 같아져 더 뚜렷하지만, 이미 확정된 다른 간격까지 함께 바뀐다.

**구현.**

```css
main > * + * {
  margin-top: var(--space-5);
}
```

인접 형제 결합자를 쓰는 이유는 블록 서식을 그대로 두기 때문이다. flex·grid 컨테이너로 바꾸면 자식이
`flex-shrink`로 눌리거나 grid 최소 크기 문제를 안는다. 래퍼 요소를 두는 방식은 **화면마다 래퍼를 잊을 수 있다** —
이 규범이 생긴 계기가 바로 「잊음」이었다.

`<dialog>`가 같은 자리에 있어도 영향이 없다. 닫혀 있을 때는 브라우저 기본 스타일이 `display: none`이고
(디자인 시스템이 이 값을 덮어쓰지 않는다), 열리면 최상위 레이어로 올라가 흐름에서 빠진다.

**이탈 조건.** 바로 앞 블록과 붙여야 하는 블록은 그 블록에 `margin-top: 0`을 직접 준다.

## 규범 2 — 한 줄에 라벨 있는 컨트롤과 없는 컨트롤이 섞일 때의 정렬

**기준.** **컨트롤 상자의 윗선**에 맞춘다. 「컨트롤 상자」란 입력·선택·버튼의 **테두리가 그려지는 사각형**을 말한다.
라벨은 그 상자 위에 있고, 사유·오류 텍스트는 그 아래로 자란다.

세 후보를 비교하면 윗선만 남는다.

| 정렬 기준 | 사유·오류가 붙었을 때 |
| --- | --- |
| 가운데(`center`) | 셀 높이가 제각각이라 어느 선도 맞지 않는다 |
| 아래 가장자리(`flex-end`) | 사유가 붙는 순간 그 컨트롤이 사유 높이만큼 **위로 밀린다** |
| **윗선(`flex-start` + 라벨 층 확보)** | 사유가 아래로 자라도 컨트롤 상자의 위치가 변하지 않는다 |

**값과 근거.**

- **라벨 층 = 20px** = 라벨 줄높이 16px(`--type-label-sm`) + 라벨–컨트롤 간격 4px(`--space-1`).
  이 값은 우연이 아니다. 디자인 시스템의 내장 라벨(`SearchInput`)이 `flex-direction: column; gap: var(--space-1)`이고,
  우리가 직접 붙이는 `.field-label`이 `margin-bottom: var(--space-1)`이라 **양쪽에서 같은 20px이 나온다**(규범 3이 이것을 보장한다).
- **컨트롤 상자 높이 = `--control-height-md`(40px)** — 버튼·검색 입력·선택 트리거의 기본 크기가 모두 이 토큰이다.

줄 위쪽을 0으로 놓았을 때 결과:

| 셀 구성 | 계산 | 컨트롤 상자 위치 |
| --- | --- | --- |
| 라벨 내장 입력 | 16 + 4 + 40 | 20 → 60 |
| 직접 붙인 라벨 + 선택 | 16 + 4 + 40 | 20 → 60 |
| 라벨 없는 버튼 | 라벨 층 20 + 40 | 20 → 60 |
| 라벨 없는 1층 컨트롤(체크박스) | 라벨 층 20 + 40px 상자 안 중앙 | 상자 20 → 60 |

**구현.**

```css
:root {
  --field-label-layer: calc(16px + var(--space-1));
}

.filter-bar {
  align-items: flex-start;
}

.field-cell {
  display: flex;
  flex-direction: column;
  align-items: flex-start;
  justify-content: center;
  align-self: start;
  min-height: var(--control-height-md);
}

.field-cell-unlabeled {
  margin-top: var(--field-label-layer);
}
```

`.field-cell`이 `justify-content: center`와 `min-height`를 함께 갖기 때문에 **한 클래스가 세 경우를 모두 처리한다.**
컨트롤이 40px보다 낮으면 상자 안 중앙에 놓이고, 40px이면 그대로이며, 40px보다 높으면(라벨+컨트롤, 컨트롤+사유) 위에서부터 쌓인다.

**`align-self: start`는 이 셀이 grid 부모 안에 놓일 때를 위한 것이다.** grid 자식은 기본이 `stretch`라
셀이 줄 높이만큼 늘어나고, 그러면 `justify-content: center`가 발동해 **사유가 없는 셀의 라벨이 같은 줄 짝보다 아래로 내려간다.**
이 규범이 막으려는 어긋남이 그대로 생기는 것이다. flex 부모 안에서는 이미 같은 값이라 영향이 없다.
셀 하나가 두 부모에서 같게 동작해야 규범이 성립한다.

`.field-cell`을 flex 컨테이너로 둔 것에는 두 번째 이득이 있다. 인라인 서식 컨트롤(`display: inline-block`인 선택 트리거,
`inline-flex`인 체크박스)이 블록 컨테이너 안에 있으면 인라인 줄상자가 생겨 글꼴 내려긋기만큼의 빈 공간이 붙는다.
flex 자식은 블록화되므로 이 빈 공간이 사라지고 셀 높이가 계산값과 정확히 같아진다.

**이탈 조건.** 한 줄에 라벨 있는 컨트롤이 **하나도 없으면** 라벨 층을 확보하지 않는다
(예: 조건 칩만 있는 줄, 폼 하단 액션 줄).

### 2-1. 짝인 액션은 함께 줄바꿈된다

**기준.** `.filter-bar`는 `flex-wrap: wrap`이라 폭이 좁아지면 컨트롤이 하나씩 다음 줄로 넘어간다.
**의미상 짝인 액션(조회·초기화)은 갈라지면 안 된다** — 좁은 페인에서 실제로 [초기화]만 혼자 한 줄로 떨어졌고,
그러면 그 버튼이 무엇에 딸린 것인지 읽히지 않는다.

**값과 근거.** 짝을 한 요소로 감싸면 그 요소가 줄바꿈의 최소 단위가 된다.
안쪽 간격은 `--space-3`(12px)으로 `.filter-bar`의 `gap`과 같게 둔다 — 다르게 두면
같은 줄에 두 종류의 간격이 생겨 묶임이 오히려 흐려진다.

**라벨 층은 묶음이 한 번만 갖는다.** 규범 2의 `.field-cell-unlabeled`를 버튼마다 붙이면
묶은 뒤에는 두 번 적용돼 짝이 아래로 내려간다. 묶음 쪽에 한 번 붙인다.

**구현.**

```css
.filter-actions {
  display: flex;
  gap: var(--space-3);
}
```

**이탈 조건.** 짝이 아닌 액션(서로 독립적으로 쓰이는 버튼)은 묶지 않는다.
묶으면 좁은 폭에서 줄바꿈 여지가 줄어 오히려 줄 수가 늘어난다.

## 규범 3 — 디자인 시스템이 `label` prop을 주지 않는 컨트롤의 라벨 처리

**기준.** 선택(`Select`) 컴포넌트에는 `label` prop이 없다(`id`·`aria-label`·`aria-labelledby`만 있다).
라벨을 직접 만들되 **디자인 시스템이 내장 라벨에 쓰는 것과 같은 토큰**을 쓴다.
그래야 규범 2의 라벨 층 20px이 양쪽에서 같게 나온다.

**값과 근거.** 내장 라벨과 1:1로 맞춘다.

| 속성 | 값 |
| --- | --- |
| 글꼴 | `var(--type-label-sm)` + `var(--type-label-sm-tracking)` |
| 색 | `var(--on-surface-variant)` |
| 컨트롤과의 간격 | `var(--space-1)` |

**구현.** `.field-label` 클래스를 쓴다. 컨트롤에는 `id`를 주고 `<label htmlFor={id}>`로 잇는다.
셀 래퍼에는 규범 2의 `.field-cell`을 붙인다.

필수 표시(`*`) 같은 **장식은 `<label>` 밖에 두되 같은 줄에 오도록** `.field-label`을 감싸는 요소로 올린다.

```tsx
<span className="field-label">
  <label htmlFor={id}>{label}</label>
  {required && <span aria-hidden="true"> *</span>}
</span>
```

두 조건을 동시에 만족시키는 유일한 배치이기 때문이다. `.field-label`이 블록 서식이라 `*`를 그 **밖**에 두면
별도 줄로 떨어진다. 반대로 `*`를 `<label>` **안**에 넣으면 접근성 이름이 「이름 *」이 되어 라벨 조회가 깨진다.

값을 보여 주기만 하면 되는 자리는 폼 컨트롤을 잠그지 말고 **값 표기**로 낸다
(`<span className="field-label" id>` + `<p aria-labelledby>`). 디자인 시스템 `docs/patterns.md`의
「읽기 전용 구획 배치」를 그대로 따른 것이다.

**이탈 조건.** 컨트롤이 시각적 라벨 없이 쓰이는 자리(예: 표 안의 인라인 편집)에서는 `.field-label` 대신 `aria-label`을 준다.

### 3-1. 폼 그리드 안에서 선택 컨트롤은 칸 폭을 채운다

**기준.** 폼 그리드(`.form-grid`) 안의 `.field-cell`은 자식을 **칸 폭에 맞춰 늘린다.**
줄 안에 컨트롤을 나란히 놓는 자리(`.filter-bar`)는 그대로 둔다 — 거기서는 각 컨트롤이 제 내용 폭을 갖는 것이 맞다.

**값과 근거.** 디자인 시스템 `Select`의 뿌리 요소는 `display: inline-block`이라 **내용 폭으로 줄어든다.**
그 안의 트리거는 `width: 100%`이고 선택지 목록은 `position: absolute; left: 0; right: 0`이라
**둘 다 뿌리 폭을 따라간다.** 그래서 뿌리가 좁아지면 트리거뿐 아니라 **선택지 문구까지 잘린다**
(실제로 「EA」가 「E」로 잘려 무엇을 고르는지 읽을 수 없었다 — 값을 고르지 못하게 만드는 기능 결함이다).

늘리는 자리를 `.field-cell`이 아니라 **`.form-grid`의 후손**으로 한정하는 이유는,
같은 셀 클래스가 필터 바에서도 쓰이기 때문이다. 셀 쪽에 일괄로 주면 필터 바의 컨트롤이 줄 전체로 퍼진다.

`Select`에만 폭을 주지 않고 셀의 정렬 축을 바꾸는 이유는 **디자인 시스템의 내부 클래스 이름을 겨냥하지 않기 위해서다.**
그 이름은 해시가 붙어 있어 버전이 바뀌면 조용히 어긋난다.

**구현.**

```css
.form-grid .field-cell {
  align-items: stretch;
}
```

**이탈 조건.** 폼 그리드 안이어도 내용 폭을 지켜야 하는 컨트롤(예: 값이 짧은 단위 토글)은
그 셀에 `align-items: flex-start`를 직접 되돌려 준다.

### 3-2. 줄 안의 선택칸은 값이 길면 최소 폭을 준다 (`.wide-select`)

**기준.** 필터 바처럼 컨트롤을 나란히 놓는 줄에서, **선택지 값이 긴 `Select`가 놓인 셀에만**
최소 폭을 준다. **옵트인이다** — 셀 클래스 전체에 걸지 않는다.

**이것은 규범 3-1의 형제이고, 같은 실패의 두 번째 목격이다.**

| | 첫 번째 (W-06-07) | 두 번째 (W-06-10) |
| --- | --- | --- |
| 증상 | 「EA」가 **「E」**로 잘렸다 | 「FAILED」가 **「FAI⋯」**로 잘렸다 |
| 어디서 | 폼 그리드 안 | **필터 바 줄 안** |
| 왜 | 칸이 좁았다 | **칸을 늘려도 트리거 폭이 「전체」에 맞춰진다** |
| 어떻게 풀었나 | 칸이 자식을 늘리게 했다(3-1) | 칸에 **최소 폭**을 줬다(3-2) |

**한 번은 우연이고 두 번은 규칙이다.** 두 번 모두 「무엇을 고르는지 읽을 수 없다」는 기능 결함으로 나타났다 —
값을 고르지 못하게 만드는 결함이라 시각 문제가 아니다.

**값과 근거.** 디자인 시스템 `Select`의 선택지 목록은 `position: absolute; left: 0; right: 0`이라
**뿌리 폭에 못 박혀 있다.** 뿌리는 `display: inline-block`이고 트리거는 `width: 100%`이므로
**폭을 정하는 것은 지금 고른 값**이다. 「전체」가 골라진 상태에서 목록을 열면 목록도 그 좁은 폭이 되고,
목록은 세로 넘침만 스크롤로 처리하고 **가로는 잘라 버린다**(`text-overflow: ellipsis`).

`13rem`(208px)은 **트리거가 가장 긴 코드값을 담는 데 필요한 폭**에서 나왔다.
트리거가 목록보다 넓게 필요하므로(안쪽 여백이 더 크다) 트리거를 기준으로 잡는다.

| 조각 | 폭 | 근거 |
| --- | ---: | --- |
| 왼쪽 안쪽 여백 | 16px | `--space-4` (`Select` 기본 크기 `md`) |
| 값 글자 | 136px | 가장 긴 코드값 **13자**를 `--type-body-lg`(16px)의 대문자 자폭(약 10.5px)으로 |
| 값–화살표 간격 | 12px | `--space-2`(8) + 화살표의 `margin-left: --space-1`(4) |
| 화살표 | 20px | `Icon size={20}` |
| 오른쪽 안쪽 여백 | 16px | `--space-4` |
| **합** | **200px** | |

**합보다 8px 넓은 `13rem`(208px)을 쓴다.** `.wide-table`이 합에서 덜어 낸 것과 반대인데, 이유가 다르다 —
그쪽 합은 **여유를 둔 하한들의 합**이라 양보할 여지가 있었고, 이쪽 합은 **한 컨트롤의 빠듯한 실측**이며
그중 자폭은 글꼴 실측이 아니라 추정이다. 추정 오차를 흡수할 만큼만 더한다.

**13자의 근거**는 이 화면이 실제로 보일 수 있는 가장 긴 코드값이다(계약 예시의 `GOODS_RECEIPT`).
코드 값 목록이 확정되지 않아 **더 긴 값이 올 수 있다** — 그것이 아래 이탈 조건이다.

**구현.**

```css
.field-cell.wide-select {
  align-items: stretch;
  min-width: 13rem;
}
```

`Select`에 직접 폭을 주지 않는 이유는 3-1과 같다 — `SelectProps`가 `ButtonHTMLAttributes`를 상속해
`className`·`style`이 **트리거로** 가는데 목록은 **뿌리 기준**으로 배치되므로, 트리거만 넓혀서는 목록이 따라오지 않는다.
디자인 시스템의 해시 클래스 이름도 겨냥하지 않는다.

**이탈 조건 셋.**

1. **값이 짧은 선택칸에는 붙이지 않는다.** 붙이면 줄이 쓸데없이 일찍 넘어간다.
2. **13자보다 긴 코드값이 확정되면 위 표로 다시 도출한다.** 값을 눈대중으로 올리지 않는다.
3. **`design-system-v2-webui#62`가 반영되면 이 규범과 클래스를 함께 걷어낸다.**
   목록이 가장 긴 항목만큼 넓어지면 바깥에서 폭을 정할 이유가 사라진다 — **이것은 임시 우회다.**

## 규범 4 — 비활성 컨트롤의 사유 표시

**기준.** 사유를 보이는 것으로는 부족하다. **어느 컨트롤의 사유인지 보이게 붙인다.** 다섯 항목이다.

1. **사유는 감추지 않고 항상 보이는 DOM 텍스트로 렌더하고 `aria-describedby`로 그 컨트롤에 잇는다.**
   비활성 컨트롤은 포커스를 받지 못해 툴팁만으로는 키보드·스크린리더 사용자가 닿을 수 없다
   (디자인 시스템 `docs/patterns.md` 「읽기 전용 구획 배치」).
2. **사유는 그 컨트롤 바로 아래, 컨트롤과 왼쪽 가장자리를 맞춰 놓는다.** 규범 2의 `.field-cell`이 그 세로 묶음이다.
3. **사유 텍스트의 폭에 상한을 준다.** 사유가 줄 전체로 퍼지면 **줄 전체의 설명으로 읽힌다.**
4. **사유가 붙는 비활성 버튼은 테두리가 남는 표현을 쓴다.**
5. **문구는 그 컨트롤의 이름으로 시작한다.**

**값과 근거.**

*폭 상한 `20rem`(320px).* 폼 페인의 액션 줄 폭은 통상 창 폭에서 700~800px 대다.
사유 폭을 그 **절반 아래**로 가두면 「줄 전체」로 읽히지 않는다.
`--type-body-sm`(14px)에서 한 줄에 한글 약 22자가 들어가 두세 줄로 접힌다.

*버튼 표현.* 비활성일 때 각 variant에 남는 것은 다음과 같다.

| variant | 비활성일 때 남는 것 | 버튼으로 보이나 |
| --- | --- | --- |
| `text` | 흐린 글자색뿐. 배경·테두리 없음 | **아니오** — 라벨로 읽힌다 |
| `outlined` | `inset` 그림자 테두리가 남는다 | 예 |
| `filled` · `tonal` | 배경 채움이 남는다 | 예(다만 주 액션처럼 보인다) |

→ 사유가 붙는 비활성 보조 액션은 **`outlined`**를 쓴다. `text`는 쓰지 않는다.

*문구.* 주어가 없으면 붙은 대상이 시각적으로 끊겼을 때 복원 단서가 없다.
문형은 **「〈컨트롤 이름〉은 … 없습니다. 〈풀리는 조건〉이면 이 버튼을 쓸 수 있습니다.」**
개발·설계 쪽 표현(「규약」·「서버 렌더링」·「API」·「스키마」)과 내부 이슈 번호를 쓰지 않는다.

**구현.**

```css
.field-note {
  max-width: 20rem;
}

.form-actions {
  align-items: flex-start;
}

.form-actions-secondary {
  margin-right: auto;
}
```

액션 줄에서 보조 액션(사유가 붙은 비활성 버튼)은 줄 **왼쪽**에 두고 주 액션(취소·저장)은 오른쪽에 남긴다.
`margin-right: auto`로 그 배치를 **의도적으로** 만든다 — 폭이 넓어서 우연히 왼쪽에 놓이는 것과 다르다.
`align-items: flex-start` 덕분에 사유가 아래로 자라도 주 액션은 윗줄에 남는다.

보조 액션을 주 액션 옆에 붙이면 사유가 취소 버튼 아래로 흘러 소유가 다시 모호해진다.
보조 액션에 자기 줄을 주면 소유는 확실해지지만 비활성 버튼 하나에 한 줄을 쓴다.

**이탈 조건.**

- 여러 컨트롤이 공유하는 안내(예: 선택지가 아직 준비되지 않았다는 알림)는 컨트롤 이름 대신
  **무엇에 대한 안내인지**로 시작한다.
- 텍스트 입력(`TextField`)은 `disabledReason` prop이 이 처리를 내장하고 있으므로 직접 만들지 말고 그대로 쓴다.

## 규범 5 — 반응형 접힘 기준점

**기준.** 접힘 기준점은 **그 배치가 유지될 수 있는 최소 폭**에서 정한다. 임의의 「모바일/태블릿」 구분이 아니다.

**값과 근거.**

| 기준점 | 무엇이 접히나 | 근거 |
| --- | --- | --- |
| **1280px** | 2단 배치 → 1단 | 좌측 열 최소 폭이 320px(`minmax(320px, 2fr)`)이고 우측이 `3fr`이다. 이 아래에서는 우측 폼이 2열을 유지할 폭을 잃는다 |
| **720px** | 폼 그리드 2열 → 1열 | 한 열이 약 340px로, 텍스트 입력·선택이 값을 자르지 않고 담기는 하한이다 |

**구현.** `.two-pane`과 `.form-grid`의 `@media (max-width: …)` 블록. 값은 이미 코드에 있고,
이 문서가 채우는 것은 **그 숫자가 어디서 왔는지**다.

창 폭이 아니라 페인 폭을 기준으로 삼는 컨테이너 쿼리가 더 정확하지만, 소비 화면이 늘어나기 전에는 이득이 없다.
두 번째 화면에서 다시 판단한다.

**이탈 조건.** 다른 열 구성을 쓰는 화면은 자기 기준점을 정하고 **그 근거를 자기 화면 파일에 적는다.**
근거 없이 숫자만 두지 않는다.

## 규범 6 — 페인·다이얼로그 안의 배너 슬롯 이음매

**기준.** 규범 1이 정한 「블록 사이 이음매는 배치하는 쪽이 소유한다」가 **중첩 컨테이너 안에서 다시 나온다.**
`main > * + *`는 화면 최상위 블록에만 닿으므로, 페인이나 다이얼로그 **안**에 놓인 배너는
바로 아래 블록(폼·표·목록)과 붙어 버린다. 알림 상자와 그 아래 내용이 붙으면 알림이 그 내용의 머리말로 읽힌다.

이음매를 아래 블록마다 붙이면 규범 1이 겪은 「잊음」이 그대로 되풀이된다. 그래서 **배너 쪽이 자기 아래 이음매를 갖는다.**
배너는 조건부로만 렌더되므로 이 방향이면 배너가 없을 때 빈 간격도 남지 않는다.

**값과 근거.** `--space-5`(20px). 규범 1과 같은 값·같은 근거다 —
블록 사이 간격은 **그 블록의 내부 최대 간격보다 커야 블록 경계가 읽힌다.**
이 자리에서 배너와 이웃하는 블록의 내부 최대 간격은 `.pane`의 안쪽 여백 16px과 `.form-grid`의 `gap` 16px이므로 20px이 그보다 크다.
규범 1과 다른 값을 쓰면 같은 화면 안에서 두 종류의 블록 리듬이 생긴다.

**구현.**

```css
.banner-slot {
  margin-bottom: var(--space-5);
}
```

배너를 담는 요소에 붙인다. 공통 저장 실패 배너(`patterns/master`의 `SaveErrorBanner`)는 이 래퍼를 **스스로** 렌더하므로
소비하는 화면이 붙일 것을 잊을 수 없다. 화면이 직접 배치하는 배너(조회 실패 등)는 화면이 이 클래스를 붙인다.

`margin-top`이 아니라 `margin-bottom`인 이유는 배너가 슬롯의 **첫 블록**이기 때문이다.
`margin-top`으로 두면 배너가 컨테이너 맨 위에 있을 때 컨테이너 안쪽 여백에 이음매가 덧붙는다.

**이탈 조건.** 배너 아래에 블록이 없는 자리(배너가 컨테이너의 마지막 요소인 경우)에는 이 클래스를 붙이지 않는다.
붙이면 컨테이너 안쪽 여백에 이음매가 덧붙어 아래쪽만 넓어진다.

**슬롯이 하는 일이 하나 더 있다 — DS 배너의 `box-sizing` 정규화(임시).**
DS `AlertBanner` 루트가 `width: 100%` + 안쪽 여백인데 `box-sizing` 선언이 없고 어디에도 전역 리셋이 없어,
감싸지 않으면 배너가 담는 컨테이너를 안쪽 여백만큼(32px) 넘쳐 페인 테두리 밖으로 삐져나온다.
`.banner-slot > * { box-sizing: border-box }`가 슬롯 안에서만 이것을 바로잡는다 —
전역 리셋은 이미 병합된 화면들의 배치를 통째로 흔들기 때문에 쓰지 않는다.
그래서 **화면 최상위 배너처럼 이음매가 필요 없는 자리에도 슬롯으로 감싼다.**
DS 이슈 `design-system-v2-webui#60`이 반영되면 이 문단과 CSS 한 줄을 함께 걷어낸다.

## 규범 7 — 한국어 줄바꿈

**기준.** 한국어 문장은 **어절 경계에서만 끊는다.** 이음매를 한 곳에서 한 번만 정의한 규범 1과 같은 형태의 결정이다 —
줄바꿈 규칙을 문구가 나오는 클래스마다 붙이면 반드시 하나를 빠뜨린다. **문서 뿌리에서 한 번 정의하고 상속시킨다.**

브라우저 기본값(`word-break: normal`)은 한글을 음절 단위로 끊을 수 있는 문자로 다뤄
**어절 중간에서 줄을 바꾼다.** 실제로 화면에 이렇게 나왔다 — 「다른 공장이면 **창/고를** 새로 등록하세요」 ·
「하나만 선택했을 때 쓸 수 **있습/니다**」 · 「이 **항목에/서** 고를 수 있습니다」.
읽는 사람이 낱말을 다시 맞춰야 하므로 **문구를 아무리 다듬어도 읽히지 않는다.**

**값과 근거.** `word-break: keep-all` + `overflow-wrap: break-word`. 둘 다 상속되는 속성이라 뿌리에 한 번 두면 전체에 닿는다.

| 선언 | 하는 일 | 왜 함께 두나 |
| --- | --- | --- |
| `word-break: keep-all` | 한국어·중국어·일본어를 어절 경계에서만 끊는다. 라틴 문자에는 영향이 없다(`normal`과 같다) | 이것만 두면 **칸보다 긴 낱말 하나가 칸을 넘쳐흐른다** — 코드·식별자에서 실제로 생긴다 |
| `overflow-wrap: break-word` | 한 낱말이 줄에 들어가지 않을 때**만** 그 낱말을 끊는다 | 넘침을 막는 최후 수단. 평소에는 발동하지 않아 `keep-all`의 결과를 바꾸지 않는다 |

`word-break: break-all`은 쓰지 않는다 — 그것이 지금의 결함을 만드는 값이다.

**구현.**

```css
body {
  word-break: keep-all;
  overflow-wrap: break-word;
}
```

`main`이 아니라 `body`에 두는 이유는 **다이얼로그와 토스트가 `main` 밖에 놓이기 때문이다.**
`main`에 두면 그 둘만 규칙에서 빠져 같은 결함이 남는다.

**이탈 조건.** 낱말 중간에서라도 반드시 칸 안에 넣어야 하는 자리(폭이 고정된 표 셀의 긴 코드 등)는
그 요소에 `word-break: break-all`을 직접 준다. 뿌리 값을 바꾸지 않는다.

| `.field-cell.wide-select` | 값이 긴 코드를 고르는 선택칸에 **최소 폭 `13rem`**을 준다. **옵트인**이며 붙인 칸만 넓어진다. 디자인 시스템 선택지 목록이 트리거 폭에 갇혀 잘리는 것의 **임시 우회**(design-system-v2-webui#62) | 3-2 |
| `.check-group` | 한 칸에 나란히 놓은 확인칸 사이 간격 `--space-2` | — |
| `body` | 한국어를 어절 경계에서만 끊는다(`word-break: keep-all` · `overflow-wrap: break-word`) | 7 |

### 아직 규범으로 올리지 않은 것 — 열이 많은 표의 가로 넘침 (`.wide-table`)

**무엇이 문제였나.** 좁은 칸에 8열짜리 표를 넣었더니 표가 폭에 맞춰 줄어들며 셀 내용이 낱말 단위로
쪼개졌다 — 한 셀이 네 줄이 되어 행 높이가 네 배가 되고 머리글도 두 줄로 접혔다.
브라우저 확인에서 실제로 「표를 읽을 수 없다」로 보고된 자리다.

**어떻게 다뤘나.** 표에 최소 폭을 주고 머리글의 줄바꿈을 막아, 폭이 모자라면 **짓누르는 대신 넘치게** 했다.
디자인 시스템 `Table`이 자기 표를 `overflow-x: auto` 상자로 이미 감싸고 있으므로 넘침이 곧 가로 스크롤이 된다.
**우리가 스크롤 상자를 만들지 않고, 디자인 시스템의 해시 클래스 이름도 겨냥하지 않는다** — 그 이름은 버전이 바뀌면 조용히 어긋난다.

**최소 폭 `58rem`(928px)의 근거.** 열마다 「짓눌리지 않는 하한」을 잡아 더하고, 그 합에서 조금 덜어 낸 값이다.

| 열 | 폭 | 근거 |
| --- | ---: | --- |
| 순서 | 64px | 두 자리 수 + 여백. 이미 `Column.width`로 지정돼 있다 |
| 공정 | 112px | 공정명 한 낱말 |
| 공정명 | 144px | 한글 8자 안팎 |
| 관리 항목 | 200px | 「MES 관리 · 실적 관리」가 한 줄에 들어가는 폭. 이 열이 가장 길다 |
| 표준 C/T(초) | 112px | **머리글**이 한 줄에 들어가는 폭(9자 × `--type-body-sm` 14px) |
| 표준 수율(0~1) | 120px | 머리글 11자 |
| 편집 | 96px | `sm` 아이콘 버튼 2개 |
| 순서 이동 | 96px | 디자인 시스템이 붙이는 열. `sm` 아이콘 버튼 2개 |
| **합** | **944px** | 그대로 쓰면 `59rem`이다 |

**합계보다 16px 작은 `58rem`(928px)을 쓴다.** 944 − 928 = **16px**이며, 그 16px은
**폭을 지정하지 않은 유일한 열인 관리 항목이 흡수한다**(200px → 184px).

합계를 그대로 최소 폭으로 삼지 않는 이유는, 이 합이 **각 열에 여유를 둔 하한들의 합**이기 때문이다.
하한을 그대로 최소 폭으로 삼으면 「어느 열도 1px도 양보하지 않는다」는 뜻이 되어
**최소 폭이 필요 이상으로 커지고 스크롤이 그만큼 일찍 생긴다.**
양보를 받을 열은 관리 항목이 맞다 — 여러 값을 이어 담는 칸이라 원래 접히는 것이 정상이고,
184px에서도 이 열이 지키려던 「`MES 관리 · 실적 관리`가 한 줄에 들어간다」가 유지된다
(`--type-body-sm` 14px에서 그 문구는 셀 안쪽 여백을 포함해 약 180px이다).

머리글에만 `white-space: nowrap`을 준다. 본문 셀은 그대로 접힌다 — 위와 같은 이유이며,
본문까지 막으면 표가 끝없이 넓어진다.

**왜 규범으로 올리지 않았나.** 이 문서의 갱신 규칙이 「**두 번째 화면에서 같은 결정을 또 하게 될 때** 규범을 추가한다」로
정해 놓았고, 열이 많은 표는 지금 W-06-01 하나뿐이다. 화면 한 장에서 뽑은 값(특히 `58rem`)은 그 화면의 열 구성에
과적합할 위험이 크다. `.three-pane`을 다뤘던 것과 같은 처리다 — **클래스 목록에만 올리고 근거는 여기 남긴다.**

**두 번째 사용처(W-06-02·03이 유력)가 생기면 규범으로 올린다.** 그때 정할 것은 둘이다.
① 최소 폭을 화면마다 정할지 공통 값으로 둘지 ② 창 폭이 아니라 페인 폭을 기준으로 하는 컨테이너 쿼리로 옮길지(규범 5의 유보와 같은 갈래).

#### 두 번째 사용처가 생겼다 — W-06-10 (2026-08-06)

**W-06-02·03이 아니라 W-06-10(연계 동기화 현황)이었다.** W-06-03은 열이 3~4개라 이 문제를 만나지 않았고,
로그성 조회 화면이 먼저 열이 많은 표를 필요로 했다.

**두 번째 화면은 `app.css`의 값을 바꾸지 않고 그대로 소비했다.** 지정 폭의 합이 최소 폭 안에 들어가도록
**열 구성을 먼저 맞췄기** 때문이다 — 계약의 `IntegrationMessage`에는 필드가 14개 있으나 목록에는 일곱만 두고
나머지는 상세로 보냈다.

| 열 | 폭 | 근거 |
| --- | ---: | --- |
| 선택 | 디자인 시스템 고정 | `Table selectable`이 렌더한다 |
| 메시지 키 | 176px | 상세를 여는 텍스트 버튼 |
| 연계 종류 | 128px | 코드 한 낱말 |
| 상태 | 160px | 상태 칩 + 보조 한 줄 |
| 시도 | 64px | 두 자리 수 + 여백 |
| 생성 | 148px | `YYYY-MM-DD HH:MM` 16자 |
| 마지막 오류 | **미지정** | 남는 폭을 흡수한다 |
| 재처리 | 88px | `sm` 버튼 하나 |
| **지정 폭 합** | **764px** | `58rem`(928px) 안에 들어간다 |

##### 예고했던 두 질문의 답

**① 최소 폭은 공통 값을 하한으로 두고, 화면이 `Column.width` 합으로 자기 하한을 만든다.**
값을 화면마다 늘리지 않는다. 두 소비 화면이 실제로 그렇게 했다 — W-06-01은 944px 하한에서 16px을 덜어 냈고,
W-06-10은 764px로 여유를 남겼다. **공통 값이 「어느 화면에서도 짓눌리지 않는 바닥」이고, 그보다 넓게 필요하면
열을 줄이는 것이 먼저다.** 값을 올리면 그 화면 하나 때문에 다른 화면의 스크롤이 일찍 생긴다.

**② 컨테이너 쿼리로 옮기지 않는다.** 소비 화면이 둘뿐이고 **둘 다 표가 놓인 칸이 충분히 넓다** —
W-06-01은 3단 배치의 가장 넓은 칸, W-06-10은 전체 폭이다. 좁은 페인에 열이 많은 표를 넣는 화면이 생기면
그때 다시 본다. 지금 옮기면 근거 없는 일반화가 된다.

##### 그래도 규범으로 올리지 않는다

이 문서의 등재 조건은 「**기준 · 값과 근거 · 구현 · 이탈 조건** 네 항목이 다 차는가」다.
앞의 셋은 위에서 찼으나 **이탈 조건이 아직 비어 있다** — 「최소 폭을 넘겨야 하는 화면은 어떤 화면인가」에
답할 사례가 없다. 두 화면 모두 열을 줄여 하한 안에 들어갔을 뿐, 넘길 수밖에 없는 경우를 만나지 않았다.

**클래스 목록에는 이미 올라 있고, 위 두 답이 다음 소비 화면의 판단 기준이 된다.**
세 번째 화면이 하한을 넘겨야 하면 그것이 곧 이탈 조건이고, 그때 규범으로 등재한다.

표에는 일곱만 두고 나머지는 편집 창으로 보냈다 — 값을 바꾸지 않고 **열 구성을 먼저 맞춘** 두 번째 사례다.

세 번째 화면도 하한을 넘기지 않았다(752px < 928px). 「최소 폭을 넘겨야 하는 화면은 어떤 화면인가」에
답할 사례가 여전히 없으므로 **네 항목 중 이탈 조건이 비어 있고, 규범으로 등재하지 않는다.**

다만 **세 화면의 지정 폭 합이 944 · 764 · 752px으로 모이는 것**은 그 자체가 관찰이다 —
열이 많은 표는 8열 안팎에서 멈추고 남는 폭을 흡수하는 열을 하나 둔다는 형태가 세 번 되풀이됐다.
등재는 이탈 사례가 나올 때 하되, **「열을 줄이는 것이 먼저다」는 판단은 이제 세 화면의 실측을 근거로 갖는다.**

#### 네 번째·다섯 번째 사용처 — W-06-06 (2026-08-07)

**한 화면이 두 자리에 썼다.** 공통코드 탭의 코드값 표와 작업자 탭의 자격·인증 표다.
둘 다 **좁은 칸이 아니라 2단 배치의 넓은 우 칸**에 있으나, 열 넷·여섯이 좁아지는 것을
막을 근거가 필요해 같은 클래스를 소비했다.

**다섯 화면이 모두 하한 안에 들어갔다**(944 · 764 · 752 · 456 · 692px).

등재 조건 네 항목 중 **이탈 조건이 비어 있고, 규범으로 등재하지 않는다.**

다만 앞선 관찰이 한 번 더 확인됐다 — **남는 폭을 흡수하는 열을 하나 둔다**는 형태가
다섯 화면 중 넷에서 되풀이됐고, 이번 두 표는 그 열을 **가장 긴 이름 칸**(코드명·자격 유형)에
두었다. 폭을 지정하지 않을 열을 고르는 기준이 「값이 길고 접혀도 읽히는 칸」으로 모인다.

**계획이 예상한 값과 다른 자리가 하나 있다.** 계획 결정 11은 자격 표의 지정 폭 합을 832px로

값 목록이 미정이라(§8-5) 자격 유형에 어떤 길이의 문구가 들어올지 아직 모르는데
좁은 고정 폭을 주면 확정된 뒤에 그 열부터 짓눌린다.

#### 여섯~열 번째 사용처 — W-06-05 (2026-08-07)

자재 명세서 탭의 표 둘(헤더 목록·구성품)이다. 다섯 모두 2단 배치의 넓은 우 칸에 있고,
그중 **구성품 표가 이 문서를 통틀어 최소 폭에 가장 가까이 갔다.**

| 표 | 흡수 열 | 지정 폭 합 | 흡수 열 하한 | 합 |
| --- | --- | ---: | ---: | ---: |
| 사업부 매핑(5열) | 대상 품목 | 576px | — | 576px |
| 단위 환산(5열) | **없다** | 656px | — | 656px |
| 외부 코드(4열) | 거래처 | 456px | — | 456px |
| 자재 명세서 헤더(6열) | BOM 코드 | 672px | — | 672px |

##### 흡수 열에도 예산을 준다 — W-06-01이 쓴 방법을 되살렸다

앞의 넷은 지정 폭 합이 넉넉히 작아 흡수 열이 저절로 넓다. **구성품 표는 아니었다.**

계약의 구성품 한 행에는 필드가 열둘이라 그대로 펴면 지정 폭 합만으로 최소 폭을 넘긴다.
열을 줄여 여덟으로 맞췄으나(소요량·단위를 한 칸에, 등록·실사용 공정을 한 칸에,
확장 표시 둘을 한 칸에), 그래도 **지정 폭 합만 보고 「928px 안에 들어간다」로 판단하면
흡수 열이 몇십 px밖에 못 받는 상태를 통과시킨다.**

그래서 W-06-01이 쓴 방법을 그대로 되살렸다 — **흡수 열에도 하한을 예산으로 잡고
그 합으로 최소 폭을 맞춘다.** 「구성품」 칸은 「코드 · 이름」이라 200px 아래로 내려가면
접히다 못해 읽히지 않는다. 724 + 200 = 924px로 `58rem`(928px) 안에 들어간다.

**앞선 다섯 화면의 기록도 같은 방법이었다** — W-06-01의 「합 944px」은 흡수 열(관리 항목)의
200px을 **포함한** 값이다. 그 뒤 네 화면이 「지정 폭 합」만 적은 것은 여유가 커서
따질 필요가 없었기 때문이지 방법이 달라서가 아니다. 여섯 번째부터 그 사실이 드러났으므로
이 표는 두 값을 나눠 적는다.

##### 이탈 조건은 열 번째에서도 비어 있다

**열 자리가 모두 하한 안에 들어갔다.** 구성품 표가 928px에 4px까지 붙었으나 넘지 않았고,
넘기지 않은 방법도 앞의 다섯과 같은 「**열을 줄이는 것이 먼저다**」였다 —
`app.css`의 값을 바꾸지 않았다.

「최소 폭을 넘겨야 하는 화면은 어떤 화면인가」에 답할 사례가 여전히 없으므로
등재 조건 네 항목 중 **이탈 조건이 비어 있고, 규범으로 등재하지 않는다.**

다만 다음 화면을 위해 **이탈에 가장 가까웠던 조건**을 남긴다 —
「한 행의 필드가 열 개를 넘고, 그중 값이 긴 이름 칸이 둘 이상인 표」다.
구성품 표는 이름 칸이 하나(구성품)뿐이라 합칠 여지가 있었다.
둘이었다면 열을 줄여도 흡수 열이 200px을 받지 못했을 것이고, 그때가 이탈 사례다.

**계획이 예상한 값과 다른 자리가 둘 있다.** 계획 결정 11은 구성품 표를 아홉 열(지정 폭 합
896px)로, 자재 명세서 헤더 표를 여섯 열 전부 폭 지정(736px)으로 잡았다.
실제로는 ① 구성품에서 소요량과 단위를 한 칸에 합쳐 여덟 열로 줄이고 편집 열을 64px로
낮췄으며(구성품에는 추가·삭제가 없어 아이콘이 하나다) ② 헤더 표의 BOM 코드를 흡수 열로
돌리고 기본 지정 열을 200px로 넓혔다 — 그 칸에 **사유가 붙는 비활성 액션**이 들어가므로
규범 4-3이 요구하는 「사유 텍스트 폭의 상한」을 이 칸이 준다.

#### 열한 번째 사용처 — W-06-11 (2026-08-07)

**두 번째 조회 형 화면이고, 흡수 열에 예산을 준 두 번째 표다.**
계약의 변경 이력 한 행에는 필드가 열 개 있으나 목록에는 일곱만 두고 나머지는 변경 내용 창으로 보냈다 —
값을 바꾸지 않고 **열 구성을 먼저 맞춘** 여섯 번째 사례다.

##### 흡수 열 예산을 두 번째로 적용했다

W-06-05의 구성품 표에서 되살린 「**흡수 열에도 하한을 예산으로 잡는다**」를 그대로 적용했다.
지정 폭 합만 보면 708px이라 넉넉해 보이지만, 그 방식은 흡수 열이 몇십 px밖에 못 받는 상태를 통과시킨다.

**이 표의 흡수 열은 앞선 열 자리와 성격이 다르다.** 지금까지의 흡수 열은 「값이 길고 접혀도 읽히는
**이름 칸**」이었는데(관리 항목·마지막 오류·코드명·자격 유형·구성품), 이 표의 흡수 열은
**서버가 준 키 이름을 그대로 이어 담는 칸**이다. 화면이 그 값의 길이도 개수도 모른다 —
계약이 키 구조를 정하지 않았다. 그래서 예산을 「키 이름 둘」이라는 **가장 흔한 최소치**로 잡고
그보다 많으면 접히게 두었다. 폭을 지정해 자르면 어떤 항목이 바뀌었는지가 통째로 가려진다.

##### 이탈 조건은 열한 번째에서도 비어 있다

**열한 자리가 모두 하한 안에 들어갔다**(944 · 764 · 752 · 456 · 692 · 576 · 656 · 456 · 672 · 924 · 888px).
「최소 폭을 넘겨야 하는 화면은 어떤 화면인가」에 답할 사례가 여전히 없으므로
등재 조건 네 항목 중 **이탈 조건이 비어 있고, 규범으로 등재하지 않는다.**

W-06-05가 남긴 「이탈에 가장 가까운 조건」(한 행의 필드가 열 개를 넘고 값이 긴 이름 칸이 둘 이상)에
이 표는 걸리지 않는다 — 필드가 정확히 열 개이고 이름 칸이 하나다.

## 갱신 규칙

- **두 번째 화면에서 같은 결정을 또 하게 될 때 규범을 추가한다.** 화면 한 장에서 전반 규범을 뽑으면 과적합한다.
- 규범을 추가할 때는 **기준 · 값과 근거 · 구현 · 이탈 조건** 네 항목을 모두 채운다. 하나라도 비면 등재하지 않은 것과 같다.
- 값을 바꿀 때는 이 문서를 먼저 고치고 `app.css`를 맞춘다. 구현이 아니라 규범이 정본이다.
- 이 문서는 공개 저장소에 있다. 고객사 식별 정보·실 운영 값·인프라 정보·비공개 문서 본문·화면 캡처를 넣지 않는다.
  가능한 한 **컴포넌트의 언어**로 쓴다.
