# 설계 → 프론트 착수 규칙

설계(UI/UX)와 프론트 개발은 서로 다른 저장소에서 일한다. 설계가 아직 진행 중이므로 프론트는 **준비된 화면부터 하나씩** 처리한다. 이 문서는 「어떤 화면을 지금 시작해도 되는가」를 **설계가 프론트에게 알려 주는 방법**을 정한다.

읽는 사람은 두 팀 모두다. 설계팀이 처음 읽어도 되도록 내부 약어는 처음 나올 때 풀어 쓴다.

| 용어 | 뜻 |
| --- | --- |
| 설계 저장소 | UI/UX 화면 스펙과 API 계약 정본이 있는 **비공개** 저장소 (`omf-mes`) |
| 이 저장소 | 클라이언트 구현 저장소 (`omf-mes-client`) — **공개(public)** |
| 계약 정본 | 서버와 클라이언트가 주고받을 형태를 정한 OpenAPI 문서. 설계 저장소가 정본이며 이 저장소로 복사하지 않는다 |
| 공유계약 | 화면을 가로지르는 공통 규약(오류 표시·낙관적 잠금·페이지네이션 등) 문서 |
| 디자인 시스템(DS) | 공용 UI 컴포넌트 묶음 `@crefle/web-ui`. 별도 **공개** 저장소이며 커밋 해시로 고정해 쓴다 |
| 화면 ID | `W-06-03`처럼 화면을 가리키는 내부 식별자. 관리웹은 `W-`, 현장 단말은 `P-` 접두 |

---

## 1. 왜 이 규칙이 있는가

전에는 프론트가 설계 산출물을 직접 뒤져 「이제 이 화면을 해도 되나」를 스스로 판단했다. 그 방식이 실제로 깨진 사례가 짧은 기간에 세 건 나왔다. **문제의 뿌리는 하나다 — 문서는 전달한 순간 고정되지만, 계약·디자인 시스템·이슈는 그 뒤로도 계속 움직인다.**

세 사례 모두 설계팀의 실수가 아니다. **작성 시점에는 맞았던 서술이 읽는 시점에는 틀려 있었다.** 사람을 바꿔서 풀 문제가 아니라 전달 형식을 바꿔서 풀 문제다.

### 사례 1 — 문서가 「없다」고 한 것이 이미 있었다

설계 문서가 **행 순서 재배치** 컴포넌트를 두고 「디자인 시스템에 없으니 제품이 만들어야 한다」고 적었고 추적 이슈 번호(DS `#39`)까지 달려 있었다. 프론트가 실제로 확인해 보니 **그 기능은 우리가 고정해 쓰는 DS 커밋의 설치본에 이미 들어 있었고, `#39`도 이미 CLOSED였다.**

문서가 쓰인 뒤 DS가 앞서 나간 것이다. 문서를 그대로 믿었다면 **네 개 화면이 함께 쓸 부품을 중복으로 새로 만들** 뻔했다.

같은 확인에서 **반대 방향의 함정**도 나왔다. 날짜 입력(DS `#40`)은 이슈가 CLOSED지만 그 구현이 **우리가 고정한 커밋보다 뒤에** 들어와 있어, 대체 부품이 여전히 필요했다.

> **이슈가 닫힌 것과 우리가 쓰는 커밋에 들어 있는 것은 서로 다른 사실이다.** 어느 쪽으로도 틀릴 수 있다.

> **그래서** — 근거에는 문서 이름만이 아니라 **무엇을 언제 확인했는지**를 함께 적는다. 특히 DS는 「이슈가 닫혔다」가 아니라 **고정한 커밋의 설치본에서 실물을 확인한 시점**을 적는다.

### 사례 2 — 스펙 서술과 계약이 어긋났다

화면 스펙의 서술 두 곳이 계약 정본과 달랐다.

- 스펙은 어떤 요청에 낙관적 잠금 헤더(`If-Match`)가 필요 없다고 읽혔으나, 계약에서는 **그 요청에도 필수**였다
- 스펙은 특정 충돌 응답(409)의 원인이 **「미확정」**이라고 읽혔으나, 계약에서는 **원인이 세 값으로 이미 확정**돼 있었다

프론트가 스펙만 보고 구현했다면 요청이 실패하거나, 이미 확정된 분기를 「미정」으로 두고 넘어갔을 것이다.

> **그래서** — 스펙과 계약이 어긋나는 지점을 아는 사람이 **「특별히 조심할 것」에 미리 적는다.** 어긋남은 대개 이미 알려져 있고, 모르는 쪽은 나중에 그 자리에 도착하는 프론트다.

### 사례 3 — 예시인지 확정인지 알 수 없어 프론트가 혼자 정했다

어떤 화면의 상태 코드가 스펙에 **딱 한 값만** 적혀 있었다. 그것이 「가능한 값 전부」인지 「예시 하나」인지 판별할 근거가 문서에 없었다.

프론트는 물어보지 않고 **「인식하지 못한 값은 작성중으로 취급한다」는 규칙을 혼자 만들어** 구현했다. 그 판단은 설계가 승인한 적이 없고, 틀렸다면 화면에 잘못된 상태가 표시된 채 굳었을 것이다.

> **그래서** — **미결 항목과 그 처리 방법을 설계가 지정한다.** 미결을 없앨 필요는 없다. 미결인 채로 **어떻게 다루라는 것인지**만 정해 주면 된다. 그 칸이 비면 프론트가 반드시 혼자 정하게 된다.

### 이 규칙이 실제로 해결하는 것

「언제 시작하나」만이 아니다. **무엇이 확정이고, 무엇이 미결이며, 미결인 채로 어떻게 처리하라는 것인가 — 이 셋을 확인 시점이 박힌 형태로 받는 것**이다.

## 2. 공개 저장소 경계 — 가장 먼저 지킬 것

**`omf-mes-client`는 공개(public) 저장소다.** 설계 저장소는 비공개지만 여기는 아니다. 습관대로 스펙 본문이나 와이어프레임을 이슈에 붙이면 **붙인 순간 사고다.**

이슈의 **제목 · 본문 · 첨부 · 라벨 · 수정 이력**이 전부 함께 공개된다. 나중에 지워도 인덱싱된 사본과 포크는 회수되지 않는다.

| ✅ 적어도 되는 것 | ⛔ 적으면 안 되는 것 |
| --- | --- |
| 화면 ID(`W-06-03`) · 화면 이름 · 라우트 · 컴포넌트명 | 설계·기획 문서의 **본문 복사 · 발췌 · 요약** |
| 설계 저장소 이슈 번호 (`omf-mes#42`) | **이미지** — 와이어프레임 · 화면 캡처 · 워크플로우 도식 |
| 문서의 **경로와 개정일** 같은 포인터 | 고객사명 · 공장/사업장 위치 · 담당자 실명 · 조직도 |
| MES 일반 업무 용어 (자재LOT · 작업지시 · 특채 승인) | 실 사번 · 품목코드 · LOT 번호 · 거래처 코드 → **합성값을 쓴다** |
| 직접 지어낸 합성 예시값 | 금액 · 수량 · 단가 · 납기 등 계약·견적 정보 |
| 계약 정본의 **오퍼레이션 존재 여부**(있다/없다) | 인프라 정보 — IP · 호스트명 · 포트 · 계정 · 접속 문자열 |

**내용은 옮기지 말고 번호로 참조한다.**

```
✅ 근거: omf-mes#42
⛔ 근거: "○○공장 3라인의 특채 승인은 …" (스펙 본문 복사)
```

경로와 개정일을 적는 것은 **포인터**이므로 허용한다 — 이 저장소는 이미 계약 정본의 경로를 코드와 문서에서 참조하고 있다. 허용되는 것은 **어디에 있는지**까지이며, **거기에 뭐라고 쓰여 있는지**는 아니다.

### 판단이 서지 않으면

**올리지 말고 먼저 묻는다.** 이미 올렸다면 **즉시 알린다.** 이슈를 조용히 지우거나 수정해 덮지 않는다 — 공개 저장소에서는 올라간 순간 노출된 것으로 보고 대응해야 하고, 조용한 삭제는 대응 시점만 늦춘다.

## 3. 세 가지 채널

설계와 프론트 사이에는 방향과 목적이 다른 세 종류의 통지가 있다. **접두어로 구분한다.**

| 채널 | 방향 | 어디에 올리나 | 제목 접두 | 언제 |
| --- | --- | --- | --- | --- |
| **착수 가능** | 설계 → 프론트 | 이 저장소 (공개) | `[uiux→client] 착수 가능 —` | 화면 하나를 지금 시작해도 될 때 |
| **변경 통지 ⛔/⚠** | 설계 → 프론트 | 이 저장소 (공개) | `[uiux→client]` + ⛔ 또는 ⚠ | 이미 전달한 설계가 바뀌었을 때 |
| **질문** | 프론트 → 설계 | 설계 저장소 (비공개) | `[client→uiux]` | 스펙·계약이 불명확하거나 서로 어긋날 때 |

**변경 통지의 두 등급**은 기존 규약을 그대로 쓴다.

- **⛔** — **이미 만든 것이 틀린다.** 고치지 않으면 잘못 동작한다. 프론트가 진행 중인 작업보다 먼저 본다
- **⚠** — **새로 만들 것이 생긴다.** 이미 만든 것은 유효하다. 다음 작업 순서에 넣는다

질문은 **설계 저장소(비공개)로 간다.** 질문에는 스펙 본문을 인용해야 할 때가 많은데, 그것을 공개 저장소에서 하면 안 되기 때문이다. 이 방향만 비공개 저장소를 쓰는 이유가 그것이다.

> 「착수 가능」은 설계 저장소의 착수 안내가 이미 정한 역방향 통지 규약에 **세 번째 종류로 더해지는 것**이다. 그쪽 문서에도 같은 내용이 반영돼야 규칙이 양쪽에서 완결된다 — 비공개 저장소 소관이라 이 문서가 대신 고칠 수 없다.

## 4. 착수 가능 이슈 쓰는 법

이슈 폼이 준비돼 있다. **Issues → New issue → 「착수 가능 통지 (설계 → 프론트)」**를 고르면 아래 항목이 그대로 뜬다.

- 제목: `[uiux→client] 착수 가능 — ` 뒤에 화면 ID와 이름을 이어 쓴다
- 라벨: `uiux→client`, `ready` (폼이 자동으로 붙인다)

> **아래 두 가지는 프론트 쪽 준비 사항이다 — 설계팀이 할 일은 없다.** ① 라벨 `uiux→client`·`ready`를 저장소에 미리 만들어 둔다. GitHub는 **없는 라벨을 조용히 무시**해서, 만들어 두지 않으면 라벨이 붙지 않은 채 이슈만 열린다. ② 이슈 폼은 **기본 브랜치(`main`)에서만 읽히므로**, 폼이 병합되기 전에는 New issue 목록에 나타나지 않는다. 둘 다 프론트가 처리하며, 끝나면 설계팀은 폼을 고르기만 하면 된다.

### 본문 6항목

| # | 항목 | 필수 | 무엇을 적나 |
| :-: | --- | :-: | --- |
| 1 | **화면 ID · 이름 · 리소스 패턴** | ✅ | `W-06-03 · 코드값 관리`. 패턴은 마스터 형 / 버전 마스터 형 / 조회 형 / 입력 형 중 하나 — 프론트가 재사용할 화면 골격이 갈린다 |
| 2 | **근거** · **확인 시점** | ✅ | 화면 스펙 경로와 개정일 · 계약 정본 버전 · 공유계약 버전 · DS 확인 대상. **확인 시점은 별도 칸**이며 날짜를 적는다 |
| 3 | **확정된 것** | — | 필드 목록 · 검증 규칙 · 예외 표시 · 화면 전이 · 엔드포인트 존재를 체크. 체크 안 한 것은 4번으로 |
| 4 | **미결 항목** | ✅ | 표로 — 항목 / 왜 미결 / **이번에 어떻게 처리** / 추적 번호. 없으면 `없음` |
| 5 | **선행·순서** | ✅ | 먼저 끝나야 하는 화면·공용 부품, 재작업 위험 |
| 6 | **특별히 조심할 것** | — | 스펙과 계약이 어긋나는 지점, 실서버와 계약이 다른 지점 |

**2번의 확인 시점은 근거와 나눠 별도 칸으로 받는다.** 근거 칸 안에 산문으로 섞이면 「스펙 확인함」 한 줄로도 넘어가 버려 정작 시점이 남지 않는다. 날짜 칸이 따로 있으면 반드시 남고, 나중에 기계로도 읽을 수 있다. 이 규칙이 지키려는 것이 바로 **시점이 박힌 판단**이므로 가장 약하게 걸려 있으면 안 되는 항목이다.

### 4번이 이 폼의 핵심이다

미결이 있어도 착수할 수 있다. **미결을 없애야 착수 가능한 것이 아니다.** 다만 미결인 채로 **어떻게 다룰지**는 설계가 정해 줘야 한다. 이 칸이 비면 프론트가 반드시 혼자 정하게 되고, 그게 실제로 벌어진 사고다(§1 사례 3).

처리 방법은 셋 중 하나로 적는다.

| 처리 방법 | 뜻 | 언제 |
| --- | --- | --- |
| **만들지 않는다** | 해당 UI를 이번 범위에서 뺀다 | 나중에 붙여도 화면 구조가 흔들리지 않을 때 |
| **자리표시 상수 + 안내** | 값을 프론트 상수 한 곳에 모으고 화면에 임시임을 알린다 | 모양은 확정이고 값만 미정일 때 |
| **비활성 + 사유 표시** | 요소는 두되 비활성화하고 왜 못 쓰는지 보여 준다 | 자리는 확정인데 동작 규칙이 미정일 때 |

작성 예 (값은 전부 합성이다):

```
| 항목 | 왜 미결 | 이번에 어떻게 처리 | 추적 번호 |
| --- | --- | --- | --- |
| 코드 그룹 선택지 | 코드값 목록이 확정 전 | 자리표시 상수 + 안내 — 프론트 상수 한 곳에 모으고 「임시 목록」 표시 | omf-mes#64 |
| 첨부 미리보기 | 저장 방식 미정 | 만들지 않는다 — 파일명만 표시 | omf-mes#71 |
| 승인 반려 버튼 | 권한 규칙 미정 | 비활성 + 사유 표시 — 「권한 규칙 확정 후 활성」 | omf-mes#72 |
```

**추적 번호는 설계 저장소의 이슈 번호(`omf-mes#64`)를 적는다.** 번호만 적고 그 이슈의 내용은 옮기지 않는다.

## 5. 운영 규칙

1. **한 이슈 = 한 화면.** 화면이 여러 개면 이슈를 나눈다. 화면마다 착수 시점·미결·선행이 다르기 때문이다.
2. **이슈가 없으면 프론트는 착수하지 않는다.** 스펙이 있어 보여도 마찬가지다. 착수 신호는 이슈이지 문서의 존재가 아니다.
   - **소급 적용하지 않는다.** 예외는 `W-06-07` · `W-06-01` · `W-06-03` · `W-06-10` **네 화면뿐**이다. 이 규칙을 세우기 전에 **이미 착수 지시를 받은 범위**라 착수 이슈를 기다리지 않고 진행한다. 넷 중 일부는 아직 구현 전이지만, 착수 여부와 순서가 이미 정해져 있다는 점은 같다.
   - **그 밖의 모든 화면은 착수 가능 이슈가 있어야 착수한다.** 예외는 이 넷으로 끝이며 늘어나지 않는다.
   - **발행 측에서 보면 넷의 처리가 같지 않다.** 소급 예외는 「프론트가 착수 이슈를 기다리지 않는다」는 뜻이지 「설계가 넷을 모두 발행한다」는 뜻이 아니다. `W-06-07` · `W-06-01`은 **구현이 끝나 병합됐으므로 착수 이슈를 발행하지 않는다.** 전할 것이 있으면 **⛔/⚠ 변경 통지**로 보낸다 — 이미 만든 것에 영향을 주는 정보라 그쪽이 성격에 맞고, 「착수 가능」으로 오면 이미 끝난 화면이라 프론트가 그대로 닫아 버릴 수 있다.
   - **`W-06-03` · `W-06-10`은 아직 착수 전이라 발행해 주면 좋다.** 프론트가 이미 착수한 뒤에 도착하면 ⛔/⚠로 취급한다. **나머지 화면은 준비되는 대로 하나씩** 올리고, 동시에 여러 개를 열 때는 본문 5번(선행·순서)에 우선순위를 적는다.
3. **미결이 있어도 처리 방법만 적혀 있으면 착수 가능하다.** 완전히 확정될 때까지 기다리지 않는다.
4. **착수 이슈는 시점 기록이므로 올린 뒤 본문을 고치지 않는다.**
   - 착수 후 설계가 바뀌면 **⛔/⚠ 변경 통지를 새 이슈로** 올리고 **착수 이슈를 링크한다.**
   - 착수 이슈를 고쳐 버리면 「무엇을 근거로 만들었는가」가 사라져, 나중에 어긋남이 났을 때 누구 판단이 틀렸는지 되짚을 수 없다.
5. **닫는 것은 프론트다.** 설계는 열고, 프론트는 구현이 끝난 뒤 닫는다.

## 6. 프론트 쪽 응답 규약

이슈는 던지고 끝나는 통지가 아니다. 프론트는 아래를 **이슈 코멘트로** 남긴다. 설계는 이 코멘트만 보고 진행 상황과 어긋남을 알 수 있어야 한다.

| 시점 | 남길 것 |
| --- | --- |
| **착수할 때** | 브랜치명과 착수일 |
| **PR을 열 때** | PR 링크 |
| **스펙과 계약이 어긋났을 때** | **실측 결과와 어느 쪽을 따랐는지, 그 이유** |
| **닫을 때** | 미결 항목을 실제로 어떻게 처리했는지 |

**세 번째가 가장 중요하다.** §1의 세 사례가 전부 이 지점에서 생겼다. 어긋남을 발견하고도 프론트가 조용히 한쪽을 골라 구현하면, 설계는 자기 문서가 틀렸다는 사실을 영영 모른다. 실측한 사실과 선택을 남기면 설계 문서도 함께 고쳐진다.

닫을 때 코멘트 예:

```
구현 완료. PR #31

미결 처리 결과
- 코드 그룹 선택지 → 자리표시 상수로 처리. src/constants/codeGroups.ts 한 곳에 모음
- 첨부 미리보기 → 만들지 않음. 파일명만 표시
- 승인 반려 버튼 → 비활성 + 「권한 규칙 확정 후 활성」 표시

어긋남
- 사용 중지 요청의 If-Match: 스펙 서술과 계약이 달라 계약을 따랐다.
  실측으로 계약 쪽이 맞음을 확인 (omf-mes#88로 질문 올림)
```

어긋남을 발견했는데 어느 쪽이 맞는지 판단이 서지 않으면, 혼자 정하지 말고 **설계 저장소에 `[client→uiux]` 질문을 올린다.**
