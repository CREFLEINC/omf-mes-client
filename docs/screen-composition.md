# 화면 구성 규범

화면 하나를 **어떤 틀로 구성하는가**의 기록이다. 배치 규범(`layout-conventions.md`)이 블록 사이 간격과 정렬을 정한다면, 이 문서는 그보다 한 단계 위에서 화면의 유형, 영역 구성, 선택 후 이동, 절차 표시, 주 동작 위치를 정한다.

목표는 하나다. **처음 쓰는 사람이 사용 방법과 업무 절차를 고민하지 않고 바로 쓸 수 있는 화면.** 그러려면 어느 화면을 열어도 다음 세 가지가 같은 자리에서 보여야 한다.

1. 무엇을 선택하는가
2. 선택하면 어디로 가는가
3. 다음에 무엇을 누르는가

## 이 문서의 범위

**담는 것**
- 화면 유형과 유형 판정 기준
- 유형별 영역 구성, 선택 후 이동, 단계 표시, 주 동작 위치
- 셸과 유형에 공통인 구성 규칙(행 선택, 비활성 사유, 확인 단계, 검증 시점, 크기 검증)
- 규칙을 구현하는 공용 부품의 명세

**담지 않는 것**
- 블록 간격과 정렬 값: `layout-conventions.md`
- 컴포넌트 내부의 치수, 색, 상태: 디자인 시스템(`@crefle/web-ui`)
- 화면별 필드, 업무 규칙, 문구: 설계 화면 스펙

**서술 방식.** 배치 규범과 같이 **기본값 하나와 이탈 조건을 함께 적는다.** 「상황에 따라 다르다」로 쓰면 규범이 아니다. 이탈하면 화면 파일 머리 주석과 완료 보고에 이탈한 규칙 번호와 근거를 적는다.

**규칙 번호.** 유형 규칙은 `T-`, 공통 규칙은 `C-`로 시작한다. 검사 스크립트와 점검표는 이 번호로 위반을 보고한다.

**기준 예시.** 관리웹 처리형의 기준 모습은 「정상품 입하 처리 시안」(W-01-10)이다. 규칙과 시안이 다르면 규칙이 우선이고, 차이는 이 문서를 고쳐 맞춘다.

## 1. 화면 유형 판정

새 화면을 만들거나 기존 화면을 크게 고칠 때 **먼저 유형을 정한다.** 화면 스펙 §3(레이아웃)과 §5(액션)를 읽고 아래 질문에 차례로 답한다. 처음 「예」가 나온 유형이 그 화면의 유형이다.

### 관리웹

| 순서 | 질문 | 「예」면 |
| --- | --- | --- |
| 1 | 화면의 목적이 지표와 현황을 한눈에 보는 것인가(대시보드, 집계) | **W-D 현황형** |
| 2 | 대상을 고른 뒤 **두 단계 이상**을 거쳐 확정, 처리, 발행하는가(입고 확정, 출하 처리, 실사 마감, 판정 전이) | **W-C 처리형** |
| 3 | 기준 정보를 등록, 수정, 사용 중지하는가(마스터, 코드, 규칙, 권한) | **W-B 마스터형** |
| 4 | 그 밖에 목록을 조회하고 상세를 보는가(현황 조회, 이력 조회) | **W-A 조회형** |

- 처리형 판정의 「단계」는 사람이 순서대로 하는 일이다. 대상 선택, 입력, 확인, 확정을 각각 한 단계로 센다. 대상을 고르고 바로 한 번 누르면 끝나는 일(승인, 반려)은 조회형 상세 안의 동작으로 둔다.
- 한 화면이 두 유형에 걸치면(예: 목록 조회와 처리를 함께) **처리 부분을 처리형 화면으로 분리**하고, 원래 화면은 처리형의 작업함이 된다.

### POP

| 순서 | 질문 | 「예」면 |
| --- | --- | --- |
| 1 | 작업지시(W/O)나 작업 세션을 전제로 하는 일인가(투입, 실적, 검사, 중단, 부품 교체, 포장, 툴 사용, 비가동) | **P-W 작업형** |
| 2 | W/O와 무관한 단독 작업인가(라벨 발행, 출고 QR, 위치 라벨) | **P-S 단독형** |

### 모바일(PDA)

| 순서 | 질문 | 「예」면 |
| --- | --- | --- |
| 1 | 업무 메뉴의 진입 화면인가 | **M-H 홈** |
| 2 | 스캔이나 선택을 거쳐 등록, 확정하는가(입하, 적치, 피킹, 이동, 실사, 점검) | **M-S 단계형** |
| 3 | 스캔한 대상의 정보를 보기만 하는가(자재 위치 확인) | **M-V 조회형** |

## 2. 관리웹 유형별 구성

### T-W-A 조회형: 목록과 상세 드로어

**기준.**

| 영역(위에서 아래) | 내용 |
| --- | --- |
| 페이지 머리 | `PageHeader`. 제목, 탐색 경로, 화면 전체 동작(엑셀 내보내기 등)은 `actions` |
| 조회 조건 | 한 줄. C-6 |
| 목록 | 전체 폭 표. 행 전체 클릭(C-1). 아래에 페이지 이동(C-8) |
| 상세 | **오른쪽 드로어**(`Dialog placement="right"`). 목록은 유지 |

- 행을 누르면 드로어가 열리고, 드로어 머리에 대상 번호와 닫기가 있다. 닫으면 목록의 같은 위치로 돌아간다.
- 드로어 안에서 다른 화면으로 가야 하는 동작(예: 처리하기)은 링크 버튼으로 해당 화면을 연다. 드로어 안에 또 목록을 쌓지 않는다.
- 선택한 대상은 주소 쿼리(`?selected=`)에 남겨 새로고침과 공유에 대응한다.

**이탈 조건.**
- 상세가 표 한 줄을 더 보는 정도(필드 3개 이하)면 드로어 대신 행 펼침을 써도 된다.
- 상세에 다시 목록(이력, 라인)이 필요하면 드로어 안 탭 한 겹까지 허용한다. 그보다 깊으면 상세를 별도 화면으로 분리한다.

### T-W-B 마스터형: 목록과 편집 패널

**기준.**

| 영역 | 내용 |
| --- | --- |
| 페이지 머리 | 제목, `actions`에 [신규 등록] |
| 검색 | 한 줄. 마스터는 조건이 적으므로 검색어와 사용 여부 정도 |
| 본문 | 좌우 2단. 왼쪽 목록(행 전체 클릭), 오른쪽 편집 패널 |
| 편집 패널 하단 | 저장 하나(C-3). 취소, 사용 중지는 왼쪽 보조 동작 |

- **2단은 1280×800에서 유지한다.** 왼쪽 목록은 핵심 열(코드, 이름, 상태) 3~4개로 줄이고 최소 폭 280px, 오른쪽은 나머지 폭을 쓴다. 편집 패널의 폼이 2열을 유지할 폭이 안 되면 패널 안에서 1열로 접는다(배치 규범 5 개정 제안 참고).
- 하위 항목(버전, 공정, 검사 항목)은 편집 패널 안 탭 한 겹까지. 하위 항목을 고쳐도 저장은 패널 하단 하나다.
- 저장하지 않은 변경이 있는 상태에서 다른 행을 누르면 확인을 받는다.

**이탈 조건.**
- 하위 항목이 독립된 수명을 가지면(별도 승인, 별도 이력) 하위 편집 화면을 분리하고 패널에는 목록과 [편집] 링크만 둔다.
- 필드가 적은 코드성 마스터(필드 4개 이하)는 편집 패널 대신 행 편집 대화상자를 써도 된다.

### T-W-C 처리형: 작업함과 처리 화면

여러 단계를 거쳐 확정하는 업무는 **목록 아래에 쌓지 않고 처리 화면으로 넘어간다.** 이 유형이 이 문서의 핵심이다.

**작업함(목록 화면) 기준.**

| 영역 | 내용 |
| --- | --- |
| 페이지 머리 | 제목, 설명 한 줄에 「처리 대기 N건」 |
| 조회 조건 | 한 줄. 기본값으로 「처리 대기만」을 켠다 |
| 목록 | 행 전체 클릭으로 처리 화면 이동. 열: 식별 번호, 상대(공급사, 고객), 일시, 문서 번호, 처리 대기 수량이나 건수, 상태 칩. 마지막 열은 이동 표시(›) |

- 목록에서 처리 판단에 필요한 정보(처리 대기 수, 판정이나 상태의 구성)를 보여 준다. 사용자가 행을 열어 보기 전에 어느 건부터 할지 정할 수 있어야 한다.
- 처리할 수 없는 건은 목록에 그대로 두되 상태 칩으로 이유를 알린다.

**처리 화면 기준.**

| 영역(위에서 아래) | 내용 |
| --- | --- |
| 처리 머리 | 왼쪽 위 [← 〈작업함 이름〉], 제목은 대상 번호, 옆에 대상 요약(상대, 일시, 문서 번호) |
| 단계 표시 | `Stepper` 가로. 단계 이름은 명사형 2~6자(예: 라인 선택, 입고 위치, 확정 확인). 단계는 2~4개 |
| 지난 단계 요약 | 점선 상자 한 줄. 지난 단계에서 정한 값만 |
| 단계 본문 | **현재 단계 하나만** 표시. 구획 제목은 명사형 |
| 하단 동작 바 | 화면 아래 고정, 스크롤 영역 밖. 왼쪽에 「남은 일: 〈할 일〉」 한 줄, 오른쪽에 [이전]과 [다음: 〈다음 단계 이름〉], 마지막 단계는 [〈업무 동사〉](주 동작) |

- 주소는 작업함 아래 경로로 둔다(예: `/logistics/goods-receipt/:id`). 브라우저 뒤로가기와 [← 작업함]이 같은 결과를 낸다.
- **완료한 단계는 단계 표시에서 눌러 돌아갈 수 있다.** 입력한 값은 유지한다. 앞 단계에서 대상을 바꾸면 뒤 단계는 다시 진행한다.
- 아직 갈 수 없는 단계는 누를 수 없고, 하단 바의 「남은 일」이 그 이유를 말한다.
- **마지막 단계는 확인 단계다.** 저장될 값의 요약과 「〈업무〉 시 반영 사항」(명사형 목록, 예: 입고 전표 생성, 자재 LOT 상태 변경: 가용)을 보여 준다. 조건에 따라 빠지는 반영 사항(예: 한도승인 건의 ERP 송신 제외)은 지운 줄과 경고로 표시한다. 되돌릴 수 없으면 「확정 후에는 수정할 수 없습니다」를 함께 둔다.
- 업무 규칙에서 정해지는 값(판정에서 승계되는 상태 등)은 입력 칸이 아니라 **읽기 전용**으로 출처와 함께 보여 준다. 화면 스펙이 사람 입력으로 정한 경우에만 입력 칸으로 둔다.
- 선택 입력(사유, 비고)은 「추가 입력(선택)」으로 접는다.
- 기준 정보로 값을 추천할 수 있으면(적치 규칙의 위치 등) 「추천 적용」 버튼을 둔다.
- **완료 화면**: 성공 알림에 결과 번호, 결과 요약(상태 변화, 연계 송신 상태), 다음 작업 안내. 하단 바 오른쪽에 [다음 〈대상〉 처리](주 동작), 그 왼쪽에 [〈작업함 이름〉으로].

**이탈 조건.**
- 단계가 5개 이상이면 업무를 나눌 수 있는지 먼저 검토한다. 나눌 수 없으면 세로 `Stepper`를 왼쪽에 두는 배치를 쓴다.
- 결재처럼 다른 사람의 승인을 기다리는 단계는 단계 표시에 넣되 「대기」 상태로 두고, 처리 화면을 닫아도 작업함에서 그 상태가 보이게 한다.

### T-W-D 현황형: 대시보드

**기준.** 지표 카드 줄, 추이 차트, 처리 대기 목록 순서. 카드와 목록 행은 해당 업무 화면으로 이동하는 링크다. 자동 갱신은 하지 않고 기준 시각과 [새로고침]을 머리에 둔다(설계 공유계약 §L).

**이탈 조건.** 서버가 집계를 지원하지 않는 지표는 오류 배너가 아니라 카드 자리에 「집계 준비 중」 안내로 둔다(C-7).

## 3. POP 유형별 구성

POP 규칙은 설계 공유계약 E-1, E-3(관리웹과 같은 밀도, 1024×768 전체 화면), E-4(스크롤 구획 지정), G-34(선택 팝업)를 전제로 한다.

### T-P-W 작업형: W/O 고정과 작업 탭

**기준.**

| 영역 | 내용 |
| --- | --- |
| 머리줄 | 셸이 제공하는 공용 머리줄(C-11). 스테이션명, 작업자, 현재 W/O와 공정, 통신 상태 |
| 왼쪽 작업 탭 | 투입, 실적, 검사, 중단, 부품 교체, 포장 등 그 W/O로 할 수 있는 일. 세로 탭 |
| 본문 | 선택한 탭의 내용. 스캔 칸과 입력 |
| 하단 동작 바 | 고정. 「남은 일」 한 줄과 주 동작 하나 |

- 작업자 확인(배지 스캔 기본, 키패드 보조)과 W/O 선택은 작업형 화면에 **들어오기 전 단계**에서 끝낸다. 작업형 화면 안에 사번 키패드를 두지 않는다.
- 선택한 W/O는 모든 작업 탭이 공유한다. 탭을 바꿔도 다시 고르지 않는다.
- W/O 목록 카드는 W/O 번호, 품목 코드와 품목명, 지시와 실적 수량, 상태 텍스트(미착수, 진행 중, 보류)를 보여 주고 진행 중인 W/O를 위에 둔다.
- 화면 이동 팝업([화면 이동])은 단독형 화면으로 가는 용도로만 쓴다.

**이탈 조건.** 탭이 7개를 넘으면 자주 쓰는 5개를 탭으로, 나머지는 [기타 작업] 하나로 묶는다.

### T-P-S 단독형

**기준.** 머리줄(C-11), 본문 좌우 2단(왼쪽 대상 목록이나 스캔, 오른쪽 입력과 미리보기), 하단 동작 바 고정. 목록 행이나 카드는 전체 터치로 선택한다(C-1).

## 4. 모바일 유형별 구성

모바일 규칙은 설계 공유계약 D-1~D-3(스캔 입력), E-4, 화면 예산(앱바 56 + 본문 + 하단 동작 72)을 전제로 한다.

### T-M-H 홈

**기준.** 앱바 한 줄, 홈 스캔 칸(지시서, LOT, 위치를 스캔하면 해당 작업 화면으로 이동), 역할별 업무 묶음 타일(6개 내외, 2열). 업무 화면 20개를 한 줄로 늘어놓지 않는다.

### T-M-S 단계형: 한 화면 한 단계

**기준.**

| 영역 | 내용 |
| --- | --- |
| 앱바 | 한 줄. [←], 화면명, 상태 아이콘 |
| 단계 표시 | 현재 단계와 전체(예: LOT 2/3) |
| 지난 단계 요약 | 한 줄씩 접힘 |
| 현재 단계 | 스캔 칸(진입 즉시 포커스)과 안내 한 줄 |
| 하단 동작 바 | 본문 밖 고정. 「다음: 〈할 일〉」과 주 동작 하나 |

- 단계가 끝나면 현재 단계를 한 줄 요약으로 접고 다음 단계를 펼친다. 지난 구획을 펼친 채 아래에 구획을 추가하지 않는다.
- 대상을 정하는 스캔을 다시 하면, 입력 중인 값이 있으면 교체 확인을 받는다(공용 `ScanReplaceDialog`).
- 목록 카드는 객체별 정의(C-10)를 따른다.
- 기준 사례: 적치(단계 표시), 설비 점검(진행률), 자재 위치(화면 골격).

### T-M-V 조회형

**기준.** 스캔 칸, 결과 카드, 하단 [다음 스캔]. 결과 카드의 행동(이동 등)은 해당 단계형 화면으로 보낸다.

## 5. 공통 규칙

### C-1 행 선택

**기준.** 표와 카드 목록은 **행 전체를 눌러 선택한다.** 선택된 행은 배경과 왼쪽 막대로 표시한다. 키보드 위아래 방향키로 이동, Enter로 선택한다.
- 여러 건을 고르는 표만 첫 열 체크박스를 쓴다. 한 표에 두 방식을 섞지 않는다.
- 편집, 삭제 같은 행 동작은 **오른쪽 고정 열**(가로 스크롤 중에도 보임)이나 행 끝 「⋯」 메뉴에 둔다.
- 끝 열 [선택] 버튼을 만들지 않는다. 첫 열 식별자를 링크 모양으로 꾸미지 않는다.
- 구현: 공용 부품 `SelectableTable`(6장).

**이탈 조건.** 행을 누르는 동작이 다른 화면 이동이고 선택 상태가 의미 없으면(작업함) 선택 표시 없이 이동만 한다.

### C-2 선택 결과의 위치

**기준.** 선택 결과(상세, 하위 목록, 입력 폼)를 **목록 아래에 추가하지 않는다.** 유형별로 드로어(조회형), 오른쪽 패널(마스터형), 처리 화면(처리형), 다음 단계(모바일 단계형)를 쓴다. 한 화면 안의 연속 선택은 2단(목록, 상세)까지다.

**이탈 조건.** 없음. 필요하면 유형을 다시 판정한다.

### C-3 주 동작

**기준.** 영역마다 채움(`filled`) 버튼은 하나다. 위치는 유형별로 고정한다.

| 유형 | 주 동작 위치 |
| --- | --- |
| 조회형 | 페이지 머리 `actions`(화면 전체 동작), 드로어 하단(대상 동작) |
| 마스터형 | 편집 패널 하단 오른쪽 [저장] |
| 처리형, POP, 모바일 | 하단 동작 바 오른쪽 |

- 빨간 강조는 되돌릴 수 없는 동작(삭제, 취소 확정)과 이상 상태에만 쓴다. 사용자 전환, 단말 재등록 같은 보조 동작은 채움이나 빨강을 쓰지 않는다.
- 한 화면에 저장 버튼은 하나다. 버튼 이름은 상태에 따라 바꾸지 않는다(「사용 중지」가 「재개」로 바뀌는 등). 상태는 옆에 표시한다.

### C-4 비활성 사유와 쓸 수 없는 기능

**기준.** 배치 규범 4를 따른다. 여기에 두 가지를 더한다.
- 하단 동작 바의 주 동작이 비활성이면 바 왼쪽 「남은 일: 〈할 일〉」이 그 사유다. 버튼에 `aria-describedby`로 잇는다.
- **계약이나 기준 정보가 정해지지 않아 늘 쓸 수 없는 기능은 화면에 두지 않는다.** 「준비 중」 버튼, 늘 잠긴 입력 칸을 노출하지 않는다. 기능이 열리면 그때 추가한다.

**이탈 조건.** 화면 스펙이 「존재를 알려야 한다」고 명시한 기능은 비활성으로 두고 사유를 붙인다.

### C-5 단계 표시와 남은 일

**기준.** 두 단계 이상의 업무(처리형, POP 작업형의 각 탭, 모바일 단계형)는 단계 표시와 「남은 일」 한 줄을 둔다. 「남은 일」은 지금 해야 할 한 가지를 동사로 끝낸다(예: 「입고 창고를 고르세요」).

### C-6 조회 조건 영역

**기준.** 페이지 머리 바로 아래 한 줄. 기본으로 보이는 조건은 4~6개, 나머지는 [조건 더보기]. [조회]는 오른쪽 끝 채움 버튼, [초기화]는 그 왼쪽. Enter로도 조회한다. 필드 아래 설명문을 두지 않는다(형식은 placeholder, 보충 설명은 ⓘ 툴팁). 날짜는 C-12.

### C-7 검증 시점과 오류 표시

**기준.** 화면을 처음 열었을 때 오류를 표시하지 않는다. 필수값 검증은 포커스가 떠날 때와 실행할 때 한다. 서버가 지원하지 않는 기능이나 집계는 오류가 아니라 안내로 표시한다. 응답 형식 오류로 화면 전체가 깨지지 않게 화면 단위 오류 경계를 둔다.

### C-8 페이지 이동

**기준.** 공용 부품 하나. 목록 아래 오른쪽에 [처음] [이전] n/N [다음] [마지막], 왼쪽에 총 건수와 페이지 크기. 비활성 버튼에 사유 문장을 붙이지 않는다(위치로 자명).

### C-9 확정 전 확인과 다음 작업

**기준.** 되돌릴 수 없는 동작은 확인을 거친다. 처리형은 마지막 확인 단계가 그 역할을 하고, 그 밖의 유형은 확인 대화상자(대상 번호와 이름, 변경되는 값, 버튼은 〈동사〉와 취소)를 쓴다. 성공 후에는 결과와 **다음 작업으로 가는 버튼**을 둔다.

### C-10 목록 행과 카드의 정보

**기준.** 업무 객체(W/O, 입하 라인, 피킹 지시 등)마다 목록에 보일 필드와 순서를 한 번 정해 공용으로 쓴다. 굵게 강조하는 필드는 2개까지. 품목은 코드와 이름을 함께 보인다. 값이 없으면 그 줄을 숨기고 「알 수 없음」, 「있음/없음」 같은 대체 문구를 쓰지 않는다. 상태는 색과 텍스트를 함께 쓴다. 긴 LOT 번호는 공용 표시 부품으로 조각을 띄워 보인다(공유계약 E-2).

### C-11 셸 공통 틀

**기준.** 머리줄과 하단 동작 바는 **화면이 조립하지 않고 셸이 제공한다.** 화면은 제목, 상태, 동작만 넘긴다. POP 머리줄 항목은 스테이션명, 작업자, 현재 W/O와 공정, 통신 상태로 고정한다. 단말은 내부 번호가 아니라 단말 코드로 표시한다.

### C-12 입력 장치

**기준.** 날짜는 DS `DatePicker` 하나(형식 yyyy-MM-dd, 타이핑과 달력 모두 허용). 브라우저 기본 `type="date"`를 쓰지 않는다. 숫자 키패드는 DS `NumberPad` 하나, 지우기 문구는 [전체 지움]으로 통일한다. 선택지가 200건 이하이면 검색 가능한 `Select`, 1,000건을 넘으면 검색 대화상자(검색어, 필터, 결과 표)를 쓴다. 200~1,000건은 검색 대화상자를 기본으로 한다.

### C-13 문구

**기준.** 화면 문구는 사용자가 할 수 있는 일만 말한다. 개발 사정(「아직 확정되지 않은 임시 목록」, 「서버가 아직 지원하지 않습니다」)과 내부 식별자를 노출하지 않는다. 라벨, 구획 제목, 단계 이름은 명사형. 안내와 오류는 무엇이 안 됐는지와 할 일을 한두 문장으로 쓴다.

### C-14 크기 검증

**기준.** 다음 크기에서 주 동작과 선택 컨트롤이 **스크롤 없이** 보여야 한다. 넘치면 구성을 바꾼다.

| 셸 | 검증 크기 |
| --- | --- |
| 관리웹 | 1280×800 (사이드바 펼침) |
| POP | 1024×768 |
| 모바일 | 360×720dp(하한), 432×792(실기) |

## 6. 공용 부품 명세

아래 부품이 없으면 위 규칙을 화면마다 다시 구현하게 되고, 그 결과가 지금의 불일치다. 부품이 생기기 전에는 첫 화면이 만든 구현을 `patterns/`로 올려 두 번째 화면부터 재사용한다.

| 부품 | 위치(제안) | 역할 | 규칙 |
| --- | --- | --- | --- |
| `SelectableTable` | `apps/web/src/patterns/selectable-table/` | DS `Table` 감싸개. 행 전체 클릭, 선택 행 표시, 키보드 이동, 오른쪽 고정 행 동작 열 | C-1 |
| `ProcessPage` | `apps/web/src/patterns/process-page/` | 처리 화면 틀. 처리 머리([← 작업함], 대상 번호, 요약), 단계 표시(완료 단계 복귀), 지난 단계 요약, 하단 동작 바(남은 일, 이전, 다음, 주 동작) | T-W-C, C-5 |
| `ActionBar` | `apps/web/src/patterns/action-bar/` | 하단 고정 동작 바. 남은 일 한 줄과 버튼 묶음. `ProcessPage`, POP, 모바일 공용 | C-3, C-4 |
| `DetailDrawer` | `apps/web/src/patterns/detail-drawer/` | `Dialog placement="right"` 기반 상세 드로어. 머리(대상 번호, 닫기), 본문, 하단 동작 | T-W-A |
| `EffectList` | `ProcessPage` 하위 | 「〈업무〉 시 반영 사항」 목록. 항목별 제외 표시 | T-W-C, C-9 |
| `PageNav` | `apps/web/src/patterns/page-nav/` | 페이지 이동 하나 | C-8 |
| `LotNumber` | `packages/ui` 후보 | 긴 LOT 번호 조각 표시 | C-10 |
| `PopHeader`, `PopActionBar` | `apps/web/src/patterns/pop-*` | POP 공용 머리줄과 하단 바 | C-11 |

- 행 클릭과 오른쪽 고정 열은 DS `Table`에 들어가야 할 기능이다. `SelectableTable`은 DS 요청이 반영될 때까지의 임시 감싸개이고, 반영되면 걷어 낸다.
- 화면별로 같은 이름의 파일(`page-nav.tsx`, `pagination.ts`, `load-error-banner.tsx`, `select-field.tsx`)을 새로 만들지 않는다. 기존 복제본은 해당 화면을 고칠 때 공용 부품으로 바꾼다.

## 7. 배치 규범 5 개정 제안

현행 규범 5는 창 폭 1280px 이하에서 2단을 1단으로 접는다. 사이드바를 펼친 1280×800 노트북에서는 이 때문에 옆에 열리던 상세가 목록 아래로 내려가고, 실측에서 선택 결과가 아래에 쌓이는 관리웹 화면이 12개에서 24개로 늘었다.

**제안.** 마스터형의 2단은 왼쪽 목록 최소 폭 280px, 오른쪽 나머지로 두고 접힘 기준을 **본문 폭 900px**(창 폭 약 1160px)로 낮춘다. 오른쪽 패널의 폼 2열은 패널 폭 680px 미만에서 1열로 접는다(컨테이너 쿼리). 조회형은 드로어를 쓰므로 접힘 기준이 필요 없다.

## 8. 점검표

화면을 만들거나 고친 뒤 완료 보고 전에 확인한다. 검사 스크립트가 잡는 항목은 (자동)으로 표시했다.

- [ ] 유형을 판정하고 화면 파일 머리 주석에 유형 번호(T-…)를 적었다
- [ ] 행 전체 클릭으로 선택된다. 끝 열 [선택] 버튼이 없다 (자동)
- [ ] 선택 결과가 목록 아래에 추가되지 않는다
- [ ] 영역마다 채움 버튼이 하나이고 유형별 위치에 있다
- [ ] 비활성 주 동작에 「남은 일」이나 사유가 보이고 `aria-describedby`로 이어진다 (자동)
- [ ] 「준비 중」 버튼과 늘 잠긴 칸이 없다
- [ ] 두 단계 이상이면 단계 표시와 「남은 일」이 있다
- [ ] 처음 열었을 때 오류가 표시되지 않는다
- [ ] 날짜는 `DatePicker`, 페이지 이동은 공용 부품을 쓴다 (자동)
- [ ] 화면 폴더에 공용 부품의 복제본을 새로 만들지 않았다 (자동)
- [ ] DS에 없는 토큰과 직접 지정한 색을 쓰지 않았다 (자동)
- [ ] 검증 크기에서 주 동작과 선택 컨트롤이 스크롤 없이 보인다 (자동: 화면 실측 검사)
- [ ] 문구가 C-13을 따른다

## 갱신 규칙

- 같은 결정을 두 번째 화면에서 다시 하게 되면 규칙으로 올린다(배치 규범과 같은 기준).
- 규칙을 바꾸면 검사 스크립트의 규칙 번호와 기준 예시(시안)를 함께 맞춘다.
- 설계 화면 스펙과 충돌하면 화면 스펙이 우선이다. 충돌은 설계 요청서로 올리고, 결정이 나기 전까지 이탈 사유를 화면 파일에 적는다.
