# OMF MES 화면 구성 절차

이 절차의 목적은 누가 만들어도 같은 구성의 화면이 나오게 하는 것이다. 규칙의 정본은 `docs/screen-composition.md`(화면 구성 규범)와 `docs/layout-conventions.md`(배치 규범)다. 이 파일은 그 규칙을 적용하는 순서만 담는다. 규칙과 이 절차가 다르면 규범 문서가 우선이다.

## 0. 시작 전 확인

1. 작업 대상 화면 번호(W-, P-, M-)와 설계 화면 스펙을 확인한다. 스펙은 고정 설계 참조본(`.client-dev/design/omf-mes/design/wiki/screens/`)에서 읽는다.
2. `docs/screen-composition.md` 전체와 `docs/layout-conventions.md`의 규범 목록을 읽는다.
3. 같은 유형의 기존 화면이 공용 부품(`patterns/selectable-table`, `process-page`, `action-bar`, `detail-drawer`, `page-nav`)을 쓰고 있으면 그 화면을 참고 구현으로 삼는다.

## 1. 유형 판정

화면 구성 규범 1장의 질문표로 유형을 정한다. 결과를 아래 형식으로 계획 문서(`.client-dev/` 아래 plan)에 적는다.

```
유형: T-W-C 처리형
근거: 대상(입하 전표) 선택 후 라인 선택, 입고 위치 입력, 확정의 3단계 (스펙 §5-1~§5-4)
분리: 기존 화면의 목록 부분은 작업함으로 남긴다
```

- 한 화면이 두 유형에 걸치면 분리안을 먼저 적는다. 분리가 설계 스펙의 레이아웃(§3)과 다르면 설계 요청서(`docs/client-dev-workflow/templates/design-request.md`)를 작성해 사용자에게 전달을 부탁하고, 결정 전에는 스펙대로 구현하되 이탈 예정 사항을 계획에 적는다.

## 2. 구성안 작성

코드를 쓰기 전에 구성안을 표로 적는다. 구성안이 규범의 유형 표와 1:1로 대응해야 한다.

| 항목 | 적을 내용 |
| --- | --- |
| 영역 | 유형 표의 영역 이름 그대로, 위에서 아래 순서 |
| 선택 후 이동 | 드로어, 오른쪽 패널, 처리 화면, 다음 단계 중 하나 (C-2) |
| 단계 | 처리형과 단계형: 단계 이름(명사형 2~6자)과 각 단계의 입력 칸 |
| 주 동작 | 동작 이름과 위치 (C-3) |
| 남은 일 문구 | 주 동작이 비활성인 각 경우의 문구 (C-4, C-5) |
| 읽기 전용 값 | 업무 규칙에서 정해지는 값과 출처 |
| 숨길 기능 | 계약이나 기준 정보가 없어 쓸 수 없는 기능 (C-4) |
| 반영 사항 | 처리형 확인 단계에 보일 「〈업무〉 시 반영 사항」 목록 (C-9) |
| 다음 작업 | 완료 후 버튼 (C-9) |

- 문구는 화면 스펙의 용어를 그대로 쓴다. 새 용어를 만들지 않는다.
- 판단이 서지 않는 항목은 「확인 필요」로 남기고 사용자에게 묻는다. 추측으로 채우지 않는다.

## 3. 구현

1. 공용 부품을 먼저 쓴다. 필요한 부품이 없으면 규범 6장 명세대로 `patterns/` 아래에 만들고, 화면 폴더 안에 만들지 않는다.
2. 화면 파일 머리 주석에 유형 번호와 이탈한 규칙(있으면 번호와 근거)을 적는다.

```ts
/**
 * W-01-10 정상품 입하 처리
 * 유형: T-W-C 처리형 (작업함: GoodsReceiptWorklist, 처리 화면: GoodsReceiptProcess)
 * 이탈: 없음
 */
```

3. 금지 사항(검사 스크립트가 잡는다)
   - 표 끝 열의 [선택] 버튼, 링크 모양의 첫 열 식별자
   - 브라우저 기본 `type="date"`
   - 화면 폴더 안의 `page-nav`, `pagination`, `load-error-banner`, `select-field` 신규 복제
   - 사유 없이 `disabled`인 주 동작
   - DS에 없는 토큰(`--type-*-md` 등)과 직접 지정한 색
4. 업무 로직과 계약은 기존 화면 구현을 재사용한다. 구성 변경 작업에서 API 호출 방식이나 검증 규칙을 바꾸지 않는다.

## 4. 자체 점검

1. **정적 검사**: `pnpm ui:check` (변경 파일 기준). 새 위반이 0이어야 한다. 기존 위반 기준선(`tools/ui-check/baseline.json`)은 줄이기만 하고 늘리지 않는다.
2. **화면 실측 검사**: 목 서버와 개발 서버를 띄우고 `pnpm ui:probe -- <화면 경로>`. 검증 크기(관리웹 1280×800, POP 1024×768, 모바일 360×720)에서 다음을 확인한다.
   - 행 클릭으로 선택되는가
   - 선택 후 내용이 아래에 추가되지 않는가(페이지 높이 증가)
   - 주 동작이 첫 화면 안에 보이는가
   - 진입 직후 오류 표시가 없는가
3. **점검표**: 화면 구성 규범 8장 점검표를 하나씩 확인한다.
4. **기준 예시 비교**: 처리형이면 「정상품 입하 처리 시안」과 같은 크기로 캡처해 영역 구성이 같은지 본다.

## 5. 완료 보고

`docs/client-dev-workflow/templates/completion-report.md`에 다음을 더한다.

- 유형과 판정 근거
- 구성안 표(최종본)
- 정적 검사 결과(새 위반 수, 줄어든 기준선 수)
- 화면 실측 결과(검증 크기별 캡처 경로, 클릭 수, 스크롤 필요 여부)
- 이탈한 규칙과 근거, 설계 요청서를 낸 경우 그 포인터

## 하지 않는 것

- 규범에 없는 새 배치를 화면에서 먼저 만들지 않는다. 필요하면 규범 갱신을 제안한다.
- 색, 간격, 글꼴을 화면 CSS에서 직접 정하지 않는다(DS 토큰과 배치 규범).
- 시안의 모양을 그대로 복사하지 않는다. 시안은 구성의 기준 예시이고, 부품은 DS와 공용 부품을 쓴다.
