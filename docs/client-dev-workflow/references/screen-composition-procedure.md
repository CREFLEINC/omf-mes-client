# OMF MES 화면 구성 절차

이 절차의 목적은 누가 만들어도 같은 구성의 화면이 나오게 하는 것이다. 규칙의 정본은 `docs/screen-composition.md`(화면 구성 규범)와 `docs/layout-conventions.md`(배치 규범)다. 이 파일은 그 규칙을 적용하는 순서만 담는다. 규칙과 이 절차가 다르면 규범 문서가 우선이다.

## 0. 시작 전 확인

1. 작업 대상 화면 번호(W-, P-, M-)와 업무 이슈(omf-all-around)를 확인하고, 그 화면이 부르는 API를 서버 계약(클라이언트 생성 타입 `packages/api-client`, 서버 `contracts/`)에서 읽는다. 업무 규칙이 이슈에 없으면 사용자에게 묻는다.
2. `docs/screen-composition.md` 전체와 `docs/layout-conventions.md`의 규범 목록을 읽는다.
3. 같은 유형의 기존 화면이 공용 부품(`patterns/selectable-table`, `process-page`, `action-bar`, `detail-drawer`, `page-nav`)을 쓰고 있으면 그 화면을 참고 구현으로 삼는다.

## 1. 유형 판정

화면 구성 규범 1장의 질문표로 유형을 정한다. 결과를 아래 형식으로 구성안 파일 `.client-dev/plans/<화면 번호>-composition.md`에 적는다(여러 화면을 합치면 대표 화면 번호).

```
유형: T-W-C 처리형
근거: 대상(입하 전표) 선택 후 라인 선택, 입고 위치 입력, 확정의 3단계 (이슈 본문의 업무 절차)
분리: 기존 화면의 목록 부분은 작업함으로 남긴다
```

- 한 화면이 두 유형에 걸치면 분리안을 먼저 적는다.
- 구성은 규범이 정한다(규범 머리말 「근거와 우선순위」). 이슈에 적힌 배치와 다르면 **규범대로 구현하고**, 차이를 그 이슈에 남긴다. 데이터나 API가 필요하면 C-15 절차로 요청 초안을 `.client-dev/requests/`에 쓰고(커밋하지 않음) 사용자에게 보낼 곳을 확인받는다.

## 2. 구성안 작성

코드를 쓰기 전에 구성안을 표로 적는다. 구성안이 규범의 유형 표와 1:1로 대응해야 한다.

| 항목         | 적을 내용                                                                                           |
| ------------ | --------------------------------------------------------------------------------------------------- |
| 영역         | 유형 표의 영역 이름 그대로, 위에서 아래 순서                                                        |
| 선택 후 이동 | 오른쪽 상세 창, 오른쪽 패널, 처리 화면, 다음 단계 중 하나 (C-2)                                     |
| 단계         | 처리형과 단계형: 단계 이름(명사형 2~6자)과 각 단계의 입력 칸                                        |
| 주 동작      | 동작 이름과 위치 (C-3)                                                                              |
| 남은 일 문구 | 주 동작이 비활성인 각 경우의 문구 (C-4, C-5)                                                        |
| 읽기 전용 값 | 업무 규칙에서 정해지는 값과 출처                                                                    |
| 숨길 기능    | 계약이나 기준 정보가 없어 쓸 수 없는 기능 (C-4)                                                     |
| 반영 사항    | 처리형 확인 단계에 보일 「〈업무〉 시 반영 사항」 목록 (C-9)                                        |
| 다음 작업    | 완료 후 버튼과 다음 처리 대상 (C-9, T-W-C 완료 화면)                                                |
| 정보 추가    | 규칙이 요구하지만 계약에 없는 정보와 결정, C-15 판단 기준 넷의 답, 화면 계산 가능 여부, 요청서 여부 |
| 재사용 부품  | 단계에 넣는 기존 부품마다 C-20 점검표의 결과(맞춤, 이탈과 근거)                                     |
| 시각 기준    | 제목 세 단계에 쓰는 요소, 조회 조건 칸별 폭(좁음, 보통, 넓음), 버튼별 높이와 모양(C-19)             |

- 문구는 업무 이슈와 서버 계약의 용어, 기존 화면에서 쓰던 업무 용어를 그대로 쓴다. 새 용어를 만들지 않는다.
- 판단이 서지 않는 항목은 「확인 필요」로 남기고 사용자에게 묻는다. 추측으로 채우지 않는다.
- 규칙이 요구하는 정보가 없다고 그 요소를 숨기지 않는다. C-15 절차로 추가를 요청하고 「계약 대기」로 기록한다.

## 3. 구현

1. 공용 부품을 먼저 쓴다. 필요한 부품이 없으면 규범 6장 명세대로 `patterns/` 아래에 만들고, 화면 폴더 안에 만들지 않는다.
2. 화면 파일 머리 주석에 유형 번호와 이탈한 규칙(있으면 번호와 근거)을 적는다.

```ts
/**
 * W-01-10 정상품 입하 처리
 * 유형: T-W-C 처리형 (작업함: GoodsReceiptWorklist, 처리 화면: GoodsReceiptProcess)
 * 이탈: 없음
 */
```

3. 금지 사항. 규범 8장 「규칙별 확인 방법」에 자동 확인 여부가 있다. 자동이 아닌 항목은 직접 점검한다.
   - 표 끝 열의 [선택] 버튼(자동), 링크 모양의 첫 열 식별자(사람)
   - 기준 정보 참조(품목, 거래처, 창고, 위치, 생산 라인, 설비, 작업자)를 `Select`로 받기(사람). 참조 선택 팝업(`patterns/reference-picker`)을 쓴다
   - 브라우저 기본 날짜, 일시, 시각 입력(자동)
   - 화면 폴더 안의 `page-nav`, `pagination`, `load-error-banner`, `select-field` 신규 복제(자동)
   - 사유 없이 `disabled`인 채움 버튼(자동)
   - DS에 없는 토큰과 직접 지정한 색(자동, 인라인 스타일 포함)
4. 업무 로직, 검증 규칙, API 호출은 기존 화면 구현을 재사용한다. 화면 문구와 코드값 표시는 C-13을 적용해 고친다(구성 변경 작업도 기존 문구 정리를 포함한다).

## 4. 자체 점검

1. **정적 검사**: `pnpm ui:check`(`node tools/ui-check/check-screen-rules.mjs`와 같다). 작업 전에 한 번 돌려 결과를 적어 둔다. 기준선은 위반 하나하나의 지문(규칙, 파일, 정규화한 줄 글자)으로 비교하므로, 한 곳을 고치고 다른 곳에 새 위반을 넣으면 새 위반으로 잡힌다. 줄 번호가 밀려도 같은 위반으로 본다. 종료 코드는 0 통과, 1 새 위반, 2 실행 불가(DS CSS나 TypeScript를 못 찾음, 옛 형식 기준선). `--init-baseline`은 기준선 파일이 없을 때만 만든다(`--force`로 덮어씀). 판정은 「이번 변경이 건드린 파일에서 늘어난 위반 0」이다(다른 작업으로 이미 늘어난 위반은 따로 보고한다). 화면 완료 조건으로 「그 화면의 위반 0」을 볼 때 범위는 **화면이 실제로 불러 쓰는 파일**(import 기준)이다. 같은 폴더에 있어도 다른 화면만 쓰는 파일은 범위 밖이고, 완료 보고에 그 파일과 쓰는 화면을 적는다. 위반을 없앴으면 `--update-baseline`으로 기준선을 낮추고 기준선 파일을 같은 커밋에 넣는다. 기준선을 올리지 않는다.
2. **화면 실측 검사**: 목 서버와 개발 서버를 띄우고 `python3 -I tools/ui-check/layout-probe.py --base <개발 서버 주소> --routes <경로…> --size <검증 크기>`(Playwright 필요). 처리형은 작업함 경로와 처리 화면 경로를 함께 넣는다. 검증 크기(관리웹 1280×800, POP 1024×768, 모바일 360×720)에서 다음을 확인한다.
   - 행 클릭으로 선택되는가
   - 선택 후 내용이 아래에 추가되지 않는가(페이지 높이 증가)
   - 주 동작이 첫 화면 안에 보이는가
   - 진입 직후 오류 표시가 없는가
   - 표 셀이 두 줄로 접히지 않는가(P-6)
3. **점검표**: 화면 구성 규범 9장 점검표를 하나씩 확인한다.
4. **기준 구현 비교**: 처리형이면 기준 구현 「작업지시 목록」과 같은 크기로 캡처해 영역 구성이 같은지 본다.

## 5. 완료 보고

완료 보고 양식(`docs/client-dev-workflow/templates/screen-completion-report.md`)을 채운다. 양식의 항목은 다음과 같다.

- 유형과 판정 근거
- 구성안 표(최종본)
- 정적 검사 결과(새 위반 수, 줄어든 기준선 지문 수)
- 실측 검사 결과(위반 수, 판정 불가 경로와 이유). 실측 검사 종료 코드는 1 위반, 2 판정 불가(`--allow-undetermined`로 0)
- 화면 실측 결과(검증 크기별 캡처 경로, 클릭 수, 스크롤 필요 여부)
- 이탈한 규칙과 근거, 요청을 낸 경우 그 이슈 링크
- 바꾼 화면 이름과 메뉴 이름(C-13)
- C-15 「계약 대기」 항목. 대기 항목이 있으면 완료가 아니다(사용자가 부분 반영을 승인한 경우만 예외, 승인 사실을 적는다)

## 하지 않는 것

- 규범에 없는 새 배치를 화면에서 먼저 만들지 않는다. 필요하면 규범 갱신을 제안한다.
- 색, 간격, 글꼴을 화면 CSS에서 직접 정하지 않는다(DS 토큰과 배치 규범).
- 기준 구현의 업무 코드를 복사하지 않는다. 기준 구현은 구성의 예시이고, 부품은 DS와 공용 부품을 쓴다.
