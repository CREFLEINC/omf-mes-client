# 검증 수준

검증 범위는 변경 위험에 비례해 개발팀이 결정한다. 모든 변경에 같은 비용을 강제하지 않되, 수행한 검증과 생략한 검증을 명시한다.

## 수준 판정

| 수준 | 예시                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------- |
| 중요 | API 계약, 인증·권한, 되돌릴 수 없는 쓰기, 데이터 손실, 상태 전이, 낙관적 잠금, 여러 화면의 공용 동작 |
| 보통 | 화면 하나의 조회·입력 흐름, 기존 패턴의 신규 기능, 국소 버그 수정                                    |
| 낮음 | 문구·스타일, 문서, 테스트 보강, 동작을 바꾸지 않는 정리                                              |

판단이 갈리면 높은 수준을 적용한다.

## 공통 게이트

모든 변경은 작업 시작과 완료 전에 아래를 확인한다.

```bash
pnpm workflow:check
git status --short --branch
```

변경 전 기준 상태를 기록해 기존 실패와 신규 실패를 구분한다.

## 저장소 검증 명령

| 항목             | 명령                                     | 적용                             |
| ---------------- | ---------------------------------------- | -------------------------------- |
| 하네스 단위 시험 | `pnpm test:workflow`                     | 하네스·업무 규칙 스크립트 변경   |
| 하네스 정적 검사 | `pnpm workflow:repo-check`               | 하네스·업무 규칙 문서 변경       |
| 타입 검사        | `pnpm typecheck`                         | TypeScript 변경                  |
| 전체 테스트      | `pnpm test`                              | 공용 경계·중요 변경              |
| 패키지 테스트    | `pnpm --filter <패키지명> test`          | 영향이 패키지 하나로 제한될 때   |
| 의존 방향        | `pnpm dep:check`                         | `apps/`·`packages/` 경계 변경    |
| 계약 스모크      | `pnpm mock:smoke`                        | 계약·목 서버·API 클라이언트 변경 |
| 생성물 경계      | `pnpm check:generated`                   | 생성 API 타입 변경               |
| 계약 타입 동기   | `pnpm gen:api` 후 diff 확인              | 공지된 계약 버전 반영            |
| 빌드             | `pnpm --filter @omf-mes/web build`       | 관리웹 빌드 영향                 |
| 실제 실행        | 목 서버와 대상 앱 실행 후 핵심 경로 확인 | 중요·보통 동작 변경              |

## 수준별 최소 범위

- **낮음**: `workflow:check`, 변경 파일 포맷, 관련 정적 검사·단위 시험. 동작이 정말 바뀌지 않았는지 diff로 확인한다.
- **보통**: 낮음 범위 + 타입 검사 + 관련 패키지 테스트 + 핵심 경로 실제 실행.
- **중요**: 보통 범위 + 전체 테스트와 관련 경계 검사 + 정상·오류 경로 실제 실행. 새 감지기는 가능한 경우 의도적 결함을 넣어 실제로 실패하는지 확인하고 원복한다.

독립 리뷰는 중요 변경에서 우선 사용한다. 사용할 수 없는 특정 도구나 과거의 기간 한정 예외를 완료 조건으로 남기지 않는다.
