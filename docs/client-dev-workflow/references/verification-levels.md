# 검증 수준 — 3단계와 저장소 검증 명령

운영 규칙 §3의 실행 절차다. 검증은 **실제로 실행하여 직접 프로그램의 동작을 검증**하는 것을 포함한다. 다만 사소한 것까지 다 검증하면 검증 비용이 커지므로, 개발 요소의 중요성에 따라 수준을 유동적으로 정한다. **각 수준에서 무엇을 검증할지는 이 저장소가 자체적으로 정한다**(규칙 §3 말미) — 아래가 그 결정이다.

## 수준 판정

| 수준 | 판정 기준 |
| :-: | --- |
| **중요** | 되돌릴 수 없는 쓰기 · 인증/권한 · 계약(API) 경계 변경 · 여러 화면이 공유하는 부품·상수 · 상태 전이·낙관적 잠금 · 데이터 손실 가능 경로 |
| **보통** | 화면 1장의 조회·입력 흐름 · 기존 패턴을 따르는 신규 화면 · 국소 버그 수정 |
| **낮음** | 문구·스타일 조정 · 주석·문서 · 테스트 보강 · 생성물 재생성 |

**판단이 갈리면 높은 쪽을 택한다.**

## 수준별 검증

| 수준 | 검증 담당 | 게이트 | 실행 확인 |
| :-: | --- | --- | --- |
| 중요 | 독립 검증 **필수** — 만든 사람이 자기 것만 보지 않는다 | 전체 게이트 | 정상+오류 경로를 **브라우저로 직접** 확인. 새 감지기(테스트)를 추가했으면 일부러 결함을 넣어 그 감지기가 실패하는지 1회 확인하고 원복 |
| 보통 | 독립 검증 수행 | 전체 게이트 | 핵심 경로 1회 실행 확인 |
| 낮음 | 자체 검증으로 갈음 | 빠른 게이트 | 필요 시에만 |

## 저장소 검증 명령

루트에서 실행한다.

| 항목 | 명령 | 적용 대상 |
| --- | --- | --- |
| 타입 검사 | `pnpm typecheck` | 코드 변경 전부 |
| 전체 테스트 | `pnpm test` | 테스트가 있는 패키지 전체 |
| 패키지 단위 테스트 | `pnpm --filter <패키지명> test` | 빠른 게이트용 (예: `pnpm --filter @omf-mes/web test`) |
| 의존 방향 검사 | `pnpm dep:check` | `apps/`·`packages/` 경계 변경 |
| 계약 스모크 | `pnpm mock:smoke` | 계약·목 서버·API 클라이언트 변경 |
| 생성물 경계 검사 | `pnpm check:generated` | `packages/api-client/src/generated/` 경계에 닿는 변경 |
| 계약 타입 동기 확인 | `pnpm gen:api` 후 `git diff --stat` | 계약 정본이 갱신됐을 가능성이 있을 때 |
| 빌드 | `pnpm --filter @omf-mes/web build` | 관리웹 코드 변경 |
| **실제 실행** | `pnpm mock` (별도 터미널) + `pnpm --filter @omf-mes/web dev` → 브라우저로 확인 | 중요·보통 수준 전부 |

**아직 없는 수단**: ESLint·포맷 검사 스크립트·시각적 회귀·접근성 자동 검사. `prettier`는 설치돼 있으나 검사 스크립트가 없다. 필요한 작업에서는 대체 검증(렌더링 테스트의 `getByRole`/`getByLabelText`, 사용자 육안 확인 담당 지정 등)을 계획에 명시한다. 도구가 늘면 이 표를 먼저 갱신한다.

## 게이트 등급

**전체 게이트** — 위 표에서 이번 작업에 해당하는 명령 전부. 세 시점에 고정한다:

1. 구현 초회 커밋 완료 시
2. 독립 검증 착수 시 (중요·보통)
3. 병합 직전 최종 1회

**빠른 게이트** — 수정 회차·재확인에 적용: `pnpm typecheck` + 해당 패키지 테스트(`pnpm --filter <패키지> test`) + 변경 파일 `pnpm exec prettier --check <변경 파일>`.

**승격 조건** — 접촉 위치가 아니라 변경의 **성격**으로 판단한다. 다른 소비처에 파급될 수 있는 변경이면 빠른 게이트라도 전체 게이트로 승격한다:

- 승격한다: 공개 export·타입 시그니처 변경 · 계약·생성물 변경 · 목 서버 동작 변경 · 라우트 구조 변경 · 공용 컴포넌트의 동작 변경
- 승격하지 않는다: 공용 패키지 안이라도 문구 상수 값·주석·문서만 바뀐 경우
- 판단이 갈리면 승격한다

## 기준 상태 기록

변경을 시작하기 **전에** 완료 조건에 걸린 검증을 전부 1회 실행해 통과/실패를 기록한다. 이 기록이 없으면 기존 실패와 신규 실패를 구분할 수 없다.

이 저장소에는 실제로 알려진 기존 실패가 있다 — 예: 이슈 #204(TZ=UTC 시간대 매임, 전역 9건) · #207(Prettier 비준수 145파일). 기준 상태에 이미 있던 실패는 이번 작업의 완료 판정에서 제외하되, 최종 보고에 남아 있는 사실을 명시한다. 기준 상태에 없던 실패가 변경 후 나타나면 **신규 실패**다.

## 「중요」 수준의 뮤테이션 확인 — 감지기가 실제로 무는지

새 테스트를 추가하는 변경은 게이트가 원리적으로 검증하지 못한다 — 추가 전에도 후에도 전부 녹색이라, 새 감지기가 실제로 결함을 무는지는 게이트 결과에 나타나지 않는다. 그래서 **일부러 결함을 넣어 그 감지기가 정확히 실패하는지 확인하고 원복**한다.

1. 감지기가 지키려는 로직에 결함 하나를 심는다(예: 조건 반전, 경계값 변경)
2. 해당 테스트만 실행 — **실패**해야 한다. 통과하면 감지기가 그 결함을 못 잡는다는 뜻이니 감지기를 고친다
3. 결함을 원복하고 `git status`로 깨끗한지 확인 — 원복 누락은 그 자체로 결함이다

## 역할 분리

- 코드 개발은 수준과 무관하게 실행과 검증을 다른 담당(사람 또는 구현자와 분리된 별도 검증)이 맡는다. 예외는 「낮음」 수준뿐이다.
- 검증 담당은 구현자의 설명이나 자체 검증 결과를 검증의 대체물로 쓰지 않는다 — 배정된 검증을 직접 실행한다.
- 검증 담당은 발견한 문제를 직접 고치지 않는다. 재현 방법과 기대 결과를 붙여 반환한다.
- 독립 검증을 구할 수 없으면 완료로 처리하지 않는다 — 수행/미수행 검증을 구분해 보고한다.
