# 병합 규칙 — 워크트리·PR·충돌·선착순

운영 규칙 §2-4.3 「메인 브랜치 무결성 유지」의 실행 절차다. `main`은 항상 모든 개발팀의 완료된 업무가 병합돼 테스트 가능한 상태를 유지한다. 개발 업무는 독립된 워크트리에서 진행하고, 그 워크트리는 **T4 하나에만 종속**된다 — 다른 팀의 워크트리와 섞이지 않는다.

## 슬라이스 — 한 PR은 한 화면의 일부

- 작업 단위는 생성 코드·잠금 파일을 제외하고 **400줄 상한**을 넘기지 않는다.
- 등록에서 병합까지를 짧게 유지한다.

**충돌 창의 길이가 곧 충돌 확률이다.** 화면 1장을 PR 여러 개로 쪼개는 것이 팀 간 충돌을 막는 가장 실질적인 장치다.

**예외(2026-08-31~09-04, T3 마감 국면, 사용자 승인)** — 개발 기간이 극도로 짧을 때 400줄 상한을 완화해 **화면 1장 = PR 1개**로 진행할 수 있다. 이 완화는 그 기간·그 팀에만 적용됐고, 정본 상한은 400줄 그대로다. 완화 상태에서도 실제 충돌은 없었다 — 화면 슬라이스가 디렉터리로 갈려 있어 팀 간 충돌 지점은 여전히 「접촉이 몰리는 파일」(아래 표) 뿐이었고, 그 파일들은 화면당 1~2줄만 건드려 병합 순서 조율로 충분했다(`omf-mes-client#111`·`#114`가 같은 시점에 `routes/index.tsx`를 건드렸을 때 병합 순서만 맞춰 처리한 사례 참고).

## PR 등록 직전 — rebase와 전체 게이트

```bash
git fetch origin && git rebase origin/main
# 전체 게이트 — 명령 목록은 verification-levels.md가 정본
git push --force-with-lease
```

- PR이 열려 있는 동안 `main`이 움직였으면 **병합 직전에 한 번 더** 같은 절차를 밟는다.
- ⚠ `--force`가 아니라 `--force-with-lease`를 쓴다 — 남의 push를 지우지 않는다.
- 작업 브랜치는 룰셋 보호 대상이 아니다(보호 대상은 `main` 하나 — `CLAUDE.md`).

## 충돌 해소 — 생성물은 재생성으로만

| 대상 | 해소 방법 |
| --- | --- |
| 일반 소스 | 직접 해소 |
| `packages/api-client/src/generated/api.d.ts` | ⛔ 손 병합 금지 — `pnpm gen:api` 재생성 |
| `pnpm-lock.yaml` | ⛔ 손 병합 금지 — `pnpm install` 재생성 |

자동 생성물을 손으로 합치면 어느 계약의 타입이 살았는지 알 수 없게 된다(`docs/decisions.md` #7). 해소 후 전체 게이트를 다시 돌린다 — 해소는 새 커밋이다.

이슈 대응 범위 밖의 변경이 추가로 필요해지면 사용자 승인을 받는다.

## 그래도 겹치면 — 선착순, 대기 측은 워크트리로 다음 작업

기준은 **PR 생성 시각**이다. 먼저 등록된 PR이 **병합될 때까지** 대기한다. 대기 중에 놀지 않되, **브랜치를 갈아타지 말고** `git worktree add`로 분리해 다음 작업을 진행한다.

전환 전 확인:

1. 현재 작업을 커밋·푸시해 정지 상태를 고정한다
2. `git status` 클린을 확인한다
3. `git worktree add`로 다음 작업을 착수한다

⛔ **`checkout`으로 브랜치만 갈아타지 않는다.** 작업 트리를 공유하면 검증 중 주입한 임시 변경이 다음 작업에 그대로 섞일 수 있다. 워크트리는 물리적으로 분리돼 이 문제가 성립하지 않는다.

담당 교체나 기존 워크트리를 인계받을 때는 **첫 명령으로 `git status` + 대상 커밋 해시 대조**를 한다 — 이전 작업의 잔여물을 그대로 물려받으면 판단이 뒤집힐 수 있다.

## 규칙이 잡지 못하는 것 — 배정으로 막는다

**자동 병합이 조용히 성공하는 의미 충돌**은 위 절차가 잡지 못한다. 두 팀이 같은 공용 파일에 각자 항목을 추가하면 git은 깨끗하게 합치지만 순서가 틀릴 수 있다. 이건 규칙이 아니라 **배정 관행**으로 막는다 — 같은 공용 파일을 크게 건드리는 이슈 둘을 동시에 진행하지 않는다. 마지막 그물은 병합 직전 전체 게이트다.

접촉이 몰리는 파일(과거 실측 기준 — 새 작업에서 갱신될 수 있다):

| 파일 |
| --- |
| `packages/i18n/src/ko.ts` |
| `apps/web/src/routes/index.tsx` |
| `apps/web/src/app/layout.tsx` |
| `packages/api-client/src/generated/api.d.ts` |

화면 슬라이스 내부는 디렉터리가 갈려 있어 팀 간 충돌이 나지 않는다.

## PR 리뷰 — 병합 전 최종 검증

개발 완료 후 PR을 올리면 `crefle-agent-skills:pr-review` 스킬로 최종 검증한다. 번호로 지정된 GitHub PR 리뷰도 같은 스킬을 쓴다. 이 하네스는 별도 리뷰 담당을 두지 않는다 — 독립 검증([verification-levels.md](verification-levels.md))과 PR 리뷰는 서로 다른 단계다.

pr-review에서 병합되지 못하고 개선 사항이 확인되면, 개선한 뒤 다시 PR을 올리고 재검증받는다.

## 다른 개발팀과 직접 소통하지 않는다

운영 규칙 §2-4.1 — 필요한 소통은 전부 설계팀과 한다. 다른 팀의 PR·이슈에 코멘트를 남기거나 작업을 조율하지 않는다. 충돌·순서 문제가 생기면 위 절차(선착순·워크트리 대기)로 자체 해소하고, 설계 수준의 조율이 필요하면 [review-request.md](review-request.md)로 설계팀에 올린다.
