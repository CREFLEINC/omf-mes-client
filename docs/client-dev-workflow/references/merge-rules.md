# 병합 규칙

`main`은 병합된 결과만 담고 항상 테스트 가능한 상태를 유지한다. 각 팀은 물리적으로 분리된 전용 워크트리와 팀 번호가 드러나는 브랜치에서 작업한다.

## PR 단위

- 하나의 명확한 목표와 되돌릴 수 있는 단위로 구성한다.
- 자동 생성물과 제품 코드처럼 검증·복구 방식이 다른 변경은 가능하면 분리한다.
- 다른 팀과 겹칠 가능성이 큰 공용 파일은 필요한 최소 범위만 수정한다.

고정된 줄 수 상한이나 종료된 기간 한정 예외는 두지 않는다. 변경 위험과 리뷰 가능성을 기준으로 나눈다.

## 최신 main 반영

PR 전과 병합 직전에 원격 상태를 확인하고 최신 `origin/main`을 반영한다. 사용자 변경을 덮어쓰지 않으며, 공유 브랜치에는 무조건 force push하지 않는다.

```bash
git fetch origin
git rebase origin/main
pnpm workflow:check
```

rebase로 이미 공개한 커밋을 다시 썼다면 `--force-with-lease`만 사용한다.

## 충돌 처리

| 대상                                         | 처리                                                          |
| -------------------------------------------- | ------------------------------------------------------------- |
| 일반 소스                                    | 양쪽 의도를 확인해 직접 해소하고 관련 테스트 재실행           |
| `packages/api-client/src/generated/api.d.ts` | 손 병합하지 않고 고정된 설계 계약에서 `pnpm gen:api`로 재생성 |
| `pnpm-lock.yaml`                             | 손 병합하지 않고 `pnpm install`로 재생성                      |

충돌 해소가 현재 업무 범위를 실질적으로 넓히면 사용자에게 알리고 승인을 받는다.

## 다른 팀과 겹칠 때

다른 개발팀에 직접 연락하거나 작업 순서를 지시하지 않는다. 이슈의 팀·상태 라벨과 PR 생성 시각을 보고 충돌이 적은 다른 일을 스스로 선택한다. 동일 변경이 이미 진행 중이면 중복 구현하지 않는다.

의미 충돌이 의심되면 자신의 이슈에 위험을 공개하고 독립된 워크트리에서 다른 작업을 계속한다. 설계 판단이 필요한 경우에는 [design-request.md](design-request.md)의 사용자 경유 절차를 따른다.

## 병합 전

1. `pnpm workflow:check`
2. 변경 위험에 맞는 최종 검증
3. 공개 저장소 금지 정보 포함 여부 확인
4. PR 리뷰 반영
5. 병합 가능 상태 확인 후 병합

특정 리뷰 스킬이나 에이전트 제품을 필수로 두지 않는다. 사용 가능한 리뷰 수단으로 실제 diff와 검증 결과를 확인한다.
