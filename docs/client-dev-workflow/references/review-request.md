# 검토 요청 — 설계팀에 보내는 통지

운영 규칙 §2-3의 실행 절차다. 개발 업무 중 설계 내용에 의문이 들거나 개선이 필요한 부분이 확인되면, 혼자 정하지 말고 설계팀에 검토를 요청한다.

## 언제 올리는가

- 스펙과 계약(OpenAPI)이 서로 어긋난다
- 미결 항목의 처리 방법이 적혀 있지 않다
- 화면 상태값·enum이 「예시 하나」인지 「전부」인지 문서에서 판별할 수 없다
- 그 밖에 설계 결정이 필요한데 우리 권한 밖인 지점(운영 규칙 §2-4.4가 우리 권한으로 남긴 것 — 코드 수준 설계·처리 순서·검증 방법 — 은 여기 해당하지 않는다)

**어긋남을 발견했다고 혼자 한쪽을 골라 조용히 구현하지 않는다.** `docs/uiux-handoff.md` §1의 세 사례가 전부 이 지점에서 실제로 사고가 났다.

## 어디에 올리는가

**설계 저장소**(`CREFLEINC/omf-mes`, 비공개)다. 이 저장소(공개)가 아니다 — 검토 요청에는 스펙 본문을 인용해야 할 때가 많고, 그것을 공개 저장소에서 하면 사고이기 때문이다.

## 제목·라벨

- 제목 접두: **`[검토 요청]`**
- 라벨: `Agent : T4` + `Agent : Client` (라벨이 없으면 [issue-lifecycle.md](issue-lifecycle.md)의 라벨 신설 절차)

```bash
gh issue create --repo CREFLEINC/omf-mes \
  --title "[검토 요청] <무엇이 어긋났는지 한 줄>" \
  --label "Agent : T4" --label "Agent : Client" \
  --body-file <본문 파일>   # templates/review-request-body.md 양식
```

## 본문에 담을 것

`templates/review-request-body.md` 양식을 쓴다. 핵심 네 가지:

1. **어느 화면/계약인가** — 화면 ID·엔드포인트
2. **무엇이 어긋났는가** — 실측 결과(스펙은 이렇게 읽히는데, 계약은 이렇다)
3. **우리가 지금 어떻게 처리 중인가** — 착수 이슈가 보류 중이면 그 사실, 임시로 어느 쪽을 따라 진행 중이면 그 사실과 이유
4. **무엇을 정해 주면 되는가** — 설계팀이 판단해야 할 지점을 좁혀서 묻는다. 「어떻게 할까요」보다 「A와 B 중 계약대로 A가 맞습니까」가 빠르다

설계 저장소는 비공개이므로 여기서는 스펙 본문 인용이 허용된다 — 클라이언트 저장소(공개)로는 절대 옮기지 않는다.

## 등록 후

- 클라이언트 저장소의 원래 이슈에 요청 번호를 남긴다: `[검토 요청] omf-mes#<번호>`
- 그 자리에서 작업을 계속할 수 없으면 [issue-lifecycle.md](issue-lifecycle.md)의 보류 절차(`in progress` → `help wanted`)를 적용하고 다른 이슈로 전환한다

## 처리 상황 추적 — 착수 전 매번 확인

새 이슈에 착수하기 전에 **내가 올린 검토 요청 중 열려 있는 것**과 **방금 닫힌 것**을 확인한다.

```bash
gh issue list --repo CREFLEINC/omf-mes --label "Agent : T4" --label "Agent : Client" --state all --search "[검토 요청] in:title"
```

- **열려 있으면** — 그 요청으로 보류된 클라이언트 이슈가 있는지 확인하고, 없으면 그대로 대기
- **닫혔으면** — 코멘트에 **「개발팀에 전달사항」**으로 시작하는 코멘트가 있는지 확인한다(설계팀 운영 규칙 §1-2가 그 형식을 요구한다). 있으면 내용을 반영해 보류 중인 클라이언트 이슈를 재개한다([issue-lifecycle.md](issue-lifecycle.md) 재개 절차)
- 코멘트 형식이 다르거나 내용이 불충분하면 짐작하지 말고 같은 이슈에 후속 질문을 남긴다
