# 정보 요청·설계 개선 절차

개발팀이 설계 정보의 오류·누락을 발견하거나 요구사항 달성을 위해 설계 요소의 개선이 필요할 때 사용한다.

## 허용되는 요청

- **정보 요청**: 설계 자료의 오류, 누락, 서로 맞지 않는 정보를 확인해야 할 때
- **설계 개선**: 명시된 기능·비기능 요구사항을 달성하려면 설계 요소 변경이 필요할 때

코드 구조, 구현 순서, 테스트 방식처럼 개발팀 권한인 결정은 요청 대상이 아니다.

## 직접 소통 금지

- 설계 저장소에 직접 이슈·PR·코멘트를 만들지 않는다.
- 설계팀 또는 다른 개발팀에 직접 메시지를 보내지 않는다.
- 요청서를 사용자에게 보여 주고 전달을 부탁한다.

## 요청서

[templates/design-request.md](../templates/design-request.md)를 사용한다. 요청서에는 현재 고정한 설계 커밋, 대상 자료, 관찰한 문제, 제품 영향, 필요한 답변을 적는다.

요청서에는 비공개 설계 내용이 포함될 수 있으므로 `.client-dev/requests/` 같은 로컬 전용 경로에 두고 커밋하지 않는다.

## 요청 후 작업

요청을 만들었다는 이유로 업무를 대기하지 않는다. 현재 고정 설계를 기준으로 안전하게 진행할 수 있는 구현·테스트·다른 이슈를 계속한다. 임의의 새 설계 결정을 코드에 굳히지는 않는다.

정말로 결정 없이는 진행할 수 없는 좁은 지점만 보류하고, 나머지 범위는 분리한다.

## 공개 추적 이슈

사용자가 요청서를 전달했고 **회신을 기다리라**고 한 경우에만 자신의 저장소에 추적 이슈를 만든다. 공개 이슈에는 아래만 적는다.

- 요청 종류
- 대상 화면 ID·문서 경로 같은 포인터
- 사용자 전달일
- 관련 작업 이슈
- 상태

요청서 본문이나 설계 자료의 상세 내용은 적지 않는다.

## 답변 처리

사용자가 답변서를 전달하면 고정 설계와의 관계를 확인한다.

- 답변이 설계 변동 공지를 가리키면 공지의 지정 커밋으로 기준을 갱신하고 모든 진행 계획을 재검토한다.
- 설명만 보완하고 설계 버전이 바뀌지 않으면 현재 고정 커밋을 유지한다.
- 반영 결과를 추적 이슈에 포인터 중심으로 남기고 닫는다.
