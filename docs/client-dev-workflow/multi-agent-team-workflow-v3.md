# 멀티 에이전트 개발 워크플로 V3

이 문서는 OMF-MES 클라이언트 개발팀의 업무 규칙과 개발 절차를 정의하는 유일한 정본이다. 특정 AI 제품·모델·스킬에 종속되지 않는다. `AGENTS.md`와 `CLAUDE.md`는 이 문서를 기초로 각 개발자가 로컬에서 생성하고 개인 노하우를 덧붙이는 도구별 어댑터이며 저장소에 커밋하지 않는다.

## 1. 목표와 우선순위

1. 설계 결과가 요구하는 제품을 구현한다.
2. 팀 간 업무 의존성·직접 소통·병합 충돌을 최소화한다.
3. 각 팀의 업무 영역과 현재 상태를 공개 이슈로 투명하게 관리한다.
4. 개발팀은 코드 수준 설계, 구현 순서, 검증 방법을 스스로 결정한다.
5. 사용자 또는 상위 지침이 이 문서와 충돌하면 상위 지침을 따르고 충돌 사실을 알린다.

## 2. 팀과 업무 경계

- **설계팀**: 고객 요구, 제품 방향, 화면·기능·API 요구사항과 설계 결과를 관리한다. 설계 변동 공지의 형식·작성·발행을 소유한다.
- **백엔드 개발팀**: 데이터 모델링, API 서버, DB 구성을 담당한다.
- **클라이언트 개발팀**: 웹, 데스크톱, 모바일 등 사용자가 직접 사용하는 GUI 소프트웨어를 담당한다.

설계 결과물은 모든 개발팀이 달성해야 할 제품 요구사항의 정본이다. 각 팀은 본인의 업무를 스스로 선택하고 처리하며 다른 팀에 업무를 배정·재배정하거나 구현 방법을 지시하지 않는다. 같은 분야의 하위 팀끼리도 직접 조율하지 않고 공개 이슈의 담당·상태를 보고 충돌을 피한다.

## 3. 프로젝트 기술 경계

이 저장소는 React + TypeScript 코드 한 벌에서 관리웹, Electron POP, Capacitor Android 셸을 만든다. 도메인 타입·검증 규칙·API 클라이언트·디자인 토큰·i18n·outbox는 공유하고 폼팩터 분기는 진입점과 레이아웃 수준으로 제한한다.

- `apps/web`: 관리웹 및 POP 셸
- `apps/mobile`: 모바일 셸
- `packages/domain`: 업무 개념·상태 전이·검증
- `packages/api-client`: OpenAPI 계약 클라이언트
- `packages/ui`: 표현 전용 공용 부품
- `packages/i18n`: 다국어 리소스
- `tools/mock`: 고정 설계 계약 기반 목 서버

공개 API·계약, 인증·권한·개인정보, 배포 파이프라인, 데이터 마이그레이션, 대규모 삭제처럼 요청 범위를 실질적으로 넓히는 변경은 별도 사용자 승인을 받는다.

## 4. 공개 저장소 경계

이 클라이언트 저장소는 공개다. 코드뿐 아니라 커밋 메시지, PR, 이슈, 주석, 테스트 픽스처, 설정과 생성물에도 같은 경계를 적용한다.

허용되는 정보:

- MES 일반 업무 용어
- 화면 ID, 라우트, 컴포넌트명 같은 내부 식별자
- 화면 라벨과 검증 메시지
- 직접 만든 합성 테스트 데이터
- 비공개 자료의 커밋·경로·이슈 번호 같은 포인터

금지되는 정보:

- 고객사명, 위치, 부서, 담당자 실명과 조직 정보
- 계약·견적·실제 납기 정보
- 실제 사번, 품목·LOT·거래처 코드 같은 실 운영 값
- IP, 호스트, 포트, 계정, 인증서와 접속 문자열
- 고객 ERP 스키마
- 비공개 설계·기획 문서의 본문, 발췌, 요약
- 와이어프레임, 화면 캡처, 비공개 워크플로 도식

의심스러우면 커밋하지 않고 사용자에게 확인한다. 이미 공개 원격에 올렸다면 즉시 알리고, 히스토리 재작성이나 force push로 조용히 숨기지 않는다.

## 5. 개인 AI 환경 부트스트랩

실행 파일은 `tools/workflow/bootstrap.mjs`다. 패키지 명령은 다음과 같다.

```bash
pnpm workflow:bootstrap --tool <codex|claude|both> --team <번호>
```

부트스트랩은 이 문서 전체와 버전·해시·담당 팀을 포함하는 로컬 `AGENTS.md` 또는 `CLAUDE.md`를 생성한다. 두 파일은 Git 비추적 대상이다. 관리 블록 밖의 `개인별 AI 도구 설정` 구역에는 개인 노하우, 도구별 명령, 선호 모델이나 스킬을 추가할 수 있지만 이 문서의 필수 규칙을 무효화할 수 없다.

이미 부트스트랩으로 만든 파일은 다시 실행하면 개인 설정을 보존하면서 관리 블록만 최신화한다. 출처를 확인할 수 없는 기존 파일은 보호를 위해 덮어쓰지 않으며, 의도적으로 교체할 때만 `--force`를 사용한다.

## 6. 최초 개발환경 구성

팀별 전용 워크트리와 브랜치를 만들고 격리된 설계 참조 클론을 준비한다. 팀 번호는 사용자가 배정한 값만 사용하며 추측하지 않는다.

```bash
git worktree add -b <도구접두>/team<N>-<작업> <전용-워크트리> origin/main
pnpm install
pnpm workflow:bootstrap --tool <codex|claude|both> --team <N>
gh repo clone CREFLEINC/omf-mes .client-dev/design/omf-mes -- --single-branch --branch main
pnpm workflow init --team <N> --issue <이슈번호> --design-ref .client-dev/design/omf-mes
pnpm workflow:check
```

`.client-dev/`에는 팀 번호, 활성 이슈, 설계 고정 버전, 비공개 요청서와 설계 참조 클론을 둔다. 이 디렉터리와 로컬 AI 어댑터는 커밋하지 않는다.

## 7. 작업 선택과 공개

각 팀은 사용자 요청과 공개 이슈를 보고 본인 업무를 스스로 선택한다. 사용자 요청에 대응하는 이슈가 없으면 공개 가능한 제목과 요약으로 자신의 개발 저장소에 이슈를 만든다.

작업 시작 시 다음을 표시한다.

- `Agent : T{번호}`
- `Agent : Client`
- `in progress`
- 현재 GitHub 사용자 담당자 지정

```bash
gh issue edit <번호> \
  --repo CREFLEINC/omf-mes-client \
  --add-label "Agent : T<번호>" \
  --add-label "Agent : Client" \
  --add-label "in progress" \
  --add-assignee @me
pnpm workflow set-issue --issue <번호>
pnpm workflow:check
```

과거 `uiux→client`, `ready` 라벨은 이력 보존 전용이며 신규 착수·승인·공지에 사용하지 않는다.

## 8. 설계 기준 고정

개발을 시작하면 `.client-dev/state.json`에 기록된 설계 커밋만 읽는다. 작업 착수마다 설계 클론을 fetch, pull, reset하거나 다른 커밋으로 이동하지 않는다. 다른 팀이나 설계팀이 사용하는 로컬 체크아웃을 직접 읽지 않는다.

`pnpm workflow:check`는 설계 참조 HEAD와 고정 커밋이 다르면 실패한다. API 타입과 목 서버도 이 고정 참조본을 기본 입력으로 사용한다.

## 9. 정보 요청과 설계 개선

허용되는 요청은 다음 두 종류다.

- **정보 요청**: 설계 자료의 오류, 누락, 불일치를 확인해야 하는 경우
- **설계 개선**: 기능·비기능 요구사항을 달성하려면 설계 요소의 변경이 필요한 경우

설계팀이나 다른 개발팀에 직접 메시지·이슈·PR·코멘트를 보내지 않는다. `docs/client-dev-workflow/templates/design-request.md`로 요청서를 작성해 사용자에게 전달을 부탁한다. 요청서는 `.client-dev/requests/`에 두고 커밋하지 않는다.

요청 후에도 현재 고정 설계를 기준으로 구현·테스트·다른 이슈를 계속한다. 결정 없이는 진행할 수 없는 최소 지점만 분리해 보류한다. 사용자가 요청서를 전달했고 **회신을 기다리라**고 지시한 경우에만 자신의 개발 저장소에 공개 추적 이슈를 만든다. 공개 이슈에는 요청 종류, 대상 포인터, 전달일, 관련 작업 이슈와 상태만 남긴다.

사용자가 답변서를 전달하면 반영 결과를 기록하고 추적 이슈를 닫는다. 답변이 설계 변동 공지를 가리키면 아래 절차를 따른다.

## 10. 설계 변동 공지

개발팀이 직접 수신할 수 있는 설계팀 통지는 모든 개발팀을 대상으로 한 설계 변동 공지뿐이다. 공지 형식·작성·발행은 설계팀이 소유한다. 개발팀은 형식을 정의·보완하거나 백엔드·클라이언트별 공지로 재작성하지 않는다. 개발 저장소에 공지 또는 영향 검토 이슈 템플릿을 만들지 않는다.

공지를 받으면:

1. 공지가 지정한 커밋만 격리 설계 클론에 가져와 정확히 체크아웃한다.
2. 설계 저장소의 공통 공지 참조와 지정 커밋을 기록한다.
3. `pnpm workflow:check`를 실행한다.
4. 모든 진행 업무의 계획, 코드 설계, 구현, 테스트 영향을 전면 재검토한다.
5. 공개 가능한 공지 포인터와 결과는 현재 작업 이슈에, 비공개 분석은 로컬 계획에 기록한다.

```bash
git -C .client-dev/design/omf-mes fetch origin <공지커밋>
git -C .client-dev/design/omf-mes checkout --detach <공지커밋>
pnpm workflow accept-design-change \
  --notice-ref <설계저장소-공통공지-URL|CREFLEINC/omf-mes#번호> \
  --commit <공지전체커밋> \
  --design-ref .client-dev/design/omf-mes
pnpm workflow:check
```

## 11. 계획과 구현

`docs/client-dev-workflow/templates/plan.md`를 기준으로 목표, 완료 조건, 영향 범위, 코드 수준 설계, 되돌릴 수 있는 작업 단위와 검증 계획을 정한다. 공개될 수 있는 계획에는 비공개 설계 내용을 적지 않고 상세 계획은 `.client-dev/`에 둔다.

설계 요구를 충족하는 코드 구조, 네이밍, 구현 순서와 테스트 방식은 개발팀이 결정한다. 기존 사용자 변경과 다른 팀의 작업을 보존하고, 범위 밖 변경이나 관련 없는 정리를 섞지 않는다.

## 12. 검증 수준

검증 비용은 변경 위험에 비례시킨다. 판단이 갈리면 높은 수준을 적용하고 수행·생략한 검증과 이유를 공개한다.

| 수준 | 기준                                                   | 최소 검증                                                   |
| ---- | ------------------------------------------------------ | ----------------------------------------------------------- |
| 낮음 | 문구·스타일·문서·테스트 보강·비동작 정리               | 워크플로 검사, 포맷, 관련 정적 검사·단위 테스트, diff 확인  |
| 보통 | 화면 하나의 조회·입력, 기존 패턴 기능, 국소 버그       | 낮음 + 타입 검사 + 관련 패키지 테스트 + 핵심 경로 실제 실행 |
| 중요 | API 계약, 인증·권한, 데이터 손실, 상태 전이, 공용 동작 | 보통 + 전체 테스트·경계 검사 + 정상·오류 경로 실제 실행     |

주요 명령:

| 대상          | 명령                               |
| ------------- | ---------------------------------- |
| 업무 상태     | `pnpm workflow:check`              |
| 저장소 정책   | `pnpm workflow:repo-check`         |
| 하네스 테스트 | `pnpm test:workflow`               |
| 타입          | `pnpm typecheck`                   |
| 전체 테스트   | `pnpm test`                        |
| 패키지 테스트 | `pnpm --filter <패키지명> test`    |
| 의존 방향     | `pnpm dep:check`                   |
| 계약·목 서버  | `pnpm mock:smoke`                  |
| 생성 API 경계 | `pnpm check:generated`             |
| 빌드          | `pnpm --filter @omf-mes/web build` |

동작 변경은 가능한 경우 실제 앱과 목 서버를 실행해 핵심 경로를 확인한다. 기존 실패와 신규 실패를 구분하고 새 감지기는 의도적 결함을 실제로 잡는지 확인한다.

## 13. 디자인 시스템

UI는 `@crefle/web-ui`와 디자인 시스템의 컴포넌트 인벤토리를 우선 사용한다.

- 기존 컴포넌트가 그대로 있으면 사용한다.
- 필요한 변형이나 prop이 부족하면 공개 경계를 지킨 컴포넌트 언어로 DS 개선을 요청한다.
- 기존 컴포넌트의 조합은 제품 저장소가 소유한다.
- 새 원시 요소는 제품에서 먼저 검증하고 세 번째 사용처가 생길 때 DS 승격을 검토한다.

DS 이슈에도 제품 화면명, 고객사명, 와이어프레임이나 화면 캡처를 붙이지 않는다.

## 14. PR과 병합

PR은 하나의 명확하고 되돌릴 수 있는 목표로 구성한다. 최신 `origin/main`을 반영하고 관련 검증을 다시 실행한다.

```bash
git fetch origin
git rebase origin/main
pnpm workflow:check
```

공개 브랜치를 재배치했다면 `--force-with-lease`만 사용하고 공유 브랜치에는 force push하지 않는다. 충돌은 양쪽 의도를 확인해 해결하며 생성 API 타입과 잠금 파일은 정본 명령으로 재생성한다. 충돌 해결이 업무 범위를 넓히면 사용자 승인을 받는다.

PR을 생성한 뒤 리뷰와 검증 결과를 반영한다. 병합 여부는 해당 업무에서 사용자가 부여한 권한을 따른다. 특정 AI 모델·리뷰 스킬을 필수 조건으로 두지 않는다.

병합이 승인되고 완료되면 `docs/client-dev-workflow/templates/completion-report.md` 형식으로 결과를 남기고 `in progress`를 제거한 뒤 이슈를 닫는다. 병합하지 말라는 지시가 있으면 PR과 이슈를 열린 상태로 유지한다.

## 15. 도구별 개인 설정의 경계

개인은 생성된 `AGENTS.md` 또는 `CLAUDE.md`의 개인 설정 구역에 다음을 추가할 수 있다.

- 선호하는 AI 모델과 추론 수준
- 사용 가능한 스킬과 도구

- 편집기·터미널·브라우저 운용 노하우

개인 설정은 팀 역할, 직접 소통 금지, 설계 고정, 공개 저장소 경계, 사용자 승인 범위와 검증 의무를 완화하거나 뒤집을 수 없다. 도구별 파일 사이에 차이가 있더라도 공통 관리 블록의 버전과 해시는 같아야 한다.
