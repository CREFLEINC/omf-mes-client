# 다중 Agent Coding 팀 운영 — 팀 식별과 이슈 라벨

이 저장소를 여러 Agent Coding 팀이 동시에 쓸 때(같은 머신의 git 워크트리든, 완전히 분리된 다른 PC의 별도 clone이든) 서로 다른 이슈를 혼선 없이 배정받기 위한 절차의 **정본**이다. `agent-development-orchestrator` 스킬의 Phase 0가 이 문서를 참조한다.

과거 이 절차는 2번 팀 워크트리의 `TEAM-A2.md`(`.claude/_workspace/` 아래 — `.gitignore` 대상)에만 있었다. 그 파일은 어떤 clone·워크트리에도 함께 오지 않아 다른 팀이 규칙을 알 방법이 없었다. **이 문서가 그 자리를 대신한다.**

## 1. 팀 식별 — 로컬 마커 파일

- 경로: 저장소 루트의 `.claude/team.local`
- **git으로 추적하지 않는다** — 파일명이 기존 `.gitignore`의 `*.local` 패턴에 이미 걸리므로 별도 gitignore 설정이 필요 없다. 워크트리·clone마다 내용이 다른 게 정상이며, 그래서 이 파일 하나로는 팀을 특정할 수 없고 **각 워크스페이스가 자기 자신의 사본을 갖는다.**
- 내용: 이 워크스페이스가 속한 팀의 GitHub 라벨 문자열 한 줄. 예:
  ```
  Agent : T3
  ```
- 오케스트레이터(Phase 0)의 처리:
  - **파일이 있으면** 그 값을 이번 세션의 팀 라벨로 쓴다. 재질문하지 않는다.
  - **파일이 없으면 추측하지 않는다.** 사용자에게 직접 묻는다 — "이 워크스페이스는 몇 번째 팀입니까?"(기존 팀 라벨 목록은 `gh label list`로 보여준다). 답을 받으면 `.claude/team.local`을 만들어 저장한다.
- ⚠ **워크트리 설정 누수 방향에 주의한다.** 워크트리는 루트 저장소에 둔 파일이 하위 워크트리로 내려오는 방향으로만 샌다(반대는 아니다). `.claude/team.local`은 항상 **각자의 워크트리/체크아웃**에만 둔다 — 루트에 두면 다른 팀의 워크스페이스까지 같은 팀 번호로 오염된다.

## 2. GitHub 라벨 — 없으면 직접 만들어 쓴다

- 팀 라벨 형식: `Agent : T{n}`(n은 1부터 정수 순차). `in progress`·`ready`는 이미 있는 공용 라벨이라 새로 만들지 않는다.
- 이슈에 라벨을 붙이기 전에 존재를 확인한다: `gh label list --repo CREFLEINC/omf-mes-client`.
- **없으면 그 자리에서 만든다** — 승인을 기다리지 않는다(라벨 생성은 되돌리기 쉬운 저장소 메타데이터 조작이고, `CLAUDE.md`·정책 §14의 승인 필요 목록에 해당하지 않는다):
  ```bash
  gh label create "Agent : T{n}" --repo CREFLEINC/omf-mes-client --color <기존과 겹치지 않는 6자리 hex>
  ```
  색상은 `gh label list`로 기존 `Agent : T*` 라벨 색을 먼저 확인하고 겹치지 않는 임의 값을 고른다(2026-08-20 기준 `T1`=`178f72`·`T2`=`041d93`·`T3`=`051c46` — 새로 만들 때마다 최신값을 다시 조회한다, 이 문서의 값은 스냅샷일 뿐 정본이 아니다).
- 생성 권한이 없어 실패하면(저장소 쓰기 권한 없는 계정) 추측으로 진행하지 않고 중단해 사용자에게 보고한다.
- 생성 직후 `gh label list`로 재확인한다 — 생성 실패를 완료로 넘기지 않는다.

## 3. 담당자(Assignee) — 고정 계정이 아니라 매번 동적으로 조회

- 특정 GitHub 계정명을 하드코딩하지 않는다. **어떤 팀이든, 그 에이전트가 실제로 이 저장소에 접근할 때 쓰고 있는 GitHub 계정을 assignee로 쓴다** — 팀마다 다른 계정일 수 있다.
- 이슈 착수 직전에 조회한다:
  ```bash
  gh issue edit <이슈번호> --add-assignee @me --repo CREFLEINC/omf-mes-client
  ```
  `@me`는 `gh` CLI가 현재 인증된 계정으로 자동 치환한다. 계정명을 직접 알아야 하면 `gh api user --jq .login`.
- `gh auth status`가 미인증을 보고하면 담당자 지정 없이 착수하지 않는다 — 중단하고 사용자에게 보고한다(담당자 없는 이슈 착수는 다른 팀과의 혼선 위험이 있다).

## 4. 이슈 착수 절차 (요약)

1. `.claude/team.local` 확인(§1) — 없으면 만든다
2. 착수하려는 이슈에 **팀 라벨**(§2 — 없으면 생성)과 **담당자**(§3 — 동적 조회)를 부착
3. 실제 작업을 시작할 때 `in progress` 라벨을 추가
4. 병합·종결 시 `in progress` 라벨을 제거
5. `ready` 라벨은 uiux 설계팀이 「착수 가능」 표시로 쓰는 전용 라벨이므로 건드리지 않는다
6. 의존성이 높아 지금 시작하지 않고 자리만 맡아두는 이슈는 2번(라벨·담당자)까지만 하고 3번은 생략한다(예약 상태)
