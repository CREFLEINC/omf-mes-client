# 다중 Agent Coding 팀 운영 — 팀 식별과 이슈 라벨

이 저장소를 여러 Agent Coding 팀이 동시에 쓸 때(같은 머신의 git 워크트리든, 완전히 분리된 다른 PC의 별도 clone이든) 서로 다른 이슈를 혼선 없이 배정받고, 그 결과를 서로 막지 않고 병합하기 위한 절차의 **정본**이다. `agent-development-orchestrator` 스킬의 Phase 0가 이 문서를 참조한다.

과거 이 절차는 2번 팀 워크트리의 `TEAM-A2.md`(`.claude/_workspace/` 아래 — `.gitignore` 대상)에만 있었다. 그 파일은 어떤 clone·워크트리에도 함께 오지 않아 다른 팀이 규칙을 알 방법이 없었다. **이 문서가 그 자리를 대신한다.**

## 1. 팀 식별 — 로컬 마커 파일

- 경로: 저장소 루트의 `.claude/team.local`
- **git으로 추적하지 않는다** — 파일명이 기존 `.gitignore`의 `*.local` 패턴에 이미 걸리므로 별도 gitignore 설정이 필요 없다. 워크트리·clone마다 내용이 다른 게 정상이며, 그래서 이 파일 하나로는 팀을 특정할 수 없고 **각 워크스페이스가 자기 자신의 사본을 갖는다.**
- 내용: 이 워크스페이스가 속한 팀의 GitHub 라벨 문자열 한 줄. 예:
  ```
  Agent : T3
  ```
- 오케스트레이터(Phase 0)의 처리:
  - **파일이 있으면** 그 값을 이번 세션의 팀 라벨로 쓴다. 재질문하지 않는다.
  - **파일이 없으면 추측하지 않는다.** 사용자에게 직접 묻는다 — "이 워크스페이스는 몇 번째 팀입니까?"(기존 팀 라벨 목록은 `gh label list`로 보여준다). 답을 받으면 `.claude/team.local`을 만들어 저장한다.
- ⚠ **워크트리 설정 누수 방향에 주의한다.** 워크트리는 루트 저장소에 둔 파일이 하위 워크트리로 내려오는 방향으로만 샌다(반대는 아니다). `.claude/team.local`은 항상 **각자의 워크트리/체크아웃**에만 둔다 — 루트에 두면 다른 팀의 워크스페이스까지 같은 팀 번호로 오염된다.

## 2. GitHub 라벨 — 없으면 직접 만들어 쓴다

- 팀 라벨 형식: `Agent : T{n}`(n은 1부터 정수 순차). `in progress`·`ready`는 이미 있는 공용 라벨이라 새로 만들지 않는다.
- 이슈에 라벨을 붙이기 전에 존재를 확인한다: `gh label list --repo CREFLEINC/omf-mes-client`.
- **없으면 그 자리에서 만든다** — 승인을 기다리지 않는다(라벨 생성은 되돌리기 쉬운 저장소 메타데이터 조작이고, `CLAUDE.md`·정책 §14의 승인 필요 목록에 해당하지 않는다):
  ```bash
  gh label create "Agent : T{n}" --repo CREFLEINC/omf-mes-client --color <기존과 겹치지 않는 6자리 hex>
  ```
  색상은 `gh label list`로 기존 `Agent : T*` 라벨 색을 먼저 확인하고 겹치지 않는 임의 값을 고른다(2026-08-20 기준 `T1`=`178f72`·`T2`=`041d93`·`T3`=`051c46` — 새로 만들 때마다 최신값을 다시 조회한다, 이 문서의 값은 스냅샷일 뿐 정본이 아니다).
- 생성 권한이 없어 실패하면(저장소 쓰기 권한 없는 계정) 추측으로 진행하지 않고 중단해 사용자에게 보고한다.
- 생성 직후 `gh label list`로 재확인한다 — 생성 실패를 완료로 넘기지 않는다.

## 3. 담당자(Assignee) — 고정 계정이 아니라 매번 동적으로 조회

- 특정 GitHub 계정명을 하드코딩하지 않는다. **어떤 팀이든, 그 에이전트가 실제로 이 저장소에 접근할 때 쓰고 있는 GitHub 계정을 assignee로 쓴다** — 팀마다 다른 계정일 수 있다.
- 이슈 착수 직전에 조회한다:
  ```bash
  gh issue edit <이슈번호> --add-assignee @me --repo CREFLEINC/omf-mes-client
  ```
  `@me`는 `gh` CLI가 현재 인증된 계정으로 자동 치환한다. 계정명을 직접 알아야 하면 `gh api user --jq .login`.
- `gh auth status`가 미인증을 보고하면 담당자 지정 없이 착수하지 않는다 — 중단하고 사용자에게 보고한다(담당자 없는 이슈 착수는 다른 팀과의 혼선 위험이 있다).

## 4. 이슈 착수 절차 (요약)

1. `.claude/team.local` 확인(§1) — 없으면 만든다
2. 착수하려는 이슈에 **팀 라벨**(§2 — 없으면 생성)과 **담당자**(§3 — 동적 조회)를 부착
3. 실제 작업을 시작할 때 `in progress` 라벨을 추가
4. 병합·종결 시 `in progress` 라벨을 제거
5. `ready` 라벨은 uiux 설계팀이 「착수 가능」 표시로 쓰는 전용 라벨이므로 건드리지 않는다
6. 의존성이 높아 지금 시작하지 않고 자리만 맡아두는 이슈는 2번(라벨·담당자)까지만 하고 3번은 생략한다(예약 상태)
7. PR 등록부터 병합까지는 §5를 따른다

## 5. PR 리뷰·병합 규칙

여러 팀의 PR이 `main` 하나로 모인다. 아래 네 조는 그 합류 지점에서 서로를 막지 않기 위한 것이며 **발동 순서대로** 적었다.

⚠ **수정 회차 절차는 여기 없다.** 리뷰·검증에서 나온 지적을 합쳐 같은 PR에서 고치는 절차는 하네스(`.claude/skills/agent-development-orchestrator/SKILL.md` 10절)가 정본이다. 이 문서는 **팀 사이에서만 생기는 문제**를 다룬다.

### 5-1. 한 PR은 한 슬라이스로 유지한다

- 작업 단위는 하네스 권장 상한(생성 코드·잠금 파일 제외 400줄)을 넘기지 않는다.
- 등록에서 병합까지를 짧게 유지한다.

**충돌 창의 길이가 곧 충돌 확률이다.** 화면 1장이 PR 4~6개로 쪼개져 온 것이 지금까지 팀 간 충돌을 막아 온 실질적 장치다. 아래 세 조는 이 조가 지켜질 때만 가볍게 돈다.

### 5-2. PR 등록 직전에 `rebase` 하고 전체 게이트를 돌린다

```bash
git fetch origin && git rebase origin/main
# 전체 게이트 실행 — 명령 목록은 아래 정본을 본다
git push --force-with-lease
```

- PR이 열려 있는 동안 `main`이 움직였으면 **병합 직전에 한 번 더** 같은 절차를 밟는다.
- ⚠ `--force`가 아니라 `--force-with-lease`를 쓴다 — 남의 push를 지우지 않는다.
- 전체 게이트의 명령 목록은 `.claude/skills/agent-development-orchestrator/references/verification-policy.md` 「저장소 검증 명령」이 정본이다. 여기에 옮겨 적지 않는다 — 도구가 늘면 그 표만 고친다.

작업 브랜치는 룰셋 대상이 아니라 force push가 허용된다(보호 대상은 `main` 하나다 — 2026-08-20 확인). 하네스의 독립 리뷰는 **PR 코멘트를 게시하지 않으므로** rebase 가 리뷰 스레드를 낡게 만들지 않는다.

**이 조가 아래 두 조의 발동 빈도를 대부분 없앤다** — 충돌을 PR에 올라온 뒤가 아니라 로컬에서 끝낸다.

### 5-3. 충돌은 직접 해소하되, 생성물은 재생성으로만 푼다

| 대상                                         | 해소 방법                               |
| -------------------------------------------- | --------------------------------------- |
| 일반 소스                                    | 직접 해소                               |
| `packages/api-client/src/generated/api.d.ts` | ⛔ 손 병합 금지 — `pnpm gen:api` 재생성 |
| `pnpm-lock.yaml`                             | ⛔ 손 병합 금지 — `pnpm install` 재생성 |

- 해소 후 **전체 게이트를 다시 돌린다.** 해소는 새 커밋이다.
- 이슈 대응 범위 밖의 변경이 필요하면 **사용자 승인**을 받는다. 승인 주체는 리더 팀이 아니라 사용자다(정책 §14) — 이원화하면 하네스와 어긋난다.

자동 생성물을 손으로 합치면 어느 계약의 타입이 살았는지 알 수 없게 된다. 병합기가 조용히 덮지 않고 멈추도록 만든 것과 같은 이유다(`docs/decisions.md` #7).

### 5-4. 그래도 겹치면 선착순, 대기 측은 워크트리로 다음 작업

- 기준은 **PR 생성 시각**이다. 먼저 등록된 PR이 **병합될 때까지** 대기한다.
- 대기 중에 놀지 않는다. 다만 **브랜치를 갈아타지 말고 `git worktree add`로 분리**한다.

전환 전 확인:

1. 현재 작업을 커밋·푸시해 정지 상태를 고정한다
2. 뮤턴트 복원을 확인한다 — `shasum` 대조 + `git status` 클린
3. 진행 중인 검증·리뷰 담당을 정리한다(보고서 회차 번호 확정)
4. `git worktree add`로 다음 작업을 착수한다

⛔ **`checkout`으로 브랜치만 갈아타면 안 된다.** 작업 트리를 공유하므로 검증 담당이 주입한 뮤턴트가 남은 트리를 그대로 물려받는다 — 하네스가 「인계 시 첫 명령은 `git status` + 커밋 해시 대조」를 못 박은 근거가 그 오염 인계 실증이다. 워크트리는 물리적으로 분리돼 그 사고가 성립하지 않는다.

### 5-5. 규칙이 잡지 못하는 것 — 배정으로 막는다

**자동 병합이 조용히 성공하는 의미 충돌**은 위 네 조가 잡지 못한다. 두 팀이 사이드바에 각자 항목을 추가하면 git 은 깨끗하게 합치지만 순서가 틀릴 수 있다. 텍스트 충돌이 아니라 5-4 가 발동하지 않는다.

이건 규칙이 아니라 **배정 관행**으로 막는다 — 같은 공용 파일을 크게 건드리는 이슈 둘을 동시에 배정하지 않는다. 마지막 그물은 병합 직전 전체 게이트다.

접촉이 몰리는 파일은 넷이다(최근 60 PR 커밋 실측 · 2026-08-20).

| 파일                                         |  등장   |
| -------------------------------------------- | :-----: |
| `packages/i18n/src/ko.ts`                    | 51 / 60 |
| `apps/web/src/routes/index.tsx`              |   10    |
| `apps/web/src/app/layout.tsx`                |    9    |
| `packages/api-client/src/generated/api.d.ts` |    5    |

화면 슬라이스 내부는 디렉터리가 갈려 있어 팀 간 충돌이 나지 않는다.
