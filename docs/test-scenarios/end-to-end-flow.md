# 절차 시험 — 기기 등록부터 제품 출하까지

**목적** — 화면 하나씩이 아니라 **일이 흘러가는 순서대로** 따라가며 확인한다. 앞 단계가 만든
것을 다음 단계가 받아 쓰므로, 화면 단위 시험이 통과해도 사슬이 끊어져 있으면 여기서 드러난다.

기존 `master-data.md`·`material-warehouse.md`·`production-execution.md` 는 화면 단위 QA 표다.
이 문서는 그것을 대체하지 않고 **세로로 한 번 꿰는** 쪽을 맡는다.

> **이 저장소는 공개다.** 아래 값은 전부 로컬 개발 서버의 합성 데이터다. 실 품목코드·LOT·
> 거래처·고객사명·사번·주소를 이 문서에 적지 않는다.

## 실행 환경

| 자리 | 무엇 | 주소 |
| --- | --- | --- |
| 백엔드 | 로컬 개발 서버 | `127.0.0.1:3100` (경로 접두 `/api`) |
| 관리자 웹 | `apps/web` 개발 서버 | `http://localhost:5174` |
| PDA | PM95 실기 · 디버그 APK | `adb reverse` 로 단말의 `127.0.0.1:3100` 을 이 기계로 |

띄우는 명령이다. 백엔드는 다른 세션이 띄워 둔 것을 쓴다.

```bash
# 관리자 웹
pnpm --filter @omf-mes/web dev --port 5174

# PDA 에 올리기 (덮어 설치라 등록이 남는다)
bash <잡 디렉터리>/build-local-backend-3100.sh
```

관리자 웹은 **세션 쿠키**로, PDA 는 **단말 토큰**으로 인증한다. 축이 다르므로 한쪽이 되어도
다른 쪽이 된다는 뜻이 아니다.

### 사람이 해야 하는 것

- **관리자 웹 로그인** — 비밀번호가 필요하다. 에이전트는 비밀번호를 넣지 않는다.
- **PDA 스캔** — 카메라·스캐너로 읽는 동작. 화면이 요구하는 자리에서 사람이 읽힌다.

## 끊긴 자리

절차를 따라가면 지금 두 곳에서 멈춘다. 둘 다 클라이언트가 고칠 자리가 아니다.

### 고친 자리 — 기기 등록 (2단계)

앱은 QR 의 토큰을 저장한 직후 서버가 그 토큰을 받아 주는지 확인한다(`M-CO-01` §6 이 등록을
온라인 전용으로 둔 이유). 그 확인을 단말 상세 조회로 하고 있었는데, 모바일 단말 토큰으로
부르면 401 이 온다(실측). 검증이 실패하면 앱이 저장한 토큰을 지우므로 **어떤 QR 로도 등록이
끝나지 않았다.**

지금은 이렇게 한다.

- 토큰이 사는지는 **모바일에 열려 있는 조회**로 확인한다. 200 자체가 서버가 받아들였다는
  증명이다. 등록 직후 어차피 받아야 하는 작업자 목록을 쓴다.
- 단말 코드와 공장은 **토큰 클레임**에서 읽는다.
- 코드가 안 실려 오면 등록을 막지 않고 **대조 표시만 생략한다.** 대조는 편의고 등록은
  필수다.
- 공장이 없으면 등록을 세우지 않는다. 확인 조회를 부를 수 없고, 쓰기 화면이 첫 저장에서
  막히기 때문이다.

⚠ **계약이 토큰 클레임 규격을 아직 갖고 있지 않다.** 서버는 이미 `terminalCode`·`plantId` 를
싣고 있지만 계약에 적힌 자리가 없어, 설계팀에 규격 명시를 요청해 둔 상태다. 회신이 다른
방향이면 이 자리를 다시 고친다.

### 끊긴 자리 2 — 피킹 지시가 생기지 않는다 (10·11단계)

`GET /logistics/picking-orders` 는 정상이지만 **목록이 늘 비어 있다.** 피킹 지시를 만드는
오퍼레이션이 서버에도 계약에도 없다. 자재 출고요청은 배포 때 자동으로 서지만 거기서 피킹
지시를 만들지 않는다.

- **10단계 자재 출고·피킹** — 대상이 없어 늘 빈 목록이다.
- **11단계 생산창고 입고** — 전표를 스캔하면 화면이 원천 유형을 보지 않고 **무조건** 피킹
  지시를 따라간다. 피킹에서 나오지 않은 전표를 스캔하면 그 조회가 실패한다.

11단계는 피킹에서 나온 전표라면 정상으로 돈다. 그런 전표가 생기려면 10단계가 먼저 돌아야
하므로, 결국 같은 자리에 묶여 있다.

## 시험 전 점검

시작하기 전에 아래가 서 있는지 본다. 하나라도 비면 그 단계에서 빈 화면을 보게 되고, 고장인지
할 일이 없는 것인지 가릴 수 없다.

| 무엇 | 어디서 | 없으면 |
| --- | --- | --- |
| 시험용 단말 | 웹 `/system/terminal-process-map` | 2단계 QR 을 못 낸다 |
| 숫자 사번 작업자 | 웹 기준정보 | 3단계를 못 지나간다 |
| 공급사·품목·발주 | 웹 `/logistics/po-register` | 5단계 고를 것이 없다 |
| LOT 이 안 붙은 입하 라인 | 5단계가 만든다 | 6단계가 401 로 떨어진다 |
| `IQC_SKIP` 결재선 + 단계 | 웹 `/system/approval-route` | 7-b 가 `ROUTE_NOT_FOUND` |
| 적치 규칙 | 웹 `/master-data/putaway-rule` | 8단계가 늘 임시 적치로 간다 |
| 설비 점검 항목 | 웹 `/equipment/master` | 설비 점검 화면이 빈다 |
| 불량 코드 | 웹 `/master-data/defect-cause-code` | 수리 왕복에서 이름이 안 뜬다 |
| 오늘 날짜 출하 요청 | 웹 14단계 | 15단계 화면이 빈다 |

## 고칠 때

화면이 바뀌면(필드·문구·검증 규칙) 이 문서도 함께 고친다. 낡은 시나리오는 실제와 다른 것을
「기대 결과」로 남겨 오히려 해가 된다.
