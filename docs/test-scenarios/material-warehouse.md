# 자재/창고 관리 사용자 테스트 시나리오

**목적** — 개발이 끝난 화면을 실제로 실행해 사람이 손으로 확인하는 시나리오다. 둘로 쓴다.

1. **자동화**: 브라우저 자동화 Agent가 이 표를 따라 프로그램을 조작하고 「기대 결과」와 실제 화면을 대조한다.
2. **QA 전달**: 품질 담당팀이 같은 표를 손으로 따라 하며 테스트 케이스로 쓴다.

작성 시점 이후 화면이 바뀌면(필드·문구·검증 규칙) 이 문서도 함께 고친다 — 낡은 시나리오는 실제 화면과 다른 것을 「기대 결과」로 남겨 오히려 해가 된다.

> **이 저장소는 공개(public)다.** 아래 테스트 데이터는 전부 지어낸 합성값이며, 화면 슬라이스의 `fixtures.ts`가 이미 쓰는 계열(`SAMPLE-`·`SYN-` 등)을 그대로 재사용했다. 실 품목코드·LOT 번호·창고 코드·거래처·고객사명·인프라 정보를 이 문서에 적지 않는다(루트 `CLAUDE.md`).

## 실행 환경

| 환경 | 실행 | 기준 URL | 특징 |
| --- | --- | --- | --- |
| 목 서버(Prism) | `pnpm mock` (별도 터미널) | `http://127.0.0.1:4010` | 계약 example을 그대로 돌려준다. **상태가 없다** — 등록·저장 후 목록에 반영되는지, 상태 전이, 잠금 충돌(409)은 검증할 수 없다 |
| 관리웹 | `pnpm --filter @omf-mes/web dev` | `http://localhost:5173`(포트 점유 시 5174…) | 기본 API 기준 URL이 목 서버(`127.0.0.1:4010`)다. 실서버로 붙이려면 `VITE_API_BASE_URL=http://localhost:3100/api pnpm --filter @omf-mes/web dev` |
| 모바일(웹) | `pnpm --filter @omf-mes/mobile dev` | Vite 개발 서버 | 카메라·보안저장소 등 네이티브 기능은 미동작. 스캔은 **키보드웨지**(하드웨어 스캐너가 키 입력으로 들어오는 방식)이므로 웹 브라우저에서 값을 입력하고 Enter를 눌러도 재현된다 |
| 실서버(`omf-mes-server`) | `docker compose up -d && pnpm exec prisma migrate deploy && pnpm run db:seed && pnpm start` | `http://localhost:3100/api` | **기준정보(MDM) API만 구현돼 있다** — `auth`·`health`·`mdm/{warehouses,locations,items,workers,departments,codes}`뿐이다. `/logistics/**`·`/inventory/**`·`/trace/**`·`/quality/**`·`/app/**`는 이 문서 작성 시점에 전부 미구현 |

**⚠ 실서버 로그인 경로가 어긋나 있다.** 관리웹 로그인 화면은 `POST /app/sessions`를 부르는데 실서버는 `POST /api/auth/login`을 쓴다. 이 어긋남이 풀리기 전에는 **실서버로는 로그인 화면을 통과할 수 없다** — 아래 표의 「실행 가능 환경」이 "실서버"인 시나리오도 이 전제가 풀린 뒤에만 유효하다. 목 서버는 계약 정본(`app-공통.json`)을 그대로 서빙하므로 이 문제가 없다.

**「실행 가능 환경」 값의 뜻**

| 값 | 뜻 |
| --- | --- |
| 실서버 | 로그인 경로 정합 후, 끝까지(저장 → 목록 반영 확인) 실행 검증 가능 |
| 목 서버 | 화면 진입·조작·입력 검증까지는 확인 가능. 저장 후 상태 반영은 확인 불가(Prism 한계) |
| 미구현 | 서버 오퍼레이션이 아직 없어 화면이 그 사실을 안내만 하는 상태. 그 상태 자체가 검증 대상 |

## 알려진 제약 — 시나리오 판정 시 참고

이 문서가 작성된 시점 기준으로 아래는 **결함이 아니라 알려진 상태**다. 자동화 Agent와 QA 모두 이 상태와 실제 화면이 일치하면 「통과」로 판정한다.

1. **W-01-13 물류 문서 진행현황**은 문서 유형 값 목록이 미확정이라 목록 조회가 한 번도 나가지 않는다(MW-23). 표만 채워지면 화면 전체가 저절로 살아나는 구조다.
2. **실서버는 MDM(기준정보) API만 구현돼 있다.** `/logistics/**`·`/inventory/**`·`/trace/**`·`/quality/**`·`/app/**`를 부르는 화면은 지금 실서버로 끝까지 검증할 수 없다 — 이 문서에서 「실행 가능 환경: 목 서버(화면 확인만)」로 표기한 시나리오가 여기 해당한다.
3. **실서버 로그인 경로가 클라이언트와 어긋나 있다**(`/app/sessions` vs `/api/auth/login`). 창고·Location(W-06-07)조차 이 전제가 풀리기 전에는 실행할 수 없다.
4. **여러 화면의 선택 필터가 「선택지 준비 중」이다**(공통코드 값 목록 미확정) — 조회 자체를 막지는 않지만 그 필터로는 좁힐 수 없다. 해당 화면: 입하 예정 조회·초과 입하 분리·정상품 입하 처리·재고 현황·긴급 IQC 생략 한도승인·재고실사(조정 사유)·공급사 반품·폐기(창고 유형).
5. **목 서버(Prism)는 상태가 없다.** 저장·등록·전기 뒤 목록에 실제로 반영되는지, 낙관적 잠금 충돌(409), `STATE_LOCKED`는 목 서버로 검증할 수 없다 — 이 문서에서 「(목 서버 한계) 요청 전송만 확인」이라 적은 스텝이 이에 해당하며, 실서버가 준비되면 그 스텝을 결과 확인까지 확장한다.
6. **베트남어 i18n은 실제로 없다** — `vi.ts`가 한국어를 그대로 재수출하는 자리표시자다. 다국어 표시 검증은 이번 범위에서 뺀다.
7. **이 문서에 실린 PDA 화면(M-01-04)은 조회 전용이다.** 관리웹에는 스캔 입력이 없다 — 자재창고 쓰기 화면은 전부 목록에서 골라 수량을 입력하는 방식이다. ⚠ 다만 PDA에는 M-01-04 말고도 이미 구현된 스캔·쓰기 화면이 더 있다(M-01-01·05·06·07·13) — 위 「범위」 참고. 이번 범위에서 뺐을 뿐 「PDA는 조회 전용 하나뿐」이라는 뜻은 아니다.
8. **오프라인 재전송 큐(outbox)는 POP(Electron) 셸에 그릇만 있고 화면에서 쓰이지 않는다.** 자재·창고 화면은 전부 온라인 전용이며, 응답 없는 요청은 「다시 보내지 말고 처리 이력에서 확인하라」는 안내로만 처리된다(MW-36 오프라인 케이스는 조회 자체를 막는 것이지 큐잉이 아니다).
9. **M-01-08(자재출고피킹)·M-01-09(생산창고 입고·호퍼 잔량 입력)이 설계에는 있지만 구현되지 않았다.** 자재창고가 출고한 것을 생산 현장에서 수령 확인하는 화면인데, 이게 없어 `production-execution.md`의 P-02-03(자재 투입 스캔)이 읽는 「계획 대비 수령」 데이터를 실제로 만들 방법이 이 코드베이스에 없다 — 목 서버 example 값으로만 그 표를 확인할 수 있다.
