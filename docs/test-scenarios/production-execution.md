# 생산실행 사용자 테스트 시나리오

**목적** — 개발이 끝난 화면을 실제로 실행해 사람이 손으로 확인하는 시나리오다. 둘로 쓴다.

1. **자동화**: 브라우저 자동화 Agent가 이 표를 따라 프로그램을 조작하고 「기대 결과」와 실제 화면을 대조한다.
2. **QA 전달**: 품질 담당팀이 같은 표를 손으로 따라 하며 테스트 케이스로 쓴다.

작성 시점 이후 화면이 바뀌면(필드·문구·검증 규칙) 이 문서도 함께 고친다 — 낡은 시나리오는 실제 화면과 다른 것을 「기대 결과」로 남겨 오히려 해가 된다.

> **이 저장소는 공개(public)다.** 아래 테스트 데이터는 전부 지어낸 합성값이며, 화면 슬라이스의 `*.test.ts(x)`가 이미 쓰는 계열(`SYN-` 등)을 그대로 재사용했다. 실 P/O 번호·W/O 번호·품목코드·거래처·고객사명·인프라 정보를 이 문서에 적지 않는다(V3 워크플로 공개 저장소 경계).

## 범위

생산실행 범위의 화면 — **관리웹 7개**(사이드바 「생산」 섹션) + **POP(현장 단말) 2개**. 모바일(Capacitor)에는 이 도메인 화면이 하나도 없다(§알려진 제약 13). 목록·라우트는 `apps/web/src/routes/index.tsx`(관리웹)·`apps/web/src/routes/pop.tsx`(POP) · 사이드바 라벨은 `apps/web/src/app/layout.tsx`가 정본이다.

| 화면ID | 화면명 | 셸 | 라우트 |
| --- | --- | --- | --- |
| W-02-01 | P/O 수신·조회 | 웹 | `/production/production-orders` |
| W-02-02 | W/O 전개·편성 | 웹 | `/production/production-plans` |
| W-02-03 | 4M 자원배정·유효성 점검 | 웹 | `/production/work-order-assignments` |
| W-02-04 | W/O 확정·배포·생산LOT 선발행 | 웹 | `/production/work-order-release` |
| W-02-05 | W/O 마감·ERP 실적 송신 | 웹 | `/production/work-order-close` |
| W-02-07 | 긴급 W/O 발행 | 웹 | `/production/emergency-work-orders` |
| W-02-08 | W/O 진행현황 조회 | 웹 | `/production/work-order-progress` |
| P-02-03 | 자재 투입 스캔 | POP | `/pop/material-input` |
| P-02-12 | 긴급 W/O 현장 투입·실적 | POP | `/pop/emergency-work-orders` |

⚠ **W-02-06은 이 저장소의 라우터·사이드바에 없다.** 번호가 비어 있는 이유는 확인하지 않았다 — 다른 화면 묶음이거나 아직 배정되지 않은 번호일 수 있다. 착수 여부는 설계 저장소가 정본이다.

⚠ **P-02-01(작업 시작)·P-02-04(실적 등록)·P-02-10(결품 처리)은 이 저장소에 아직 없다.** 코드 주석이 셋 모두 "아직 이 저장소에 없다"고 명시한다 — 아래 사슬에서 이 셋이 서야 할 자리는 공백으로 남는다(§알려진 제약 9~11).

⚠ **POP은 별도 앱이 아니라 관리웹(`apps/web`) 화면 슬라이스다.** `apps/pop`(Electron)은 아직 별도 빌드 엔트리가 없고 `apps/web/dist`를 그대로 복사해 쓴다(코드 주석) — 그래서 이 문서의 POP 시나리오도 관리웹 개발 서버에서 `/pop/...` 주소로 직접 들어가는 것으로 검증한다.

**업무 순서 사슬(관리웹)** — 코드 주석(`routes/index.tsx`)이 밝힌 화면 간 이동 경로: P/O 조회(W-02-01) → 그 상세에서 「W/O 전개·편성」 링크로 계획 편성(W-02-02) → 전개 확정 결과에서 W/O를 골라 4M 배정(W-02-03) → 배정을 마친 W/O를 확정·배포(W-02-04) → 배포된 W/O의 실적을 마감(W-02-05). 긴급 W/O 발행(W-02-07)은 계획을 거치지 않는 별개 갈래이고, 진행현황 조회(W-02-08)는 이 흐름 전체를 가로질러 보는 조회 전용 화면이다.

**현장(POP) 사슬과 그 공백** — W-02-04(확정·배포)로 배포된 W/O는 현장 단말에서 자재를 투입하는 것으로 이어진다(P-02-03). 그런데 그 앞에 서야 할 P-02-01(작업 시작 — 단말·공정·작업지시를 정하는 화면)이 없어, P-02-03이 요구하는 단말·공정 컨텍스트(`patterns/pop-identity`)를 채우는 공급자가 어디에도 없다 — 그 결과 이 화면은 지금 **자재를 스캔해 담는 것까지만 되고, 개별 기록과 투입 확정은 항상 잠긴다**(PE-21). 그 뒤에 와야 할 실적 등록(P-02-04)도 없어, W-02-05(마감)가 다루는 실적판정 데이터가 실제로 어디서 만들어지는지는 이 저장소 범위 밖이다. **즉 계획→배포까지는 관리웹에서 끝까지 따라갈 수 있지만, 현장 실행(투입 확정→생산 진행→실적 등록)은 지금 코드베이스만으로는 끝까지 따라갈 수 없다.** 긴급 갈래(W-02-07 → P-02-12)도 같은 지점(P-02-03)에서 같은 벽에 부딪히고, P-02-12의 [실적 입력] 버튼은 아예 라우트가 없다(PE-24).

**한 단계 더 앞선 공백 — 수령 데이터 자체가 생기지 않는다.** P-02-03이 읽는 「계획 대비 수령」(`shopfloor_receipt`·`shopfloor_receipt_line`)은 설계상 자재창고관리(도메인 01) **모바일** 화면 `M-01-09`(생산창고 입고·호퍼 잔량 입력)가 자재창고의 출고(`M-01-08` 자재출고피킹)를 현장에서 수령 확인하며 만드는 데이터다(설계 문서 `design/wiki/screens/01/M-01-09-생산창고입고호퍼잔량.md` §5-4가 "P-02-03이 수령을 겸하는 것을 권고"한다고 명시). 그런데 `M-01-08`·`M-01-09` 둘 다 이 저장소에 구현돼 있지 않다 — `docs/test-scenarios/material-warehouse.md`의 「알려진 제약」에도 같은 내용을 남겼다. 그래서 P-02-03의 「계획 대비 수령」 표는 지금 목 서버 example 값으로만 채워지고, 실제 수령 데이터가 만들어지는 경로는 이 코드베이스 어디에도 없다.

## 실행 환경

| 환경 | 실행 | 기준 URL | 특징 |
| --- | --- | --- | --- |
| 목 서버(Prism) | `pnpm mock` (별도 터미널) | `http://127.0.0.1:4010` | 계약 example을 그대로 돌려준다. **상태가 없다** — 등록·저장 후 목록에 반영되는지, 상태 전이, 낙관적 잠금 충돌(409)은 검증할 수 없다 |
| 관리웹 | `pnpm --filter @omf-mes/web dev` | `http://localhost:5173`(포트 점유 시 5174…) | 기본 API 기준 URL이 목 서버(`127.0.0.1:4010`)다. 실서버로 붙이려면 `VITE_API_BASE_URL=http://localhost:3100/api pnpm --filter @omf-mes/web dev` |
| 실서버(`omf-mes-server`) | `docker compose up -d && pnpm exec prisma migrate deploy && pnpm run db:seed && pnpm start` | `http://localhost:3100/api` | **기준정보(MDM) API만 구현돼 있다** — `auth`·`health`·`mdm/{warehouses,locations,items,workers,departments,codes}`뿐이다. `/production/**`는 이 문서 작성 시점에 미구현 |

**⚠ 실서버 로그인 경로가 어긋나 있다.** 관리웹 로그인 화면은 `POST /app/sessions`를 부르는데 실서버는 `POST /api/auth/login`을 쓴다. 이 어긋남이 풀리기 전에는 **실서버로는 로그인 화면을 통과할 수 없다.** 목 서버는 계약 정본을 그대로 서빙하므로 이 문제가 없다.

**「실행 가능 환경」 값의 뜻**

| 값 | 뜻 |
| --- | --- |
| 목 서버 | 화면 진입·조작·입력 검증까지는 확인 가능. 저장 후 상태 반영은 확인 불가(Prism 한계) |
| 목 서버(화면 확인만) | 요청이 나가는 것까지만 확인 가능. 배포·마감·발행 같은 되돌릴 수 없는 처리의 결과 반영은 실서버 구현 후에만 검증 가능 |

**POP 화면(P-02-03·P-02-12) 실행** — 별도 실행 방법이 없다. 관리웹 개발 서버(`pnpm --filter @omf-mes/web dev`)를 띄운 채 브라우저로 `/pop/...` 주소에 직접 들어간다. **단말 컨텍스트(`patterns/pop-identity`)를 채우는 공급자가 코드에 없어, 로컬에서도 실서버에서도 게이팅은 항상 `unidentified`다** — 이것은 실행 환경의 한계가 아니라 현재 코드베이스의 실제 상태다(§알려진 제약 10).

## 알려진 제약 — 시나리오 판정 시 참고

이 문서가 작성된 시점 기준으로 아래는 **결함이 아니라 알려진 상태**다. 자동화 Agent와 QA 모두 이 상태와 실제 화면이 일치하면 「통과」로 판정한다.

1. **실서버는 MDM(기준정보) API만 구현돼 있다.** `/production/**`를 부르는 화면은 지금 실서버로 끝까지 검증할 수 없다 — 이 문서에서 「실행 가능 환경: 목 서버(화면 확인만)」로 표기한 시나리오가 여기 해당한다. 다만 상태 코드값 조회(`/mdm/code-values`, PE-10·PE-16의 상태 필터)는 MDM API라 실서버에서도 실제로 동작할 수 있다.
2. **W-02-01(P/O 수신·조회)의 「상태」 필터는 값이 확정되지 않아 비어 있다.** `statusOptionsPending` 안내만 뜨고 실제로 상태로 좁혀 볼 수 없다 — 값이 오면 이 칸만 채워진다.
3. **W-02-08(W/O 진행현황 조회)의 요약 카드는 「전체」 하나만 실제 값이다.** 상태별 건수·양품/불량/손실 수량·달성률은 서버가 아직 내려주지 않아(omf-mes#265) 라벨만 보이고 값은 비어 있다. 「지연」 표시도 서버 필드가 없어 화면이 계산한 참고값이다.
4. **목 서버(Prism)는 상태가 없다.** 저장·확정·배포·발행·마감 뒤 목록에 실제로 반영되는지, 낙관적 잠금 충돌(409)은 목 서버로 검증할 수 없다 — 이 문서에서 「(목 서버 한계) 요청 전송만 확인」이라 적은 스텝이 이에 해당하며, 실서버가 준비되면 그 스텝을 결과 확인까지 확장한다.
5. **W-02-07(긴급 W/O 발행)의 발행·배포는 정상 경로에서 두 호출**(① 지시 생성 — 응답이 ETag를 함께 준다 → ② 그 ETag를 `If-Match`로 실어 배포)이다. ①은 성공하고 ②가 실패하는 창이 실제로 존재해, 재시도가 ETag를 다시 받아 오는 조회(GET)를 거칠 수 있다. 이 창에서 화면은 「성공」이라 말하지 않고 W/O 번호를 보이며 **배포만 재시도**하게 한다 — 새로 발행하면 같은 지시가 둘이 되므로 그렇게 만들지 않는다.
6. ~~**긴급 W/O 발행이 유형 코드 미확정으로 잠겨 있었다**~~ — 2026-09-02 기준 해소됨. `EMERGENCY_WORK_ORDER_TYPE_CODE`가 값을 갖고 있어 정상 발행이 가능하다.
7. **W-02-02·W-02-03은 사이드바에 있지만 그리로 바로 들어오면 빈손이다.** 둘 다 `?productionOrderId=`·`?productionPlanId=` 맥락이 있어야 작업 구획이 열리는데, 사이드바 클릭은 그 맥락 없이 화면만 연다 — 그때는 안내와 이전 화면으로의 링크만 보인다. 실제 작업은 앞 화면(P/O 수신·조회 → W/O 전개·편성)의 결과에서 나오는 링크를 거쳐야 한다.
8. **베트남어 i18n은 실제로 없다** — `vi.ts`가 한국어를 그대로 재수출하는 자리표시자다. 다국어 표시 검증은 이번 범위에서 뺀다.
9. **P-02-01(작업 시작)·P-02-04(실적 등록)·P-02-10(결품 처리)은 이 저장소에 아직 없다.** 코드 주석이 셋 모두 "아직 이 저장소에 없다"고 명시한다 — 생산실행의 현장 실행 구간(작업 시작 → 자재 투입 확정 → 생산 진행 → 실적 등록)을 처음부터 끝까지 실제로 따라갈 수 없는 이유가 이 공백이다.
10. **P-02-03(자재 투입 스캔)은 단말 컨텍스트(`patterns/pop-identity`)를 채우는 공급자가 아직 없어 지금은 항상 게이팅이 `unidentified`다.** 계획 대비 수령 확인·스캔해 담기는 정상 동작하지만, 개별 [기록]과 [투입 확정]은 항상 잠긴다(PE-21) — 오프라인 큐잉(outbox)도 그 앞의 게이트를 지나야 큐에 담기므로 지금은 검증할 방법이 없다.
11. **P-02-12(긴급 W/O 현장 투입·실적)의 [실적 입력] 버튼은 존재하지 않는 라우트(`/pop/production-result`)를 가리킨다.** `P-02-04`가 서기 전까지는 이 버튼을 눌러도 진입할 화면이 없다(PE-24).
12. **POP은 별도 앱이 아니라 관리웹(`apps/web`) 빌드를 그대로 쓴다.** `apps/pop`(Electron)은 아직 별도 빌드 엔트리가 없다 — 로컬 검증은 관리웹 개발 서버에서 `/pop/...` 주소로 직접 들어가는 것으로 한다.
13. **모바일(Capacitor)에는 생산실행(도메인 02) 화면이 하나도 없다.** 라우트·화면 슬라이스 어디에도 없다 — 빠뜨린 것이 아니라 이 도메인이 지금 모바일 셸에 배정돼 있지 않다.
14. **P-02-03(자재 투입 스캔)이 읽는 「계획 대비 수령」 데이터는 만들어질 방법이 없다.** 설계상 그 데이터(`shopfloor_receipt`)는 자재창고관리(도메인 01) 모바일 화면 `M-01-09`(생산창고 입고·호퍼 잔량 입력)가 자재창고 출고(`M-01-08` 자재출고피킹)를 수령 확인하며 만드는데, 이 둘 다 이 저장소에 구현돼 있지 않다(`material-warehouse.md`의 「알려진 제약」에도 같은 내용을 남겼다) — 도메인 01·02 경계를 가로지르는 공백이라 두 문서에 함께 적는다.
